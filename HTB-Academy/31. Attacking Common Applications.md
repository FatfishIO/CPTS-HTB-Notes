# Attacking Common Applications
## Introduction to Attacking Common Applications

| **Category** | **Details** |
|---|---|
| **Context** | Web-based applications are prevalent in most if not all environments encountered as penetration testers; assessments will include a wide variety of web applications such as CMS, custom web applications, intranet portals used by developers and sysadmins, code repositories, network monitoring tools, ticketing systems, wikis, knowledge bases, issue trackers, servlet container applications, and more; it's common to find the same applications across many different environments — an application may not be vulnerable in one environment but may be misconfigured or unpatched in the next; an assessor needs a firm grasp of enumerating and attacking the common applications covered in this module |
| **Web applications — architecture** | Interactive applications accessed via web browsers; typically adopt a client-server architecture; made up of front-end components (website interface, "what the user sees") running on the client-side (browser) and back-end components (web application source code) running on the server-side (back end server/databases); for an in-depth study, see the Introduction to Web Applications module |
| **Vulnerability scope** | All types of web applications (commercial, open-source, custom) can suffer from the same kinds of vulnerabilities and misconfigurations — the top 10 web application risks covered in the OWASP Top 10; may encounter vulnerable versions of many common applications suffering from known (public) vulnerabilities such as SQL injection, XSS, remote code execution bugs, local file read, and unrestricted file upload; equally important to understand how to abuse built-in functionality to achieve remote code execution |
| **Why web apps are attractive targets** | As organizations harden external perimeter and limit exposed services, web applications become a more attractive target for malicious actors and penetration testers; more companies are transitioning to remote work and exposing (intentionally or unintentionally) applications to the outside world; applications discussed are typically just as likely to be exposed on the external network as the internal network; can serve as a foothold into the internal environment during an external assessment or as a foothold, lateral movement, or additional issue to report during an internal assessment |
| **State of application security (2021 survey)** | Research survey commissioned by Barracuda, 750 decision-makers in companies with 500+ employees across the globe; findings: **72%** of respondents suffered at least one breach due to an application vulnerability, **32%** suffered two breaches, **14%** suffered three; challenges: bot attacks (43%), software supply chain attacks (39%), vulnerability detection (38%), securing APIs (37%); this module focuses on known vulnerabilities and misconfigurations in open-source and commercial applications |

| **Learning approach** | Make a concerted effort to learn how applications work and why specific vulnerabilities/misconfigurations exist rather than just reproducing examples; these skills help identify attack paths in different applications encountered for the first time |
| **A Quick Story — Nexus Repository OSS** | During an external pentest, encountered Nexus Repository OSS from Sonatype (never seen before); found default admin credentials `admin:admin123` unchanged → logged in and poked around admin functionality; leveraged the API as an authenticated user to gain remote code execution; encountered the application on another assessment, logged in with default credentials again, this time abused the Tasks functionality (disabled the first time) and wrote a quick Groovy script in Java syntax to execute a script and gain RCE — similar to abusing the Jenkins script console later in this module |
| **A Quick Story — other apps** | Encountered other applications such as OpManager from ManageEngine that allow running a script as the user the application runs under (usually the powerful `NT AUTHORITY\SYSTEM` account) and gain a foothold; never overlook applications during internal and external assessments — they may be the only way "in" in a relatively well-maintained environment |
| **Common Applications — WordPress** | Open-source CMS used for multiple purposes; often used to host blogs and forums; highly customizable and SEO friendly → popular among companies; customizability and extensible nature make it prone to vulnerabilities through third-party themes and plugins; written in PHP, usually runs on Apache with MySQL backend |
| **Common Applications — Drupal** | Another open-source CMS popular among companies and developers; written in PHP; supports MySQL or PostgreSQL for the backend; SQLite can be used if no DBMS installed; like WordPress, allows users to enhance websites through themes and modules |
| **Common Applications — Joomla** | Yet another open-source CMS written in PHP that typically uses MySQL but can run with PostgreSQL or SQLite; used for blogs, discussion forums, e-commerce, and more; heavily customizable with themes and extensions; estimated to be the third most used CMS on the internet after WordPress and Shopify |
| **Common Applications — Tomcat** | Apache Tomcat is an open-source web server that hosts applications written in Java; initially designed to run Java Servlets and Java Server Pages (JSP) scripts; popularity increased with Java-based frameworks; now widely used by frameworks such as Spring and tools such as Gradle |
| **Common Applications — Jenkins** | Open-source automation server written in Java that helps developers build and test software projects continuously; server-based system that runs in servlet containers such as Tomcat; researchers have uncovered various vulnerabilities including some that allow remote code execution without authentication |
| **Common Applications — Splunk** | Log analytics tool used to gather, analyze, and visualize data; though not originally intended as a SIEM tool, often used for security monitoring and business analytics; deployments often house sensitive data and could provide a wealth of information if compromised; historically has not suffered from a considerable amount of known vulnerabilities aside from an information disclosure vulnerability (CVE-2018-11409) and an authenticated remote code execution vulnerability in very old versions (CVE-2011-4642) |
| **Common Applications — PRTG Network Monitor** | Agentless network monitoring system used to monitor metrics such as uptime, bandwidth usage, and more from a variety of devices (routers, switches, servers, etc.); utilizes auto-discovery mode to scan a network and then leverages protocols such as ICMP, WMI, SNMP, and NetFlow to communicate with and gather data from discovered devices; written in Delphi |
| **Common Applications — osTicket** | Widely-used open-source support ticketing system; used to manage customer service tickets received via email, phone, and the web interface; written in PHP; can run on Apache or IIS with MySQL as the backend |
| **Common Applications — GitLab** | Open-source software development platform with a Git repository manager, version control, issue tracking, code review, continuous integration and deployment, and more; originally written in Ruby but now utilizes Ruby on Rails, Go, and Vue.js; offers community (free) and enterprise versions |

## Application Discovery & Enumeration

| **Category** | **Details** |
|---|---|
| **Context** | Organizations should maintain an asset inventory covering all network-connected devices, installed software, and applications; if an organization is unsure what is present on its network, it cannot know what to protect and what potential holes exist; should know if applications are local or third-party hosted, their patch level, end-of-life status, detect rogue applications (shadow IT), ensure strong (non-default) passwords, ideally MFA; certain applications have administrative portals restricted to specific IPs or localhost |
| **Reality** | Many organizations do not know everything on their network, and some have very little visibility; enumeration can help clients enhance or start building an asset inventory; may identify forgotten applications, demo versions with expired trials converted to no-auth versions (e.g., Splunk), default/weak credentials, unauthorized/misconfigured applications, and applications with public vulnerabilities; provide data as findings (e.g., default credentials admin:admin), appendices (services mapped to hosts), or supplemental scan data; can educate clients on tools to perform periodic/proactive recon |
| **Enumeration skills** | Strong enumeration skills are needed to get the "lay of the land" starting with very little to no information (black box discovery or just CIDR ranges); typically start with a ping sweep to identify live hosts, then targeted port scanning, then deeper port scanning to identify running services; in a network with hundreds or thousands of hosts, enumeration data can become unwieldy |
| **Nmap web discovery** | `nmap -p 80,443,8000,8080,8180,8888,10000 --open -oA web_discovery -iL scope_list`; may find an enormous amount of hosts with services on ports 80 and 443 alone; sifting through enumeration data by hand in a large environment is far too time-consuming, especially under strict time constraints; browsing to each IP/hostname + port is highly inefficient |
| **Tools overview** | Two phenomenal tools every tester should have: **EyeWitness** and **Aquatone**; both can be fed raw Nmap XML scan output (Aquatone also takes Masscan XML; EyeWitness takes Nessus XML); used to quickly inspect all hosts running web applications and take screenshots; screenshots assembled into a report to work through in the browser to assess web attack surface; help narrow down potentially 100s of hosts and build a targeted list of applications to enumerate and attack; available for Windows and Linux |
| **Getting Organized — overview** | Although notetaking, reporting, and documentation are covered in a separate module, it is worth selecting a notetaking application and beginning to set it up to record data gathered in this phase; good options include OneNote, Evernote, Notion, Cherrytree, etc. — personal preference; work on notetaking methodology and create templates for every assessment type |
| **Getting Organized — breakdown** | Break down the Enumeration & Discovery section into a separate **Application Discovery** section; create subsections for scope, scans (Nmap, Nessus, Masscan), application screenshotting, and interesting/notable hosts to dig into later; time and date stamp every scan, save all output and exact scan syntax and targeted hosts (useful if client has questions about activity); being organized from the start and keeping detailed logs/notes helps with the final report; set up the skeleton of the report at the beginning of the assessment along with the notebook so sections can be filled in while waiting for scans to finish |
| **Getting Organized — example OneNote structure** | External Penetration Test - <Client Name>: Scope (in-scope IPs/ranges, URLs, fragile hosts, testing timeframes, limitations, relative info); Client Points of Contact; Credentials; Discovery/Enumeration (Scans, Live hosts, Application Discovery, Scans, Interesting/Notable Hosts); Exploitation (<Hostname or IP>, <Hostname or IP>); Post-Exploitation (<Hostname or IP>, <Hostname or IP>) |
| **Getting Organized — practice** | Replicate this structure and record all work on this module as if working through an actual engagement; helps refine documentation methodology (essential skill for a successful penetration tester); having notes to refer back to from each section will be helpful for the three skills assessments at the end of the module and as you progress in the Penetration Tester path |
| **Initial Enumeration — scope example** | `cat scope_list` → `app.inlanefreight.local`, `dev.inlanefreight.local`, `drupal-dev.inlanefreight.local`, `drupal-qa.inlanefreight.local`, `drupal-acc.inlanefreight.local`, `drupal.inlanefreight.local`, `blog-dev.inlanefreight.local`, `blog.inlanefreight.local`, `app-dev.inlanefreight.local`, `jenkins-dev.inlanefreight.local`, `jenkins.inlanefreight.local`, `web01.inlanefreight.local`, `gitlab-dev.inlanefreight.local`, `gitlab.inlanefreight.local`, `support-dev.inlanefreight.local`, `support.inlanefreight.local`, `inlanefreight.local`, `10.129.201.50` |
| **Initial Enumeration — approach** | Start with an Nmap scan of common web ports (80,443,8000,8080,8180,8888,10000), then run EyeWitness or Aquatone (or both depending on results) against the initial scan; while reviewing the screenshot report, may run a more thorough Nmap scan against the top 10,000 ports or all TCP ports depending on scope size; enumeration is iterative — run a web screenshotting tool against any subsequent Nmap scans to ensure maximum coverage; on a non-evasive full scope pentest, usually run a Nessus scan too, but must be able to perform assessments without relying on scanning tools |
| **Initial Enumeration — methodology** | Even though most assessments are time-limited, provide maximum value by establishing a repeatable and thorough enumeration methodology applicable to all environments; be efficient during information gathering/discovery while not taking shortcuts that could leave critical flaws undiscovered; everyone's methodology and preferred tools vary — create one that works well while arriving at the same end goal; all scans during a non-evasive engagement gather data as inputs to manual validation and manual testing — do not rely solely on scanners; the human element is essential; most unique and severe vulnerabilities and misconfigurations are found only through thorough manual testing |

# Content Management Systems (CMS)
## WordPress - Discovery & Enumeration

| **Category** | **Details** |
|---|---|
| **WordPress — overview** | Launched in 2003; open-source Content Management System (CMS) used for multiple purposes; often used to host blogs and forums; highly customizable and SEO friendly → popular among companies; customizability and extensible nature make it prone to vulnerabilities through third-party themes and plugins; written in PHP, usually runs on Apache with MySQL backend |
| **WordPress — market share** | At time of writing, accounts for around **32.5%** of all sites on the internet; most popular CMS by market share |
| **WordPress — interesting facts** | Over 50,000 plugins and over 4,100 GPL-licensed themes; 317 separate versions released since initial launch; roughly 661 new WordPress websites built every day; blogs written in over 120 languages; a study showed roughly **8%** of WordPress hacks happen due to weak passwords, while **60%** were due to an outdated WordPress version; according to WPScan, out of nearly 4,000 known vulnerabilities, **54%** are from plugins, **31.5%** from WordPress core, and **14.5%** from themes; major brands using WordPress include The New York Times, eBay, Sony, Forbes, Disney, Facebook, Mercedes-Benz, and many more |
| **WordPress — attack surface** | Extremely prevalent on the internet and presents a vast attack surface; guaranteed to come across WordPress during many External Penetration Test assessments; must understand how it works, how to enumerate it, and various ways it can be attacked; the Hacking WordPress module on HTB Academy goes very far in-depth |
| **Discovery/Footprinting — robots.txt** | Quick way to identify a WordPress site is browsing to `/robots.txt`; typical example: `User-agent: *`, `Disallow: /wp-admin/`, `Allow: /wp-admin/admin-ajax.php`, `Disallow: /wp-content/uploads/wpforms/`, `Sitemap: https://inlanefreight.local/wp-sitemap.xml`; presence of `/wp-admin` and `/wp-content` directories is a dead giveaway; browsing to `wp-admin` typically redirects to `wp-login.php` — the login portal to the WordPress instance's back-end |
| **Discovery — directories** | Plugins stored in `wp-content/plugins` (helpful to enumerate vulnerable plugins); themes stored in `wp-content/themes` (carefully enumerated as they may lead to RCE) |
| **WordPress — user types** | **Administrator**: access to administrative features — adding/deleting users and posts, editing source code; **Editor**: can publish and manage posts, including other users' posts; **Author**: can publish and manage their own posts; **Contributor**: can write and manage their own posts but cannot publish them; **Subscriber**: standard users who can browse posts and edit their profiles; getting access to an administrator is usually sufficient to obtain code execution on the server; editors and authors might have access to certain vulnerable plugins which normal users don't |
| **Enumeration — page source** | Quick way to identify WordPress is looking at page source; viewing with cURL and grepping for WordPress confirms use and footprints the version number: `curl -s http://blog.inlanefreight.local \| grep WordPress` → `<meta name="generator" content="WordPress 5.8" /` |

| **Category** | **Details** |
|---|---|
| **Context** | Even unauthenticated access to a GitLab instance could lead to sensitive data compromise; if able to gain access as a valid company user or an admin, could potentially uncover enough data to fully compromise the organization; GitLab has **553 CVEs** reported as of September 2021; while not every single one is exploitable, there have been several severe ones over the years that could lead to remote code execution |

| **Username Enumeration — lockout considerations** | As with any type of password spraying attack, be mindful of account lockout and other kinds of interruptions; in versions below **16.6**, GitLab's defaults are set to **10 failed login attempts**, resulting in an automatic unlock after **10 minutes**; previously, changing these settings required compiling GitLab from source, as there was no option to modify them through the admin UI; however, starting with GitLab version 16.6, administrators can configure these values directly through the admin UI; the number of authentication attempts before locking an account and the unlock period can be set using the `max_login_attempts` and `failed_login_attempts_unlock_period_in_minutes` settings; if these settings are not manually configured, they will still default to 10 failed login attempts and an unlock period of 10 minutes; additionally, while admins can modify the minimum password length to encourage stronger passwords, this alone will not fully mitigate the risk of password attacks |

## Attacking Common Gateway Interface (CGI) Applications - Shellshock

| **Category** | **Details** |
|---|---|
| **CGI — overview** | Common Gateway Interface used to help a web server render dynamic pages and create a customized response for the user making a request via a web application; primarily used to access other applications running on a web server; essentially middleware between web servers, external databases, and information sources; CGI scripts and programs are kept in the `/CGI-bin` directory on a web server and can be written in C, C++, Java, PERL, etc.; CGI scripts run in the security context of the web server; often used for guest books, forms (email, feedback, registration), mailing lists, blogs, etc.; language-independent and can be written very simply to perform advanced tasks much easier than writing them using server-side programming languages |
| **CGI — why used** | If the webserver must dynamically interact with the user; when a user submits data to the web server by filling out a form, the CGI application processes the data and returns the result to the user via the webserver |
| **CGI — how it works** | 1) A directory is created on the web server containing the CGI scripts/applications (typically called `CGI-bin`); 2) The web application user sends a request to the server via a URL (e.g., `https://acme.com/cgi-bin/newchiscript.pl`); 3) The server runs the script and passes the resultant output back to the web client |
| **CGI — disadvantages** | The CGI program starts a new process for each HTTP request which can take up a lot of server memory; a new database connection is opened each time; data cannot be cached between page loads which reduces efficiency; risks and inefficiencies outweigh the benefits; CGI has not kept up with the times and has not evolved to work well with modern web applications; superseded by faster and more secure technologies; however, testers will run into web applications from time to time that still use CGI and will often see it when encountering embedded devices during an assessment |
| **Shellshock — overview** | Perhaps the most well-known CGI attack is exploiting the **Shellshock** (aka, "Bash bug") vulnerability via CGI; **CVE-2014-6271** discovered in 2014; relatively simple to exploit and can still be found in the wild (during pentests) from time to time; security flaw in the Bash shell (GNU Bash up until version **4.3**) that can be used to execute unintentional commands using environment variables; at the time of discovery, it was a **25-year-old bug** and a significant threat to companies worldwide |
| **Shellshock — mechanism** | Allows an attacker to exploit old versions of Bash that save environment variables incorrectly; typically when saving a function as a variable, the shell function will stop where it is defined to end by the creator; vulnerable versions of Bash will allow an attacker to execute operating system commands that are included after a function stored inside an environment variable |
| **Shellshock — simple example** | Define an environment variable and include a malicious command afterward: `env y='() { :;}; echo vulnerable-shellshock' bash -c "echo not vulnerable"`; when the above variable is assigned, Bash will interpret the `y='() { :;};'` portion as a function definition for a variable `y`; the function does nothing but returns an exit code 0, but when it is imported, it will execute the command `echo vulnerable-shellshock` if the version of Bash is vulnerable; this (or any other command, such as a reverse shell one-liner) will be run in the context of the web server user; most of the time, this will be a user such as `www-data`, and we will have access to the system but still need to escalate privileges; occasionally will get really lucky and gain access as the root user if the web server is running in an elevated context |
| **Shellshock — patched system** | If the system is not vulnerable, only "not vulnerable" will be printed: `env y='() { :;}; echo vulnerable-shellshock' bash -c "echo not vulnerable"` → `not vulnerable`; this behavior no longer occurs on a patched system, as Bash will not execute code after a function definition is imported; furthermore, Bash will no longer interpret `y=() {...}` as a function definition; function definitions within environment variables must now be prefixed with `BASH_FUNC_` |
| **Enumeration — Gobuster** | Hunt for CGI scripts using a tool such as Gobuster: `gobuster dir -u http://10.129.204.231/cgi-bin/ -w /usr/share/wordlists/dirb/small.txt -x cgi` → output: `Gobuster v3.1.0`, `Url: http://10.129.204.231/cgi-bin/`, `Method: GET`, `Threads: 10`, `Wordlist: /usr/share/wordlists/dirb/small.txt`, `Negative Status codes: 404`, `User Agent: gobuster/3.1.0`, `Extensions: cgi`, `Timeout: 10s`; result: `/access.cgi (Status: 200) [Size: 0]` |

# Thick Client Applications
## Attacking Thick Client Applications

| **Category** | **Details** |
|---|---|
| **Thick client — overview** | Applications installed locally on computers; unlike thin client applications that run on a remote server and are accessed through the web browser, these do not require internet access to run and perform better in processing power, memory, and storage capacity; usually enterprise applications created to serve specific purposes — project management systems, customer relationship management systems, inventory management tools, and other productivity software; usually developed using Java, C++, .NET, or Microsoft Silverlight |
| **Java — security measures** | Java has a technology called **sandbox** — a virtual environment that allows untrusted code (such as code downloaded from the internet) to run safely on a user's system without posing a security risk; isolates untrusted code, preventing it from accessing or modifying system resources and other applications without proper authorization; also Java API restrictions and Code Signing help create a more secure environment |
| **.NET — thick client definition** | A thick client, also known as a rich client or fat client, refers to an application that performs a significant amount of processing on the client side rather than relying solely on the server; can provide better performance, more features, and improved user experiences compared to thin client counterparts, which rely heavily on the server for processing and data storage |
| **Thick client — examples** | Web browsers, media players, chatting software, and video games; some are available to purchase or download for free through official website or third-party application stores; other custom applications created for a specific company can be delivered directly from the IT department that developed the software; deploying and maintaining can be more difficult than thin client applications since patches and updates must be done locally to the user's computer |
| **Thick client — characteristics** | Independent software; working without internet access; storing data locally; less secure; consuming more resources; more expensive |
| **Thick client — architectures** | **Two-tier**: application installed locally on the computer and communicates directly with the database; **Three-tier**: applications installed locally but to interact with databases they first communicate with an application server, usually using HTTP/HTTPS protocol; in this case, the application server and database might be located on the same network or over the internet; makes three-tier architecture more secure since attackers won't be able to communicate directly with the database |
| **Thick client — security concerns** | Since a large portion of thick client applications are downloaded from the internet, there is no sufficient way to ensure users will download the official application, raising security concerns; web-specific vulnerabilities like XSS, CSRF, and Clickjacking do not apply to thick client applications; however, thick client applications are considered less secure than web applications with many attacks being applicable |
| **Applicable attacks** | Improper Error Handling; Hardcoded sensitive data; DLL Hijacking; Buffer Overflow; SQL Injection; Insecure Storage; Session Management |

## LDAP

| **Category** | **Details** |
|---|---|
| **LDAP — overview** | Lightweight Directory Access Protocol is a protocol used to access and manage directory information; a directory is a hierarchical data store containing information about network resources such as users, groups, computers, printers, and other devices |
| **LDAP — functionality (benefits)** | **Efficient**: efficient and fast queries and connections to directory services thanks to lean query language and non-normalised data storage; **Global naming model**: supports multiple independent directories with a global naming model ensuring unique entries; **Extensible and flexible**: meets future and local requirements by allowing custom attributes and schemas; **Compatibility**: compatible with many software products and platforms — runs over TCP/IP and SSL directly, platform-independent, suitable for heterogeneous environments; **Authentication**: provides authentication mechanisms enabling users to sign on once and access multiple resources securely |
| **LDAP — issues** | **Compliance**: directory servers must be LDAP compliant for service to be deployed, which may limit vendor/product choice; **Complexity**: difficult to use and understand for many developers and administrators; **Encryption**: LDAP does not encrypt its traffic by default, exposing sensitive data to eavesdropping and tampering — LDAPS (LDAP over SSL) or StartTLS must be used; **Injection**: vulnerable to LDAP injection attacks where malicious users manipulate LDAP queries and gain unauthorised access — input validation and output encoding must be implemented |
| **LDAP — use cases** | **Authentication**: central authentication allowing single login credentials across multiple applications/systems (most common use case); **Authorisation**: manage permissions and access control for network resources such as folders or files on a network share (may require additional configuration or integration with protocols like Kerberos); **Directory Services**: search, retrieve, and modify data stored in a directory — helpful for managing large numbers of users and devices in a corporate network; based on the X.500 standard; **Synchronisation**: keep data consistent across multiple systems by replicating changes made in one directory to another |
| **LDAP — implementations** | Two popular implementations: **OpenLDAP**, open-source software widely used and supported; **Microsoft Active Directory**, Windows-based implementation seamlessly integrating with other Microsoft products and services |
| **LDAP vs AD** | Although related, they serve different purposes; LDAP is a protocol specifying the method of accessing and modifying directory services, whereas AD is a directory service that stores and manages user and computer data; LDAP can communicate with AD and other directory services but is not a directory service itself; AD offers extra functionalities such as policy administration, single sign-on, and integration with various Microsoft products |
| **LDAP vs AD — comparison** | **LDAP**: a protocol defining how clients and servers communicate to access and manipulate data stored in a directory service; open and cross-platform protocol usable with different types of directory servers/applications; flexible and extensible schema allowing custom attributes and object classes; supports multiple authentication mechanisms (simple bind, SASL, etc.). **AD**: a directory server using LDAP as one of its protocols to provide authentication, authorisation, and other services for Windows-based networks; proprietary software only working with Windows-based systems and requiring additional components such as DNS and Kerberos; predefined schema following and extending the X.500 standard with additional object classes/attributes specific to Windows; supports Kerberos as primary authentication mechanism but also NTLM and LDAP over SSL/TLS for backward compatibility |
| **LDAP — how it works** | Client-server architecture; a client sends an LDAP request to a server, which searches the directory service and returns a response; simpler and more efficient than X.500 on which it is based; clients send requests to servers using LDAP messages encoded in **ASN.1** (Abstract Syntax Notation One) and transmitted over **TCP/IP**; servers process requests and send back responses using the same format; supports various requests such as bind, unbind, search, compare, add, delete, modify, etc. |
| **LDAP requests — components** | **Session connection**: client connects to the server via an LDAP port (usually 389 or 636); **Request type**: client specifies the operation (bind, search, etc.); **Request parameters**: client provides additional information (distinguished name (DN) of the entry, scope and filter of the search query, attributes and values to be added or changed, etc.); **Request ID**: client assigns a unique identifier to match with the corresponding response |
| **LDAP responses — components** | **Response type**: server indicates the operation performed; **Result code**: server indicates whether the operation was successful and why; **Matched DN**: if applicable, returns the DN of the closest existing entry matching the request; **Referral**: returns a URL of another server that may have more information; **Response data**: any additional data related to the response (attributes and values of an entry searched or modified); after receiving and processing the response, the client disconnects from the LDAP port |
| **ldapsearch — overview** | Command-line utility used to search for information stored in a directory using the LDAP protocol; commonly used to query and retrieve data from an LDAP directory service: `ldapsearch -H ldap://ldap.example.com:389 -D "cn=admin,dc=example,dc=com" -w secret123 -b "ou=people,dc=example,dc=com" "(mail=john.doe@example.com)"` |
| **ldapsearch — breakdown** | Connect to the server `ldap.example.com` on port 389; bind (authenticate) as `cn=admin,dc=example,dc=com` with password `secret123`; search under the base DN `ou=people,dc=example,dc=com`; use the filter `(mail=john.doe@example.com)` to find entries with this email address |
| **ldapsearch — response example** | `dn: uid=jdoe,ou=people,dc=example,dc=com`, `objectClass: inetOrgPerson`, `objectClass: organizationalPerson`, `objectClass: person`, `objectClass: top`, `cn: John Doe`, `sn: Doe`, `uid: jdoe`, `mail: john.doe@example.com`, `result: 0 Success`; includes the entry's distinguished name (DN) matching the search criteria and its attributes and values |
| **LDAP Injection — overview** | Attack exploiting web applications that use LDAP for authentication or storing user information; attacker injects malicious code or characters into LDAP queries to alter the application's behaviour, bypass security measures, and access sensitive data stored in the LDAP directory |
| **LDAP Injection — test inputs** | `*`: asterisk can match any number of characters; `( )`: parentheses can group expressions; `\|`: vertical bar can perform logical OR; `&`: ampersand can perform logical AND; `(cn=*)`: input values that try to bypass authentication or authorisation checks by injecting conditions that always evaluate to true — e.g., `(cn=*)` or `(objectClass=*)` as input values for username or password fields; LDAP injection attacks are similar to SQL injection attacks but target the LDAP directory service instead of a database |
| **LDAP Injection — example** | Suppose an application uses the following LDAP query to authenticate users: `(&(objectClass=user)(sAMAccountName=$username)(userPassword=$password))`; `$username` and `$password` contain the user's login credentials; an attacker could inject the `*` character into the `$username` or `$password` field to modify the query and bypass authentication; if injecting `*` into the `$username` field, the LDAP query will match any user account with the password `dummy` — allows access using any password: `$username = "*";`, `$password = "dummy";`, `(&(objectClass=user)(sAMAccountName=$username)(userPassword=$password))`; alternatively, injecting `*` into the `$password` field — the LDAP query would match the `dummy` user account using any password containing the injected string — allows access with any username: `$username = "dummy";`, `$password = "*";`, `(&(objectClass=user)(sAMAccountName=$username)(userPassword=$password))` |
| **LDAP Injection — consequences** | Can lead to severe consequences such as unauthorised access to sensitive information, elevated privileges, and even full control over the affected application or server; can also considerably impact data integrity and availability as attackers may alter or remove data within the directory service, causing disruptions to applications and services dependent on that data |
| **LDAP Injection — mitigation** | Thoroughly validate and sanitize user input before incorporating it into LDAP queries; remove LDAP-specific special characters like `*`; employ parameterised queries to ensure user input is treated solely as data, not executable code |
| **Enumeration — Nmap** | Enumerating the target helps understand services and exposed ports; an nmap services scan identifies and analyzes services running on a target system or network; by probing open ports and assessing responses, nmap deduces which services are active and their respective versions; provides valuable information about the target's network infrastructure, potential vulnerabilities, and attack surface: `nmap -p- -sC -sV --open --min-rate=1000 10.129.204.229` → `PORT 80/tcp open http Apache httpd 2.4.41 ((Ubuntu))`, `http-server-header: Apache/2.4.41 (Ubuntu)`, `http-cookie-flags: /: PHPSESSID: httponly flag not set`, `http-title: Login`, `PORT 389/tcp open ldap OpenLDAP 2.2.X - 2.3.X`; nmap detects an HTTP server running on port 80 and an LDAP server running on port 389 |
| **Injection — scenario** | As OpenLDAP runs on the server, it is safe to assume the web application running on port 80 uses LDAP for authentication; attempting to log in using a wildcard character (`*`) in the username and password fields grants access to the system, effectively bypassing any authentication measures implemented; significant security issue as it allows anyone with knowledge of the vulnerability to gain unauthorised access to the system and potentially sensitive data |

## Web Mass Assignment Vulnerabilities

| **Category** | **Details** |
|---|---|
| **Mass assignment — overview** | Several frameworks offer handy mass-assignment features to lessen the workload for developers; programmers can directly insert a whole set of user-entered data from a form into an object or database; often used without a whitelist for protecting fields from user input; vulnerability could be used by an attacker to steal sensitive information or destroy data |
| **Mass assignment — definition** | Type of security vulnerability where attackers can modify the model attributes of an application through the parameters sent to the server; reversing the code, attackers can see these parameters and by assigning values to critical unprotected parameters during the HTTP request, they can edit the data of a database and change the intended functionality of an application |
| **Ruby on Rails — example** | Ruby on Rails is a web application framework vulnerable to this type of attack; assuming a User model with the following attributes: `class User < ActiveRecord::Base`<br>`  attr_accessible :username, :email`<br>`end`; the above model specifies only `username` and `email` attributes are allowed to be mass-assigned; however, attackers can modify other attributes by tampering with the parameters sent to the server; assume the server receives: `{ "user" => { "username" => "hacker", "email" => "hacker@example.com", "admin" => true } }`; although the User model does not explicitly state the `admin` attribute is accessible, the attacker can still change it because it is present in the arguments; bypassing any access controls, the attacker can send this data as part of a POST request to establish a user with admin privileges |
| **Exploiting — scenario** | Suppose we come across an **Asset Manager** web application; also suppose the application's source code has been provided; completing the registration step, get the message **Success!!**, and we can try to log in: login form with fields for username, password, 'Remember Me' checkbox, and 'Forgot Your Password?' link |
| **Exploiting — login message** | After logging in, get the message **Account is pending approval**; the administrator must approve our registration; reviewing the python code of the `/opt/asset-manager/app.py` file reveals: `for i,j,k in cur.execute('select * from users where username=? and password=?',(username,password)):`<br>`  if k:`<br>`    session['user']=i`<br>`    return redirect("/home",code=302)`<br>`  else:`<br>`    return render_template('login.html',value='Account is pending for approval')`; the application is checking if the value `k` is set; if yes, it allows the user to log in |
| **Exploiting — registration code** | In the code below, if we set the `confirmed` parameter during registration, it inserts `cond` as `True` and allows us to bypass the registration checking step: `try:`<br>`  if request.form['confirmed']:`<br>`    cond=True`<br>`except:`<br>`      cond=False`<br>`with sqlite3.connect("database.db") as con:`<br>`  cur = con.cursor()`<br>`  cur.execute('select * from users where username=?',(username,))`<br>`  if cur.fetchone():`<br>`    return render_template('index.html',value='User exists!!')`<br>`  else:`<br>`    cur.execute('insert into users values(?,?,?)',(username,password,cond))`<br>`    con.commit()`<br>`    return render_template('index.html',value='Success!!')` |
| **Exploiting — registration bypass** | Register another user and try setting the `confirmed` parameter to a random value; using Burp Suite, capture the HTTP POST request to the `/register` page and set the parameters `username=new&password=test&confirmed=test`: intercepted HTTP POST request to `/register` with username and password parameters |
| **Exploiting — login** | Try to log in using the `new:test` credentials; the mass assignment vulnerability is exploited successfully and we are now logged into the web app without waiting for the administrator to approve our registration request |
| **Prevention — overview** | To prevent this type of attack, explicitly assign the attributes for the allowed fields, or use whitelisting methods provided by the framework to check the attributes that can be mass-assigned |
| **Prevention — example** | The following example shows how to use strong parameters in the User controller: `class UsersController < ApplicationController`<br>`  def create`<br>`    @user = User.new(user_params)`<br>`    if @user.save`<br>`      redirect_to @user`<br>`    else`<br>`      render 'new'`<br>`    end`<br>`  end`<br>`  private`<br>`  def user_params`<br>`    params.require(:user).permit(:username, :email)`<br>`  end`<br>`end`; in the example above, the `user_params` method returns a new hash that includes only the `username` and `email` attributes, ignoring any more input the client may have sent; by doing this, we ensure only explicitly permitted attributes can be changed by mass assignment |
