# Linux Privilege Escalation
## Introduction to Linux Privilege Escalation

| **Category** | **Details** |
|---|---|
| **Context** | The root account on Linux provides full administrative access; during an assessment, may gain a low-privileged shell and need to perform privilege escalation to root; fully compromising the host allows capturing traffic and accessing sensitive files, which may be used to further access within the environment; if the Linux machine is domain joined, can gain the NTLM hash and begin enumerating and attacking Active Directory |
| **Enumeration — overview** | Enumeration is key to privilege escalation; several helper scripts (such as **LinEnum**) exist to assist, but important to understand what pieces of information to look for and to perform enumeration manually; check several key details when gaining initial shell access |
| **OS Version** | Knowing the distribution (Ubuntu, Debian, FreeBSD, Fedora, SUSE, Red Hat, CentOS, etc.) gives an idea of the types of tools available; identifies the operating system version, for which there may be public exploits |
| **Kernel Version** | As with OS version, there may be public exploits targeting a vulnerability in a specific kernel version; kernel exploits can cause system instability or a complete crash — be careful running against production systems and fully understand the exploit and possible ramifications |
| **Running Services** | Knowing what services are running, especially those running as root; a misconfigured or vulnerable service running as root can be an easy win for privilege escalation; flaws discovered in common services such as Nagios, Exim, Samba, ProFTPd, etc.; public exploit PoCs exist for many — e.g., **CVE-2016-9566**, a local privilege escalation flaw in Nagios Core < 4.2.4 |

| **SSH keys** | If you find an SSH key for your current user, this could be used to open an SSH session on the host (if SSH is exposed externally) and gain a stable and fully interactive session; SSH keys could be leveraged to access other systems within the network; at the minimum, check the ARP cache to see what other hosts are being accessed and cross-reference against any useable SSH private keys: `ls -l ~/.ssh` → `total 8`, `-rw------- 1 mrb3n mrb3n 1679 Aug 30 23:37 id_rsa`, `-rw-r--r-- 1 mrb3n mrb3n 393 Aug 30 23:37 id_rsa.pub` |
| **Bash History** | Important to check a user's bash history as they may be passing passwords as an argument on the command line, working with git repositories, setting up cron jobs, and more; reviewing what the user has been doing gives insight into the type of server and privilege escalation paths: `history` → `1 id`, `2 cd /home/cliff.moore`, `3 exit`, `4 touch backup.sh`, `5 tail /var/log/apache2/error.log`, `6 ssh ec2-user@dmz02.inlanefreight.local`, `7 history` |
| **Sudo Privileges** | Can the user run any commands either as another user or as root? | **Configuration Files** | Can hold a wealth of information; worth searching through all files ending in extensions such as `.conf` and `.config` for usernames, passwords, and other secrets |
| **Readable Shadow File** | If the shadow file is readable, you can gather password hashes for all users who have a password set; while this does not guarantee further access, these hashes can be subjected to an offline brute-force attack to recover the cleartext password |
| **Password Hashes in /etc/passwd** | Occasionally, password hashes appear directly in `/etc/passwd`; file is readable by all users, and as with hashes in the shadow file, these can be subjected to an offline password cracking attack; while not common, can sometimes be seen on embedded devices and routers: `cat /etc/passwd` → `root:x:0:0:root:/root:/bin/bash`, `daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin`, `bin:x:2:2:bin:/bin:/usr/sbin/nologin`, `sys:x:3:3:sys:/dev:/usr/sbin/nologin`, `sync:x:4:65534:sync:/bin:/bin/sync`, `games:x:5:60:games:/usr/games:/usr/sbin/nologin`, `man:x:6:12:man:/var/cache/man:/usr/sbin/nologin`, `lp:x:7:7:lp:/var/spool/lpd:/usr/sbin/nologin`, `mail:x:8:8:mail:/var/mail:/usr/sbin/nologin`, `news:x:9:9:news:/var/spool/news:/usr/sbin/nologin`, `<...SNIP...>`, `dnsmasq:x:109:65534:dnsmasq,,,:/var/lib/misc:/bin/false`, `sshd:x:110:65534::/var/run/sshd:/usr/sbin/nologin`, `mrb3n:x:1000:1000:mrb3n,,,:/home/mrb3n:/bin/bash`, `colord:x:111:118:colord colour management daemon,,,:/var/lib/colord:/bin/false`, `backupsvc:x:1001:1001::/home/backupsvc:`, `bob.jones:x:1002:1002::/home/bob.jones:`, `cliff.moore:x:1003:1003::/home/cliff.moore:`, `logger:x:1004:1004::/home/logger:`, `shared:x:1005:1005::/home/shared:`, `stacey.jenkins:x:1006:1006::/home/stacey.jenkins:`, `sysadm:$6$vdH7vuQIv6anIBWg$Ysk.UZzI7WxYUBYt8WRIWF0EzWlksOElDE0HLYinee38QI1A.0HW7WZCrUhZ9wwDz13bPpkTjNuRoUGYhwFE11:1007:1007::/home/sysadm:` |
| **Cron Jobs** | Similar to Windows scheduled tasks; often set up to perform maintenance and backup tasks; in conjunction with other misconfigurations such as relative paths or weak permissions, can be leveraged to escalate privileges when the scheduled cron job runs: `ls -la /etc/cron.daily/` → `total 60`, `drwxr-xr-x 2 root root 4096 Aug 30 23:49 .`, `drwxr-xr-x 93 root root 4096 Aug 30 23:47 ..`, `-rwxr-xr-x 1 root root 376 Mar 31 2016 apport`, `-rwxr-xr-x 1 root root 1474 Sep 26 2017 apt-compat`, `-rwx--x--x 1 root root 379 Aug 30 23:49 backup`, `-rwxr-xr-x 1 root root 355 May 22 2012 bsdmainutils`, `-rwxr-xr-x 1 root root 1597 Nov 27 2015 dpkg`, `-rwxr-xr-x 1 root root 372 May 6 2015 logrotate`, `-rwxr-xr-x 1 root root 1293 Nov 6 2015 man-db`, `-rwxr-xr-x 1 root root 539 Jul 16 2014 mdadm`, `-rwxr-xr-x 1 root root 435 Nov 18 2014 mlocate`, `-rwxr-xr-x 1 root root 249 Nov 12 2015 passwd`, `-rw-r--r-- 1 root root 102 Apr 5 2016 .placeholder`, `-rwxr-xr-x 1 root root 3449 Feb 26 2016 popularity-contest`, `-rwxr-xr-x 1 root root 214 May 24 2016 update-notifier-common` |

# Information gathering
## Environment Enumeration

| **Category** | **Details** |
|---|---|
| **Context** | Enumeration is key to privilege escalation; several helper scripts (such as **LinPEAS** and **LinEnum**) exist to assist, but important to understand what pieces of information to look for and to perform enumeration manually; check several key details when gaining initial shell access |
| **Key details — OS Version** | Knowing the distribution (Ubuntu, Debian, FreeBSD, Fedora, SUSE, Red Hat, CentOS, etc.) gives an idea of the types of tools available; identifies the operating system version, for which there may be public exploits |
| **Key details — Kernel Version** | As with OS version, there may be public exploits targeting a vulnerability in a specific kernel version; kernel exploits can cause system instability or a complete crash — be careful running against production systems and fully understand the exploit and possible ramifications |
| **Key details — Running Services** | Knowing what services are running, especially those running as root; a misconfigured or vulnerable service running as root can be an easy win; flaws discovered in common services such as Nagios, Exim, Samba, ProFTPd, etc.; public exploit PoCs exist for many — e.g., **CVE-2016-9566**, a local privilege escalation flaw in Nagios Core < 4.2.4 |
| **Gaining Situational Awareness — overview** | Suppose we just gained access by exploiting an unrestricted file upload during an External Penetration Test; after establishing a reverse shell (and ideally persistence), start by gathering basics about the system; first answer the fundamental question: what operating system are we dealing with? If we landed on CentOS or RHEL, enumeration would be slightly different than Debian-based (Ubuntu); if we land on FreeBSD, Solaris, HP-UX, or AIX, commands will likely be different; principles are the same; begin with an Ubuntu target to cover general tactics and techniques; with the basics and the stages of the Penetration Testing Process, it shouldn't matter what type of Linux system we land on because we'll have a thorough and repeatable process |
| **Gaining Situational Awareness — methodology** | Many cheat sheets exist to help with enumerating Linux systems and some bits of information will have two or more ways to obtain it; this module covers one methodology that can likely be used for the majority of Linux systems encountered in the wild; make sure you understand what commands are doing and how to tweak them or find the information a different way if a particular command doesn't work; challenge yourself to try things various ways to practice your methodology; anyone can re-type commands from a cheat sheet but a deep understanding of what you are looking for and how to obtain it will help us be successful in any environment |
| **Basic orientation commands** | `whoami` — what user are we running as; `id` — what groups does our user belong to?; `hostname` — what is the server named, can we gather anything from the naming convention?; `ifconfig` or `ip a` — what subnet did we land in, does the host have additional NICs in other subnets?; `sudo -l` — can our user run anything with sudo (as another user or root) without needing a password? This can sometimes be the easiest win — can do `sudo su` and drop right into a root shell; including screenshots of the above information can be helpful in a client report to provide evidence of a successful Remote Code Execution (RCE) and to clearly identify the affected system |
| **OS version — example** | `cat /etc/os-release` → `NAME="Ubuntu"`, `VERSION="20.04.4 LTS (Focal Fossa)"`, `ID=ubuntu`, `ID_LIKE=debian`, `PRETTY_NAME="Ubuntu 20.04.4 LTS"`, `VERSION_ID="20.04"`, `HOME_URL="https://www.ubuntu.com/"`, `SUPPORT_URL="https://help.ubuntu.com/"`, `BUG_REPORT_URL="https://bugs.launchpad.net/ubuntu/"`, `PRIVACY_POLICY_URL="https://www.ubuntu.com/legal/terms-and-policies/privacy-policy"`, `VERSION_CODENAME=focal`, `UBUNTU_CODENAME=focal`; target is running Ubuntu 20.04.4 LTS ("Focal Fossa"); important to see if we're dealing with something out-of-date or maintained; Ubuntu publishes its release cycle — "Focal Fossa" does not reach end of life until April 2030; can assume we will not encounter a well-known Kernel vulnerability because the customer has been keeping their internet-facing asset patched, but still look regardless |
| **PATH — check** | Check current user's PATH, where the Linux system looks every time a command is executed for any executables to match the name of what we type (e.g., `id` located at `/usr/bin/id`); if the PATH variable for a target user is misconfigured we may be able to leverage it to escalate privileges; note it down: `echo $PATH` → `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin` |
| **Environment variables — check** | Check all environment variables set for our current user; may get lucky and find something sensitive such as a password; note this down and move on: `env` → `SHELL=/bin/bash`, `PWD=/home/htb-student`, `LOGNAME=htb-student`, `XDG_SESSION_TYPE=tty`, `MOTD_SHOWN=pam`, `HOME=/home/htb-student`, `LANG=en_US.UTF-8`, `<SNIP>` |

## Capabilities

| **Category** | **Details** |
|---|---|
| **Capabilities — overview** | Linux capabilities are a security feature in the Linux operating system that allows specific privileges to be granted to processes, allowing them to perform specific actions that would otherwise be restricted; allows for more fine-grained control over which processes have access to certain privileges, making it more secure than the traditional Unix model of granting privileges to users and groups |

## Containers

| **Category** | **Details** |
|---|---|
| **Containers — overview** | Containers operate at the operating system level and virtual machines at the hardware level; containers share an operating system and isolate application processes from the rest of the system, while classic virtualization allows multiple operating systems to run simultaneously on a single system |
| **Isolation and virtualization** | Essential because they help manage resources and security aspects as efficiently as possible; e.g., facilitate monitoring to find errors in the system that often have nothing to do with newly developed applications; another example is the isolation of processes that usually require root privileges — such an application could be a web application or API that must be isolated from the host system to prevent escalation to databases |
| **Linux Containers (LXC) — overview** | Operating system-level virtualization technique that allows multiple Linux systems to run in isolation from each other on a single host by owning their own processes but sharing the host system kernel; very popular due to ease of use and has become an essential part of IT security |

# Hardening Considerations
## Linux Hardening

| **Category** | **Details** |
|---|---|
| **Context** | Proper Linux hardening can eliminate most, if not all, opportunities for local privilege escalation; the following steps should be taken, at a minimum, to reduce the risk of an attack being able to elevate to root-level access |
| **Updates and Patching** | Many quick and easy privilege escalation exploits exist for out-of-date Linux kernels and known vulnerable versions of built-in and third-party services; performing periodic updates will remove some of the most "low hanging fruit" that can be leveraged to escalate privileges; on Ubuntu, the package **unattended-upgrades** is installed by default from 18.04 onwards and can be manually installed on Ubuntu dating back to at least 10.04 (Lucid); Debian-based operating systems going back to before Jessie also have this package available; on Red Hat-based systems, the **yum-cron** package performs a similar task |
| **Configuration Management — measures** | Audit writable files and directories and any binaries set with the SUID bit; ensure any cron jobs and sudo privileges specify any binaries using the absolute path; do not store credentials in cleartext in world-readable files; clean up home directories and bash history; ensure low-privileged users cannot modify any custom libraries called by programs; remove any unnecessary packages and services that potentially increase the attack surface; consider implementing **SELinux**, which provides additional access controls on the system |
| **User Management** | Limit the number of user accounts and admin accounts on each system; ensure logon attempts (valid/invalid) are logged and monitored; enforce a strong password policy, prioritise longer memorized secrets or passphrases rather than relying on arbitrary periodic password changes; restrict users from reusing old passwords by using the `/etc/security/opasswd` file with the PAM module; check that users are not placed into groups that give them excessive rights not needed for their day-to-day tasks; limit sudo rights based on the principle of least privilege |
