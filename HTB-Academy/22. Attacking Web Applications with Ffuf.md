# Attacking Web Applications with Ffuf
## Introduction

| **Category** | **Details** |
|---|---|
| **Welcome** | Welcome to the **Attacking Web Applications with Ffuf** module |
| **Context** | Many tools and methods exist for directory and parameter fuzzing/brute-forcing; this module mainly focuses on the **ffuf** tool for web fuzzing, as it is one of the most common and reliable tools available for web fuzzing |
| **Topics covered** | Fuzzing for directories; fuzzing for files and extensions; identifying hidden vhosts; fuzzing for PHP parameters; fuzzing for parameter values |
| **How ffuf works** | Tools such as ffuf provide a handy automated way to fuzz the web application's individual components or a web page; e.g., use a list to send requests to the webserver if the page with the name from the list exists; a response code **200** means the page exists on the webserver and can be looked at manually |

## Web Fuzzing

| **Category** | **Details** |
|---|---|
| **Context** | Start by learning the basics of using ffuf to fuzz websites for directories; run the exercise, visit the URL, and see a website with no links or information leading to more pages — the only option is to "fuzz" the website |
| **Fuzzing — definition** | Testing technique that sends various types of user input to a certain interface to study how it would react |
| **Fuzzing — examples** | For SQL injection: send random special characters and see how the server reacts; for buffer overflow: send long strings and increment their length to see if/when the binary breaks |
| **Web fuzzing — approach** | Usually utilize pre-defined wordlists of commonly used terms for each type of test to see if the webserver would accept them; done because web servers do not usually provide a directory of all available links/domains (unless terribly configured), so we must check various links and see which return pages |
| **Web fuzzing — example** | Visiting `https://www.hackthebox.eu/doesnotexist` returns HTTP code **404 Page Not Found** (error page); visiting a page that exists like `/login` returns HTTP code **200 OK** (login page) |
| **Web fuzzing — automation** | Cannot do this manually — would take forever; tools send hundreds of requests per second, study the response HTTP code, and determine whether the page exists; quickly determine what pages exist and manually examine them to see their content |
| **Wordlists — purpose** | Have a wordlist containing commonly used words for web directories and pages (similar to a Password Dictionary Attack discussed later); will not reveal all pages (some are randomly named or use unique names), but in general returns the majority of pages — up to **90% success rate** on some websites |
| **Wordlists — source** | No need to reinvent the wheel; great efforts made to search the web and determine the most commonly used words for each type of fuzzing; most commonly used wordlists found under the GitHub **SecLists** repository, categorizing wordlists under various types of fuzzing, even including commonly used passwords (for Password Brute Forcing later) |
| **Wordlists — PwnBox location** | Entire SecLists repo available under `/opt/useful/SecLists` |
| **Wordlists — example** | For pages and directory fuzzing, commonly used wordlist called **directory-list-2.3** (available in various forms and sizes); locate with `locate directory-list-2.3-small.txt` → `/opt/useful/seclists/Discovery/Web-Content/directory-list-2.3-small.txt` |
| **Tip — copyright comments** | The wordlist contains copyright comments at the beginning, which can clutter results; use the `-ic` flag in ffuf to get rid of these lines |

# Basic Fuzzing
## Directory Fuzzing

| **Category** | **Details** |
|---|---|
| **Context** | Now that we understand the concept of Web Fuzzing and know our wordlist, we should be ready to start using ffuf to find website directories |
| **Ffuf — installation** | Pre-installed on the PwnBox instance; to use on your own machine, either `apt install ffuf -y` or download it from its GitHub Repo |
| **Ffuf — help** | Start by issuing `ffuf -h` to see how the tool can be used; help output is quite large, so only relevant options kept |
| **Ffuf — HTTP options (key)** | `-H` (Header "Name: Value", multiple accepted), `-X` (HTTP method, default GET), `-b` (Cookie data), `-d` (POST data), `-recursion` (scan recursively; only FUZZ keyword supported; URL must end in it), `-recursion-depth` (max recursion depth, default 0), `-u` (target URL) |
| **Ffuf — matcher options** | `-mc` (match HTTP status codes, or "all"; default 200,204,301,302,307,401,403), `-ms` (match HTTP response size) |
| **Ffuf — filter options** | `-fc` (filter HTTP status codes from response; comma-separated list of codes and ranges), `-fs` (filter HTTP response size; comma-separated list of sizes and ranges) |
| **Ffuf — input options** | `-w` (wordlist file path and optional keyword separated by colon, e.g., `/path/to/wordlist:KEYWORD`) |
| **Ffuf — output options** | `-o` (write output to file) |
| **Ffuf — example usage** | Fuzz file paths from `wordlist.txt`, match all responses but filter out those with content-size 42; colored, verbose output: `ffuf -w wordlist.txt -u https://example.org/FUZZ -mc all -fs 42 -c -v` |
| **Directory Fuzzing — main options** | `-w` for wordlists and `-u` for the URL; assign a wordlist to a keyword by adding `:FUZZ` after it |
| **Directory Fuzzing — assign keyword** | `ffuf -w /opt/useful/seclists/Discovery/Web-Content/directory-list-2.3-small.txt:FUZZ` |
| **Directory Fuzzing — place keyword** | Place the FUZZ keyword where the directory would be within the URL: `ffuf -w <SNIP> -u http://SERVER_IP:PORT/FUZZ` |
| **Directory Fuzzing — run** | `ffuf -w /opt/useful/seclists/Discovery/Web-Content/directory-list-2.3-small.txt:FUZZ -u http://SERVER_IP:PORT/FUZZ` |
| **Directory Fuzzing — output header** | Shows Method GET, URL `http://SERVER_IP:PORT/FUZZ`, Wordlist `FUZZ: /opt/useful/.../directory-list-2.3-small.txt`, Follow redirects false, Calibration false, Timeout 10, Threads 40, Matcher Response status 200,204,301,302,307,401,403 |

| **Speed note** | Speed varies depending on internet speed and ping; can make it faster with `-t 200` (increase threads to 200), but not recommended — especially on a remote site — as it may disrupt it, cause a Denial of Service, or bring down your internet connection in severe cases |
| **Verify hit** | Visit one of the hits to verify it exists (`http://SERVER_IP:PORT/blog`); get an empty page indicating the directory does not have a dedicated page but shows we have access to it (no 404 Not Found or 403 Access Denied) |

| **Extension Fuzzing — common way** | Find the server type through HTTP response headers and guess the extension (e.g., Apache → `.php`, IIS → `.asp`/`.aspx`); this method is not very practical, so utilize ffuf to fuzz the extension |

## Recursive Fuzzing

| **Category** | **Details** |
|---|---|
| **Context** | So far fuzzing for directories, going under them, and then fuzzing for files; with dozens of directories (each with subdirectories and files), this would take a very long time; automate this with **recursive fuzzing** |
| **Recursive Flags — behavior** | When scanning recursively, it automatically starts another scan under any newly identified directories on their pages until it has fuzzed the main website and all its subdirectories |
| **Recursive Flags — caution** | Some websites have a big tree of sub-directories (e.g., `/login/user/content/uploads/...`), expanding the scanning tree and taking a very long time; always advised to specify a **depth** to the recursive scan so it does not scan directories deeper than that depth; once first directories are fuzzed, pick the most interesting directories and run another scan to direct the scan better |
| **Recursive Flags — ffuf flags** | Enable recursive scanning with `-recursion`; specify depth with `-recursion-depth`; `-recursion-depth 1` only fuzzes main directories and their direct sub-directories (sub-sub-directories like `/login/user` are not fuzzed for pages); specify extension with `-e .php` |
| **Recursive Flags — note** | Can still use `.php` as the page extension, as these extensions are usually site-wide |
| **Recursive Flags — verbose** | Add the `-v` flag to output full URLs; otherwise difficult to tell which `.php` file lies under which directory |
| **Recursive Scanning — run** | Repeat the first command, add recursion flags, specify `.php` as extension: `ffuf -w /opt/useful/seclists/Discovery/Web-Content/directory-list-2.3-small.txt:FUZZ -u http://SERVER_IP:PORT/FUZZ -recursion -recursion-depth 1 -e .php -v` |
| **Recursive Scanning — output header** | Method GET, URL `http://SERVER_IP:PORT/FUZZ`, Wordlist `FUZZ: /opt/useful/.../directory-list-2.3-small.txt`, Extensions `.php`, Follow redirects false, Calibration false, Timeout 10, Threads 40, Matcher Response status 200,204,301,302,307,401,403 |
| **Recursive Scanning — results (examples)** | `[Status: 200, Size: 986, Words: 423, Lines: 56] \| URL \| http://SERVER_IP:PORT/ * FUZZ: `; `[INFO] Adding a new job to the queue: http://SERVER_IP:PORT/forum/FUZZ`; `[Status: 200, Size: 986, Words: 423, Lines: 56] \| URL \| http://SERVER_IP:PORT/index.php * FUZZ: index.php`; `[Status: 301, Size: 326, Words: 20, Lines: 10] \| URL \| http://SERVER_IP:PORT/blog --> http://SERVER_IP:PORT/blog/ * FUZZ: blog`; `[Status: 200, Size: 0, Words: 1, Lines: 1] \| URL \| http://SERVER_IP:PORT/blog/index.php * FUZZ: index.php`; `[Status: 200, Size: 0, Words: 1, Lines: 1] \| URL \| http://SERVER_IP:PORT/blog/ * FUZZ: ` |
| **Recursive Scanning — takeaway** | Scan took much longer, sent almost six times the number of requests, and the wordlist doubled in size (once with `.php` and once without); still got a large number of results, including all previously identified results, all with a single line of command |

# Domain Fuzzing
## DNS Records

| **Category** | **Details** |
|---|---|
| **Context** | Once we accessed the page under `/blog`, we got a message saying "Admin panel moved to academy.htb"; visiting the website in the browser gives "can't connect to the server at www.academy.htb" |
| **Why the error** | The exercises are not public websites accessible by anyone but local websites within HTB; browsers only understand how to go to IPs — if provided with a URL, they try to map the URL to an IP by looking into the local `/etc/hosts` file and the public **DNS (Domain Name System)**; if the URL is not in either, it cannot connect |
| **How browsers resolve URLs** | Visiting the IP directly works (browser goes to that IP directly); telling it to go to `academy.htb` → looks into local `/etc/hosts` and finds no mention → asks the public DNS (e.g., Google's DNS `8.8.8.8`) and finds no mention (not a public website) → fails to connect |
| **Fix — add to /etc/hosts** | To connect to `academy.htb`, add it to the `/etc/hosts` file: `sudo sh -c 'echo "SERVER_IP  academy.htb" >> /etc/hosts'` |
| **Verify access** | Visit the website (don't forget to add the PORT in the URL) → reach the website (`http://academy.htb:PORT` → "Welcome to HTB Academy" text) |
| **Observation** | Get the same website as when visiting the IP directly — `academy.htb` is the same domain tested so far; verify by visiting `/blog/index.php` and see the page is accessible |
| **Next step** | Tests on this IP did not find anything about admin or panels (even with a full recursive scan); start looking for sub-domains under `*.academy.htb` — attempted in the next section |

## Sub-domain Fuzzing

| **Category** | **Details** |
|---|---|
| **Context** | Learn how to use ffuf to identify sub-domains (i.e., `*.website.com`) for any website |
| **Sub-domains — definition** | Any website underlying another domain; e.g., `https://photos.google.com` is the photos sub-domain of `google.com` |
| **Sub-domain fuzzing — approach** | Checking different websites to see if they exist by checking if they have a **public DNS record** that would redirect to a working server IP |
| **Prerequisites** | A wordlist and a target |
| **Wordlist — source** | In the SecLists repo, a specific section for sub-domain wordlists with common words usually used for sub-domains: `/opt/useful/seclists/Discovery/DNS/`; in this case use the shorter wordlist `subdomains-top1million-5000.txt`; if extending the scan, pick a larger list |
| **Target — example** | Use `inlanefreight.com` as the target and run the scan on it |
| **Run — inlanefreight.com** | `ffuf -w /opt/useful/seclists/Discovery/DNS/subdomains-top1million-5000.txt:FUZZ -u https://FUZZ.inlanefreight.com/` |

| **Results — inlanefreight.com** | `support` (301, Size 0, Words 1, Lines 1, Duration 381ms); `ns3` (301, 385ms); `blog` (301, 402ms); `my` (301, 180ms); `www` (200, Size 22266, Words 2903, Lines 316, Duration 589ms); plus more hits (SNIP) |
| **Run — academy.htb** | `ffuf -w /opt/useful/seclists/Discovery/DNS/subdomains-top1million-5000.txt:FUZZ -u http://FUZZ.academy.htb/` |

## Vhost Fuzzing

| **Category** | **Details** |
|---|---|
| **Context** | In the previous section, we fuzzed public sub-domains using public DNS records; for sub-domains without a public DNS record (or sub-domains under non-public websites), we could not use the same method; learn how to do that with **Vhost Fuzzing** |
| **Vhosts vs. Sub-domains** | Key difference: a VHost is basically a "sub-domain" served on the same server and has the same IP — a single IP could be serving two or more different websites |
| **Vhosts — DNS records** | VHosts may or may not have public DNS records |
| **Why sub-domain fuzzing falls short** | Many websites have sub-domains that are not public and not published in public DNS records; visiting them in a browser would fail to connect (public DNS would not know their IP); sub-domain fuzzing only identifies public sub-domains, not non-public ones |
| **Vhost Fuzzing — approach** | Utilize VHosts Fuzzing on an IP we already have; run a scan and test on the same IP to identify both public and non-public sub-domains and VHosts |
| **Vhost Fuzzing — method** | Scan for VHosts without manually adding the entire wordlist to `/etc/hosts` by fuzzing HTTP headers, specifically the `Host:` header; use the `-H` flag to specify a header and use the FUZZ keyword within it |
| **Vhost Fuzzing — run** | `ffuf -w /opt/useful/seclists/Discovery/DNS/subdomains-top1million-5000.txt:FUZZ -u http://academy.htb:PORT/ -H 'Host: FUZZ.academy.htb'` |
| **Output header** | Method GET, URL `http://academy.htb:PORT/`, Wordlist `FUZZ: /opt/useful/.../subdomains-top1million-5000.txt`, Header `Host: FUZZ`, Follow redirects false, Calibration false, Timeout 10, Threads 40, Matcher Response status 200,204,301,302,307,401,403 |
| **Results (examples)** | `mail2` (200, Size 900, Words 423, Lines 56), `dns2` (200, 900), `ns3` (200, 900), `dns1` (200, 900), `lists` (200, 900), `webmail` (200, 900), `static` (200, 900), `web` (200, 900), `www1` (200, 900); plus more (SNIP) |
| **Interpretation** | All words in the wordlist return 200 OK — expected, as we are simply changing the header while visiting `http://academy.htb:PORT/`, so we always get 200 OK; however, if the VHost does exist and we send a correct one in the header, we should get a **different response size**, as we would be getting the page from that VHost (likely a different page) |

## Filtering Results

| **Filtering — options** | Ffuf provides the option to match or filter out a specific HTTP code, response size, or amount of words; see with `ffuf -h` |

# Parameter Fuzzing
## Parameter Fuzzing - GET

| **Category** | **Details** |
|---|---|
| **Context** | Running a recursive ffuf scan on `admin.academy.htb` should find `http://admin.academy.htb:PORT/admin/admin.php`; accessing this page shows "You don't have access to read the flag" |
| **Why** | Indicates something identifies users to verify whether they have access to read the flag; did not log in, nor have any cookie verifiable at the backend; perhaps there is a key that can be passed to the page to read the flag; such keys are usually passed as a parameter using either a GET or POST HTTP request |
| **Tip — unpublished parameters** | Fuzzing parameters may expose unpublished parameters that are publicly accessible; such parameters tend to be less tested and less secured — important to test them for the web vulnerabilities discussed in other modules |
| **GET Request Fuzzing — approach** | Use ffuf to enumerate parameters; GET requests are usually passed right after the URL with a `?` symbol, like `http://admin.academy.htb:PORT/admin/admin.php?param1=key`; replace `param1` with FUZZ and rerun the scan |
| **GET Request Fuzzing — wordlist** | SecLists has `/opt/useful/seclists/Discovery/Web-Content/burp-parameter-names.txt` |
| **GET Request Fuzzing — run** | `ffuf -w /opt/useful/seclists/Discovery/Web-Content/burp-parameter-names.txt:FUZZ -u http://admin.academy.htb:PORT/admin/admin.php?FUZZ=key -fs xxx` |
| **Output header** | Method GET, URL `http://admin.academy.htb:PORT/admin/admin.php?FUZZ=key`, Wordlist `FUZZ: /opt/useful/.../burp-parameter-names.txt`, Follow redirects false, Calibration false, Timeout 10, Threads 40, Matcher Response status 200,204,301,302,307,401,403, Filter Response size: xxx |

## Parameter Fuzzing - POST

| **Category** | **Details** |
|---|---|
| **Main difference — POST vs GET** | POST requests are not passed with the URL and cannot simply be appended after a `?` symbol; POST requests are passed in the **data field** within the HTTP request (see the Web Requests module for more on HTTP requests) |
| **Fuzzing the data field** | Use the `-d` flag (seen in `ffuf -h` output); also add `-X POST` to send POST requests |
| **Tip — PHP content-type** | In PHP, "POST" data "content-type" can only accept `application/x-www-form-urlencoded`; set that in ffuf with `-H 'Content-Type: application/x-www-form-urlencoded'` |
| **Run** | Repeat what was done earlier, but place the FUZZ keyword after the `-d` flag: `ffuf -w /opt/useful/seclists/Discovery/Web-Content/burp-parameter-names.txt:FUZZ -u http://admin.academy.htb:PORT/admin/admin.php -X POST -d 'FUZZ=key' -H 'Content-Type: application/x-www-form-urlencoded' -fs xxx` |

## Value Fuzzing

| **Category** | **Details** |
|---|---|
| **Context** | After fuzzing a working parameter, now have to fuzz the correct value that would return the flag content; fuzzing for parameter values is fairly similar to fuzzing for parameters once the wordlist is developed |
| **Custom Wordlist — why** | For parameter values, may not always find a pre-made wordlist that works, as each parameter expects a certain type of value |
| **Custom Wordlist — examples** | For usernames, can find a pre-made wordlist or create one based on potential users; look for various wordlists under the SecLists directory and try to find one containing values matching the parameter; for custom parameters, may have to develop your own wordlist |
| **Custom Wordlist — id parameter** | Can guess the `id` parameter accepts a number input of some sort; IDs can be in a custom format or sequential (e.g., 1-1000, 1-1000000); start with a wordlist containing all numbers from 1-1000 |
| **Custom Wordlist — creation** | Many ways: manually typing IDs in a file, or scripting with Bash or Python; simplest: `for i in $(seq 1 1000); do echo $i >> ids.txt; done` |
| **Custom Wordlist — verify** | `cat ids.txt` → `1`, `2`, `3`, `4`, `5`, `6`, ... (SNIP) |
| **Value Fuzzing — run** | Command similar to the POST command used to fuzz for parameters, but place the FUZZ keyword where the parameter value would be, using the `ids.txt` wordlist: `ffuf -w ids.txt:FUZZ -u http://admin.academy.htb:PORT/admin/admin.php -X POST -d 'id=FUZZ' -H 'Content-Type: application/x-www-form-urlencoded' -fs xxx` |
