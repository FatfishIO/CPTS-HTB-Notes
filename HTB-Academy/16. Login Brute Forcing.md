# Login Brute Forcing
## Introduction

| **Category** | **Details** |
|---|---|
| **What is Brute Forcing?** | In cybersecurity, a trial-and-error method used to crack passwords, login credentials, or encryption keys; involves systematically trying every possible combination of characters until the correct one is found; likened to a thief trying every key on a giant keyring until they find the one that unlocks the treasure chest |
| **Success factors — complexity** | Longer passwords with a mix of uppercase/lowercase letters, numbers, and symbols are exponentially more complex to crack |
| **Success factors — computational power** | Modern computers and specialized hardware can try billions of combinations per second, significantly reducing the time needed for a successful attack |
| **Success factors — security measures** | Account lockouts, CAPTCHAs, and other defenses can slow down or even thwart brute-force attempts |
| **How it works — steps** | **Start**: attacker initiates the process, often with specialized software; **Generate Possible Combination**: software generates a potential password/key based on predefined parameters (character sets, length); **Apply Combination**: attempted against the target system (login form, encrypted file); **Check if Successful**: system evaluates — if it matches the stored password/key, access is granted, otherwise continue; **Access Granted**: attacker gains unauthorized access; **End**: process repeats until correct combination is found or attacker gives up |
| **Types — Simple Brute Force** | Systematically tries all possible combinations of characters within a defined character set and length range; e.g., all combinations of lowercase letters a-z for passwords of length 4-6; best when no prior information about the password and computational resources are abundant |
| **Types — Dictionary Attack** | Uses a pre-compiled list of common words, phrases, and passwords; e.g., passwords from `rockyou.txt` against a login form; best when the target likely uses a weak/easily guessable password based on common patterns |
| **Types — Hybrid Attack** | Combines simple brute force and dictionary attacks, often appending/prepending characters to dictionary words; e.g., adding numbers or special characters to the end of dictionary words; best when the target might use a slightly modified version of a common password |
| **Types — Credential Stuffing** | Leverages leaked credentials from one service to attempt access to other services, assuming users reuse passwords; e.g., using a list of usernames/passwords leaked from a data breach; best when a large set of leaked credentials is available and the target is suspected of reusing passwords |
| **Types — Password Spraying** | Attempts a small set of commonly used passwords against a large number of usernames; e.g., trying `password123` or `qwerty` against all usernames in an organization; best when account lockout policies are in place and the attacker aims to avoid detection by spreading attempts |
| **Types — Rainbow Table Attack** | Uses pre-computed tables of password hashes to reverse hashes and recover plaintext passwords quickly; e.g., pre-computing hashes for all possible passwords of a certain length/character set, then comparing captured hashes against the table; best when a large number of password hashes need cracking and storage space is available |
| **Types — Reverse Brute Force** | Targets a single password against multiple usernames, often used with credential stuffing; e.g., using a leaked password from one service to try logging into multiple accounts with different usernames; best when strong suspicion exists that a particular password is reused across multiple accounts |
| **Types — Distributed Brute Force** | Distributes the workload across multiple computers/devices to accelerate the process; e.g., using a cluster of computers to significantly increase combinations tried per second; best when the target password/key is highly complex and a single machine lacks the computational power |
| **Role in Penetration Testing** | Ethical hacking that simulates real-world attacks to identify and address vulnerabilities before malicious actors exploit them; brute forcing is crucial when assessing the resilience of password-based authentication mechanisms |
| **When brute forcing is employed — exhausted avenues** | Initial attempts to gain access (exploiting known vulnerabilities or social engineering) may prove unsuccessful; brute forcing is a viable alternative to overcome password barriers |
| **When brute forcing is employed — weak policies** | If the target system employs lax password policies, users are more likely to have weak/easily guessable passwords; brute forcing can effectively expose these vulnerabilities |
| **When brute forcing is employed — targeted accounts** | May focus on compromising specific user accounts, such as those with elevated privileges; brute forcing can be tailored to target these accounts directly |

## Password Security Fundamentals

| **Category** | **Details** |
|---|---|
| **The Importance of Strong Passwords** | Passwords are the first line of defense protecting sensitive information and systems; a strong password is a formidable barrier, making it significantly harder for attackers to gain unauthorized access through brute forcing or other techniques; the longer and more complex a password, the more combinations an attacker has to try, exponentially increasing the time and resources required |
| **NIST guidelines — Length** | The longer the better; aim for a minimum of **12 characters**, but longer is always preferable; each additional character dramatically increases the number of possible combinations — a 6-character password using only lowercase letters has 26^6 (~300 million) combinations, while an 8-character password has 26^8 (~200 billion) combinations; exponential increase makes longer passwords significantly more resistant to brute-force attacks |
| **NIST guidelines — Complexity** | Traditional advice emphasized mixing uppercase/lowercase letters, numbers, and symbols; recent NIST guidelines shifted focus toward password length and the use of passphrases; complexity remains an important consideration, especially for brute-force attacks — including different character types expands the pool of potential characters per position (only lowercase = 26 possibilities per character; both upper and lowercase = 52 possibilities per character); increased complexity makes it more challenging for attackers to predict or guess passwords |
| **NIST guidelines — Uniqueness** | Don't reuse passwords across different accounts; each account should have its own unique and strong password; if one account is compromised, all other accounts using the same password are also at risk; unique passwords compartmentalize the potential damage of a breach |
| **NIST guidelines — Randomness** | Avoid dictionary words, personal information, or common phrases; the more random the password, the harder it is to crack; attackers often use wordlists containing common passwords and personal information to speed up brute-force attempts; creating a random password minimizes the chances of being included in such wordlists |
| **Common weaknesses — Short Passwords** | Fewer than eight characters are particularly vulnerable, as the number of possible combinations is relatively small |
| **Common weaknesses — Common Words and Phrases** | Dictionary words, names, or common phrases make them susceptible to dictionary attacks (pre-defined list of common passwords) |
| **Common weaknesses — Personal Information** | Birthdates, pet names, or addresses make them easier to guess, especially if publicly available on social media |
| **Common weaknesses — Reusing Passwords** | Using the same password across multiple accounts is risky; if one account is compromised, all others using the same password are at risk |
| **Common weaknesses — Predictable Patterns** | Patterns like `qwerty`, `123456`, or simple substitutions like `p@ssw0rd` are well-known to attackers and easy to guess |
| **Password Policies — typical requirements** | Minimum Length (number of characters); Complexity (types of characters — uppercase, lowercase, numbers, symbols); Password Expiration (frequency of changes); Password History (number of previous passwords that cannot be reused) |
| **Password Policies — balance** | Can help improve password security but can also lead to user frustration and poor practices (writing passwords down, using slight variations of the same password); balance security and usability when designing policies |
| **Default Credentials — danger** | Pre-set passwords come with various devices, software, or online services; often simple and easily guessable, making them a prime target; significantly increase the success rate of brute-force attacks; attackers leverage lists of common default passwords, reducing the search space and accelerating cracking; may not even need a brute-force attack — a few common defaults can gain access |
| **Default Credentials — low-hanging fruit** | Prevalence makes them an easy entry point into systems and networks, potentially leading to data breaches, unauthorized access, and other malicious activities |
| **Default credentials — examples** | Linksys Router `admin/admin`; D-Link Router `admin/admin`; Netgear Router `admin/password`; TP-Link Router `admin/admin`; Cisco Router `cisco/cisco`; Asus Router `admin/admin`; Belkin Router `admin/password`; Zyxel Router `admin/1234`; Samsung SmartCam `admin/4321`; Hikvision DVR `admin/12345`; Axis IP Camera `root/pass`; Ubiquiti UniFi AP `ubnt/ubnt`; Canon Printer `admin/admin`; Honeywell Thermostat `admin/1234`; Panasonic DVR `admin/12345` |
| **Default usernames** | Another major concern — manufacturers ship devices with pre-set usernames like `admin`, `root`, or `user`; widely known and published in documentation or online; SecLists maintains a list at `top-usernames-shortlist.txt`; give attackers a predictable starting point — knowing the username is half the battle; even when default passwords are changed, retaining the default username still leaves systems vulnerable, drastically narrowing the attack surface |
| **Brute-forcing and Password Security** | A weak password is like a flimsy lock easily picked open; a strong password acts as a fortified vault demanding significantly more time and resources to breach |
| **Pentester understanding — Evaluating System Vulnerability** | Password policies (or their absence) and the likelihood of users employing weak passwords directly inform the potential success of a brute-force attack |
| **Pentester understanding — Strategic Tool Selection** | Complexity of passwords dictates the tools and methodologies deployed; a simple dictionary attack might suffice for weak passwords, while a sophisticated hybrid approach may be required for stronger ones |
| **Pentester understanding — Resource Allocation** | Estimated time and computational power needed is intrinsically linked to password complexity; essential for effective planning and resource management |
| **Pentester understanding — Exploiting Weak Points** | Default passwords are often a system's Achilles' heel; identifying and leveraging easily guessable credentials can provide a swift entry point into the target network |
| **Takeaway** | Deep understanding of password security is a roadmap for navigating brute-force attacks — unveils potential weak points, informs strategic choices, predicts effort required; also underscores the critical importance of robust password practices, highlighting each user's pivotal role in safeguarding sensitive information |

# Brute Force Attacks
## Brute Force Attacks

| **Category** | **Details** |
|---|---|
| **Mathematics — formula** | `Possible Combinations = Character Set Size^Password Length` |
| **Mathematics — example** | A 6-character password using only lowercase letters (character set size 26) has 26^6 (~300 million) possible combinations; an 8-character password with the same character set has 26^8 (~200 billion) combinations; adding uppercase letters, numbers, and symbols further expands the search space exponentially |
| **Mathematics — takeaway** | Exponential growth highlights the importance of password length and complexity; even a small increase in length or inclusion of additional character types dramatically increases the time and resources required for a successful brute-force attack |
| **Scenarios — Short and Simple** | Length 6, lowercase letters (a-z) → 26^6 = 308,915,776 combinations |
| **Scenarios — Longer but Still Simple** | Length 8, lowercase letters (a-z) → 26^8 = 208,827,064,576 combinations |
| **Scenarios — Adding Complexity** | Length 8, lowercase and uppercase letters (a-z, A-Z) → 52^8 = 53,459,728,531,456 combinations |
| **Scenarios — Maximum Complexity** | Length 12, lowercase/uppercase letters, numbers, and symbols → 94^12 = 475,920,493,781,698,549,504 combinations |
| **Scenarios — conclusion** | Even a slight increase in password length or inclusion of additional character types dramatically expands the search space, significantly increasing the number of possible combinations an attacker must try, making brute-forcing increasingly challenging and time-consuming |
| **Computational power** | Cracking time depends not only on search space size but also on the attacker's available computational power; more powerful hardware (GPUs, CPUs, cloud resources) means more password guesses per second; a complex password may take years with a single machine, but a sophisticated attacker using a distributed network of high-performance computing resources could reduce that time drastically |
| **Chart — exponential relationship** | Password complexity vs. cracking time is exponential; as password length increases and character set expands, total possible combinations grow exponentially, significantly increasing cracking time even with powerful computing resources |
| **Basic Computer (1 million passwords/second)** | Adequate for cracking simple passwords quickly but impractically slow for complex passwords; e.g., cracking an 8-character password using letters and digits would take approximately **6.92 years** |
| **Supercomputer (1 trillion passwords/second)** | Drastically reduces cracking times for simpler passwords; however, even with this immense power, cracking highly complex passwords can take an impractical amount of time; e.g., a 12-character password with all ASCII characters would still take about **15,000 years** to crack |
| **Cracking the PIN — setup** | Start the target system via the question section; the instance application generates a random 4-digit PIN and exposes an endpoint (`/pin`) that accepts a PIN as a query parameter; if the provided PIN matches, the application responds with a success message and a flag; otherwise, it returns an error message |
| **Cracking the PIN — script** | `import requests`<br>`ip = "127.0.0.1"  # Change this to your instance IP address`<br>`port = 1234       # Change this to your instance port number`<br>`for pin in range(10000):`<br>`    formatted_pin = f"{pin:04d}"`<br>`    print(f"Attempted PIN: {formatted_pin}")`<br>`    response = requests.get(f"http://{ip}:{port}/pin?pin={formatted_pin}")`<br>`    if response.ok and 'flag' in response.json():`<br>`        print(f"Correct PIN found: {formatted_pin}")`<br>`        print(f"Flag: {response.json()['flag']}")`<br>`        break` |

## Dictionary Attacks

| **Category** | **Details** |
|---|---|
| **The Power of Words — overview** | Brute-force can be time-consuming and resource-intensive, especially with complex passwords; dictionary attacks exploit the human tendency to prioritize memorable passwords over secure ones; many individuals continue to opt for passwords based on readily available information (dictionary words, common phrases, names, easily guessable patterns), making them vulnerable |
| **The Power of Words — wordlist quality** | Success hinges on the quality and specificity of the wordlist; a well-crafted wordlist tailored to the target audience/system significantly increases the probability of a successful breach; e.g., for gamers, a wordlist enriched with gaming-related terminology is more effective than a generic dictionary; the more closely the wordlist reflects the target's likely password choices, the higher the chances of success |
| **The Power of Words — core concept** | Rooted in understanding human psychology and common password practices; leveraging this insight allows attackers to efficiently crack passwords that might otherwise require an impractically lengthy brute-force attack; the power of words resides in their ability to exploit human predictability and compromise otherwise robust security measures |
| **Brute Force vs. Dictionary — Brute Force** | Pure brute-force systematically tests every possible combination of characters within a predetermined set and length; guarantees eventual success given enough time but can be extremely time-consuming, particularly against longer or complex passwords |
| **Brute Force vs. Dictionary — Dictionary Attack** | Employs a pre-compiled list of words and phrases, dramatically reducing the search space; targeted methodology results in a far more efficient and rapid attack, especially when the target password is suspected to be a common word or phrase |
| **Comparison — Efficiency** | Dictionary: considerably faster and more resource-efficient; Brute Force: can be extremely time-consuming and resource-intensive; dictionary attacks leverage a pre-defined list, significantly narrowing the search space |
| **Comparison — Targeting** | Dictionary: highly adaptable, can be tailored to specific targets or systems; Brute Force: no inherent targeting capability; wordlists can incorporate information relevant to the target (company name, employee names), increasing success rate |
| **Comparison — Effectiveness** | Dictionary: exceptionally effective against weak or commonly used passwords; Brute Force: effective against all passwords given sufficient time and resources; if the target password is within the dictionary, it will be swiftly discovered; brute force, while universally applicable, can be impractical for complex passwords |
| **Comparison — Limitations** | Dictionary: ineffective against complex, randomly generated passwords; Brute Force: often impractical for lengthy or highly complex passwords; a truly random password is unlikely to appear in any dictionary; the astronomical number of possible combinations for lengthy passwords can make brute-force attacks infeasible |
| **Hypothetical scenario** | Attacker targets a company's employee login portal; constructs a specialized wordlist incorporating: commonly used weak passwords (e.g., `password123`, `qwerty`), the company name and variations, names of employees or departments, industry-specific jargon; deploying this targeted wordlist significantly elevates the likelihood of successfully cracking employee passwords compared to a purely random brute-force endeavor |
| **Wordlist sources — Publicly Available Lists** | The internet hosts a plethora of freely accessible wordlists — collections of commonly used passwords, leaked credentials from data breaches, and other valuable data; repositories like **SecLists** offer various wordlists catering to various attack scenarios |
| **Wordlist sources — Custom-Built Lists** | Penetration testers can craft their own wordlists by leveraging information gleaned during reconnaissance — target's interests, hobbies, personal information, or other data for password creation |
| **Wordlist sources — Specialized Lists** | Wordlists refined to target specific industries, applications, or individual companies; increase likelihood of success by focusing on passwords more likely to be used within a particular context |
| **Wordlist sources — Pre-existing Lists** | Certain tools and frameworks come pre-packaged with commonly used wordlists; e.g., penetration testing distributions like ParrotSec often include `rockyou.txt`, a massive collection of leaked passwords |
| **Useful wordlists — rockyou.txt** | Popular password wordlist containing millions of passwords leaked from the RockYou breach; commonly used for password brute force attacks; source: RockYou breach dataset |
| **Useful wordlists — top-usernames-shortlist.txt** | Concise list of the most common usernames; suitable for quick brute force username attempts; source: SecLists |
| **Useful wordlists — xato-net-10-million-usernames.txt** | More extensive list of 10 million usernames; used for thorough username brute forcing; source: SecLists |
| **Useful wordlists — 2023-200_most_used_passwords.txt** | List of the 200 most commonly used passwords as of 2023; effective for targeting commonly reused passwords; source: SecLists |
| **Useful wordlists — Default-Credentials/default-passwords.txt** | List of default usernames and passwords commonly used in routers, software, and other devices; ideal for trying default credentials; source: SecLists |
| **Dictionary solver — script** | `import requests`<br>`ip = "127.0.0.1"  # Change this to your instance IP address`<br>`port = 1234       # Change this to your instance port number`<br>`passwords = requests.get("https://raw.githubusercontent.com/danielmiessler/SecLists/refs/heads/master/Passwords/Common-Credentials/500-worst-passwords.txt").text.splitlines()`<br>`for password in passwords:`<br>`    print(f"Attempted password: {password}")`<br>`    response = requests.post(f"http://{ip}:{port}/dictionary", data={'password': password})`<br>`    if response.ok and 'flag' in response.json():`<br>`        print(f"Correct password found: {password}")`<br>`        print(f"Flag: {response.json()['flag']}")`<br>`        break` |
| **Dictionary solver — steps** | 1) **Downloads the Wordlist**: fetches a wordlist of 500 commonly used (weak) passwords from SecLists using the requests library; 2) **Iterates and Submits Passwords**: iterates through each password, sending a POST request to the Flask application's `/dictionary` endpoint with the password in the form data; 3) **Analyzes Responses**: checks the response status code — if 200 (OK), examines the content further; if the response contains the "flag" key, it signifies a successful login, then prints the discovered password and captured flag; 4) **Continues or Terminates**: if the response doesn't indicate success, proceeds to the next password; continues until the correct password is found or the wordlist is exhausted |

## Hybrid Attacks

| **Category** | **Details** |
|---|---|
| **Context** | Many organizations require periodic password changes; these policies can inadvertently breed predictable patterns if users are not educated on proper password hygiene; widespread insecure practice: minor modifications when forced to change — appending a number or special character to the current password (e.g., `Summer2023` → `Summer2023!` or `Summer2024`) |
| **Why hybrid attacks work** | This predictable behavior creates a loophole; attackers capitalize on this human tendency by employing sophisticated techniques that combine the strengths of dictionary and brute-force attacks, drastically increasing the likelihood of successful breaches |
| **Hybrid Attacks in Action — example** | Consider an attacker targeting an organization known to enforce regular password changes; begins with a dictionary attack using a wordlist curated with common passwords, industry-specific terms, and potentially personal information related to the organization or employees — quickly identifies low-hanging fruit (accounts with weak/easily guessable passwords) |
| **Hybrid Attacks in Action — transition** | If the dictionary attack is unsuccessful, the hybrid attack seamlessly transitions into brute-force mode; instead of randomly generating combinations, it strategically modifies words from the original wordlist, appending numbers, special characters, or incrementing years (as in the `Summer2023` example) |
| **Hybrid Attacks in Action — result** | Targeted brute-force drastically reduces the search space compared to traditional brute force while covering many potential password variations users might employ to comply with password change policy |
| **Power of Hybrid Attacks** | Effectiveness lies in adaptability and efficiency; leverage strengths of both dictionary and brute-force techniques, maximizing chances of cracking passwords, especially where users fall into predictable patterns |
| **Power — not limited to password change** | Can be tailored to exploit any observed or suspected password patterns within a target organization |
| **Practical example — policy** | Target organization with password policy: minimum length 8 characters; at least one uppercase letter; at least one lowercase letter; at least one number |
| **Practical example — download wordlist** | `wget https://raw.githubusercontent.com/danielmiessler/SecLists/refs/heads/master/Passwords/Common-Credentials/darkweb2017_top-10000.txt` |
| **Practical example — filter min length** | `grep -E '^.{8,}$' darkweb2017_top-10000.txt > darkweb2017-minlength.txt` — regex `^.{8,}$` ensures only passwords with at least 8 characters pass through |
| **Practical example — filter uppercase** | `grep -E '[A-Z]' darkweb2017-minlength.txt > darkweb2017-uppercase.txt` — regex `[A-Z]` discards passwords lacking an uppercase letter |
| **Practical example — filter lowercase** | `grep -E '[a-z]' darkweb2017-uppercase.txt > darkweb2017-lowercase.txt` — regex `[a-z]` keeps only passwords with at least one lowercase letter |
| **Practical example — filter number** | `grep -E '[0-9]' darkweb2017-lowercase.txt > darkweb2017-number.txt` — regex `[0-9]` ensures passwords contain at least one numerical digit |
| **Practical example — result** | `wc -l darkweb2017-number.txt` → `89 darkweb2017-number.txt`; meticulously filtering the 10,000-password list against the policy narrowed potential passwords to **89**; drastic reduction in search space = significant boost in efficiency for subsequent cracking; smaller targeted list = faster, more focused attack, optimizing computational resources and increasing likelihood of success |
| **Credential Stuffing — overview** | Exploits the reality that many users reuse passwords across multiple online accounts; pervasive practice driven by convenience and the challenge of managing numerous unique credentials; creates fertile ground for attackers |
| **Credential Stuffing — stage 1** | Attackers acquire lists of compromised usernames and passwords; lists can stem from large-scale data breaches or be compiled through phishing scams and malware; publicly available wordlists like `rockyou` or those in SecLists can also serve as a starting point |
| **Credential Stuffing — stage 2** | Once armed with credentials, attackers identify potential targets — online services likely used by the individuals (social media, email providers, online banking, e-commerce sites are prime targets due to sensitive data) |
| **Credential Stuffing — stage 3** | Attack shifts into an automated phase; attackers use tools/scripts to systematically test stolen credentials against chosen targets, often mimicking normal user behavior to avoid detection; rapidly test vast numbers of credentials, increasing chances of finding a match |
| **Credential Stuffing — stage 4** | A successful match grants unauthorized access, opening the door to malicious activities — data theft, identity fraud, financial crimes; the compromised account may be a launchpad for further attacks, spreading malware, or infiltrating connected systems |
| **The Password Reuse Problem** | Core issue fueling credential stuffing's success; when users rely on the same or similar passwords for multiple accounts, a breach on one platform can have a domino effect, compromising numerous other accounts; highlights the urgent need for strong, unique passwords for every online service, coupled with proactive measures like multi-factor authentication |


# Hydra
## Hydra

| **Category** | **Details** |
|---|---|
| **Overview** | Fast network login cracker supporting numerous attack protocols; versatile tool to brute-force a wide range of services, including web applications, remote login services like SSH and FTP, and even databases |
| **Popularity — Speed and Efficiency** | Utilizes parallel connections to perform multiple login attempts simultaneously, significantly speeding up the cracking process |
| **Popularity — Flexibility** | Supports many protocols and services, making it adaptable to various attack scenarios |
| **Popularity — Ease of Use** | Relatively easy to use despite its power, with a straightforward command-line interface and clear syntax |
| **Installation — verify** | Often pre-installed on popular penetration testing distributions; verify presence with `hydra -h` |
| **Installation — install** | If not installed or using a different Linux distribution: `sudo apt-get -y update` then `sudo apt-get -y install hydra` |
| **Basic syntax** | `hydra [login_options] [password_options] [attack_options] [service_options]` |
| **Parameter — -l LOGIN or -L FILE** | Login options: specify either a single username (`-l`) or a file containing a list of usernames (`-L`); e.g., `hydra -l admin ...` or `hydra -L usernames.txt ...` |
| **Parameter — -p PASS or -P FILE** | Password options: provide either a single password (`-p`) or a file containing a list of passwords (`-P`); e.g., `hydra -p password123 ...` or `hydra -P passwords.txt ...` |
| **Parameter — -t TASKS** | Tasks: define the number of parallel tasks (threads) to run, potentially speeding up the attack; e.g., `hydra -t 4 ...` |
| **Parameter — -f** | Fast mode: stop the attack after the first successful login is found; e.g., `hydra -f ...` |
| **Parameter — -s PORT** | Port: specify a non-default port for the target service; e.g., `hydra -s 2222 ...` |
| **Parameter — -v or -V** | Verbose output: display detailed information about the attack's progress, including attempts and results; e.g., `hydra -v ...` or `hydra -V ...` (even more verbosity) |
| **Parameter — service://server** | Target: specify the service (e.g., ssh, http, ftp) and the target server's address or hostname; e.g., `hydra ssh://192.168.1.100` |
| **Parameter — /OPT** | Service-specific options: provide any additional options required by the target service; e.g., `hydra http-get://example.com/login.php -m "POST:user=^USER^&pass=^PASS^"` (HTTP form-based authentication) |
| **Hydra Services — overview** | Services define the specific protocols/services Hydra can target; each module understands a particular protocol's communication patterns and authentication requirements, allowing Hydra to send appropriate login requests and interpret responses |
| **Service — ftp** | File Transfer Protocol (FTP); brute-force login credentials for FTP services, commonly used to transfer files over a network; e.g., `hydra -l admin -P /path/to/password_list.txt ftp://192.168.1.100` |
| **Service — ssh** | Secure Shell (SSH); targets SSH services to brute-force credentials, commonly used for secure remote login; e.g., `hydra -l root -P /path/to/password_list.txt ssh://192.168.1.100` |
| **Service — http-get/post** | HTTP Web Services; brute-force login credentials for HTTP web login forms using GET or POST requests; e.g., `hydra -l admin -P /path/to/password_list.txt http://192.168.1.100 http-post-form "/login.php:user=^USER^&pass=^PASS^:F=incorrect"` |
| **Service — smtp** | Simple Mail Transfer Protocol; attacks email servers by brute-forcing login credentials for SMTP, commonly used to send emails; e.g., `hydra -l admin -P /path/to/password_list.txt smtp://mail.server.com` |
| **Service — pop3** | Post Office Protocol (POP3); targets email retrieval services to brute-force credentials for POP3 login; e.g., `hydra -l user@example.com -P /path/to/password_list.txt pop3://mail.server.com` |
| **Service — imap** | Internet Message Access Protocol; brute-force credentials for IMAP services, which allow users to access their email remotely; e.g., `hydra -l user@example.com -P /path/to/password_list.txt imap://mail.server.com` |
| **Service — mysql** | MySQL Database; attempts to brute-force login credentials for MySQL databases; e.g., `hydra -l root -P /path/to/password_list.txt mysql://192.168.1.100` |
| **Service — mssql** | Microsoft SQL Server; targets Microsoft SQL servers to brute-force database login credentials; e.g., `hydra -l sa -P /path/to/password_list.txt mssql://192.168.1.100` |
| **Service — vnc** | Virtual Network Computing (VNC); brute-forces VNC services, used for remote desktop access; e.g., `hydra -P /path/to/password_list.txt vnc://192.168.1.100` |
