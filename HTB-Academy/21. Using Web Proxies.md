# Using Web Proxies
## Intro to Web Proxies

| **Category** | **Details** |
|---|---|
| **Context** | Most modern web and mobile applications work by continuously connecting to back-end servers to send/receive data and processing it on the user's device (browsers, mobile phones); with heavy reliance on back-end servers, testing and securing them is increasingly important |
| **Web App Pen Testing** | Testing web requests to back-end servers makes up the bulk of Web Application Penetration Testing; concepts apply to both web and mobile applications |
| **Purpose of web proxies** | To capture requests/traffic between applications and back-end servers and manipulate them for testing purposes, we need Web Proxies |
| **What are web proxies** | Specialized tools set up between a browser/mobile application and a back-end server to capture and view all web requests sent between both ends; essentially act as **man-in-the-middle (MITM)** tools |
| **Web proxies vs network sniffers** | Network sniffing applications like Wireshark analyze all local traffic to see what passes through a network; Web Proxies mainly work with web ports such as (but not limited to) **HTTP/80** and **HTTPS/443** |
| **Why web proxies are essential** | Among the most essential tools for any web pentester; significantly simplify capturing and replaying web requests compared to earlier CLI-based tools |
| **Capabilities** | Once set up, see all HTTP requests made by an application and all responses from the back-end server; intercept a specific request to modify its data and see how the back-end server handles it — an essential part of any web penetration test |
| **Uses of web proxies** | Web application vulnerability scanning; web fuzzing; web crawling; web application mapping; web request analysis; web configuration testing; code reviews |
| **Module scope** | Will not discuss specific web attacks (covered in other HTB Academy web modules); will thoroughly cover how to use web proxies and their features, and mention which type of web attacks require which feature; covers the two most common web proxy tools: **Burp Suite** and **ZAP** |
| **Burp Suite — overview** | Most common web proxy for web penetration testing; excellent user interface for its various features; provides a built-in Chromium browser to test web applications; certain features only available in the commercial version Burp Pro/Enterprise, but even the free version is an extremely powerful testing tool |
| **Burp — paid-only features** | Active web app scanner; fast Burp Intruder; ability to load certain Burp Extensions |
| **Burp — free vs pro** | Community free version is enough for most penetration testers; pro features may become handy for more advanced web app pentesting; most features covered in this module are available in the community free version, but some pro features (like the Active Web App Scanner) will be touched upon |
| **Burp — tip** | With an educational or business email address, apply for a free trial of Burp Pro to follow along with some Burp Pro-only features showcased later in the module |
| **ZAP — overview** | OWASP Zed Attack Proxy (ZAP) is another common web proxy tool; free and open-source project initiated by the Open Web Application Security Project (OWASP) and maintained by the community — no paid-only features as Burp has; has grown significantly and is quickly gaining market recognition as the leading open-source web proxy tool |
| **ZAP — features** | Provides various basic and advanced features for web pentesting; has certain strengths over Burp (covered throughout the module) |
| **ZAP — main advantage over Burp** | Being a free, open-source project means no throttling or limitations in scans that are only lifted with a paid subscription; with a growing community of contributors, ZAP is gaining many paid-only Burp features for free |
| **Learning both tools** | Learning both can be quite similar and provides options for every situation through a web pentest; choose whichever is more suitable — sometimes not enough value to justify a paid Burp subscription → switch to ZAP for a completely open and free experience; other times a more mature solution for advanced/corporate pentests → Burp Pro features may justify the cost |

# Web Proxy
## Proxy Setup

| **Category** | **Details** |
|---|---|
| **Context** | After installing and starting both tools (Burp and ZAP), learn the most commonly used feature: Web Proxy; set up tools as a proxy for any application so all web requests route through them to manually examine requests/responses, understand background behavior, intercept/change requests, or reuse them with changes |
| **Pre-configured browser — overview** | To use tools as web proxies, configure browser proxy settings to use them as the proxy or use the pre-configured browser; both tools have a pre-configured browser with proxy settings and CA certificates pre-installed, making starting a web pentest quick and easy |
| **Burp — pre-configured browser** | In Burp's **Proxy > Intercept**, click **Open Browser** → opens Burp's pre-configured browser and automatically routes all web traffic through Burp; Proxy tab shows Intercept off, option to use Burp's embedded browser |
| **ZAP — pre-configured browser** | Click the **Firefox browser icon** at the end of the top bar → opens the pre-configured browser proxied through ZAP (tooltip: "Open the browser you've chosen in the Quick Start tab pre-configured to proxy through ZAP") |
| **Pre-configured browser — suitability** | For uses in this module, using the pre-configured browser should be enough |
| **Proxy setup — real browser** | In many cases, want to use a real browser (e.g., Firefox); configure it manually via Firefox preferences to use the web proxy listening port |
| **Default ports** | Both Burp and ZAP use port **8080** by default; can use any available port; if the chosen port is in use, the proxy will fail to start and show an error message |
| **Changing proxy port** | Burp: **Proxy > Proxy settings > Proxy listeners**; ZAP: **Tools > Options > Network > Local Servers/Proxies**; must ensure Firefox proxy uses the same port |
| **FoxyProxy — overview** | Firefox extension to easily and quickly change the Firefox proxy instead of manually switching; pre-installed in PwnBox; install on own Firefox via Firefox Extensions Page → Add to Firefox |
| **FoxyProxy — configure** | Click the icon in Firefox's top bar → **Options** → click **Add** on the left pane → use `127.0.0.1` as IP, `8080` as port, name it Burp or ZAP, click **Save** |
| **FoxyProxy — PwnBox note** | This configuration is already added to FoxyProxy in PwnBox — no need to do this step if using PwnBox |
| **FoxyProxy — enable** | Click the FoxyProxy icon and select Burp/ZAP |
| **CA certificate — why** | Important step when using Burp Proxy/ZAP with a browser; without it, some HTTPS traffic may not get properly routed, or you may need to click accept every time Firefox sends an HTTPS request |
| **Burp — install certificate** | Select Burp as proxy in FoxyProxy → browse to `http://burp` → download certificate by clicking **CA Certificate** (Burp Suite Community Edition header with 'CA Certificate' button) |
| **ZAP — install certificate** | **Tools > Options > Network > Server Certificates** → click **Save** (Dynamic SSL Certificates window with Generate, Import, View, Save buttons); can change certificate by generating a new one with **Generate** |
| **Firefox — install certificate** | Browse to `about:preferences#privacy` → scroll to bottom → click **View Certificates** → select **Authorities** tab → click **Import** → select downloaded CA certificate |
| **Firefox — trust certificate** | Select **Trust this CA to identify websites** and **Trust this CA to identify email users** → click **OK** (Downloading Certificate dialog asking to trust 'PortSwigger CA' for websites and email) |
| **Result** | Once the certificate is installed and Firefox proxy is configured, all Firefox web traffic starts routing through the web proxy |

## Intercepting Web Requests

| **Category** | **Details** |
|---|---|
| **Context** | Now that the proxy is set up, use it to intercept and manipulate various HTTP requests sent by the web application under test; learn to intercept web requests, change them, and send them to their intended destination |
| **Burp — interception setup** | Navigate to the **Proxy** tab; request interception should be on by default; to turn it on/off, go to the **Intercept** sub-tab and click the **Intercept is on/off** button |
| **Burp — intercept workflow** | Turn interception on → start the pre-configured browser → visit the target website → go back to Burp to see the intercepted request awaiting action → click **Forward** to forward the request |
| **Burp — note** | As all Firefox traffic is intercepted, another request may be intercepted before the target one; if that happens, click **Forward** until reaching the request to the target IP |
| **ZAP — interception setup** | Interception is off by default (green button on the top bar indicates requests can pass); click the button to turn Request Interception on/off, or use shortcut **CTRL+B** to toggle |
| **ZAP — intercept workflow** | Start the pre-configured browser → revisit the exercise webpage → see the intercepted request in the top-right pane → click the **step** button (right of the red break button) to forward the request |
| **ZAP — Heads Up Display (HUD)** | Powerful feature allowing control of most main ZAP features from within the pre-configured browser; enable by clicking its button at the end of the top menu bar |
| **ZAP — HUD interception** | Click the second button from the top on the left pane to turn request interception on; once the page is refreshed or another request is sent, the HUD intercepts and presents it for action; note: in some browser versions, the ZAP HUD might not work as intended |
| **ZAP — HUD action buttons** | **Step** (send the request and examine its response, break any further requests — helpful to examine every step of the page's functionality); **Continue** (let the page send the remaining requests — useful when only interested in a single request); **Drop** (discard the request) |
| **ZAP — HUD tip** | First time using the pre-configured ZAP browser, a HUD tutorial is presented; consider taking it after this section to learn HUD basics; if you do not get the tutorial, click the configuration button on the bottom right and choose "Take the HUD tutorial" |
| **Manipulating intercepted requests** | Once intercepted, the request hangs until forwarded; examine the request, manipulate it to make any changes, then send it to its destination; helps understand what information a web application sends in its web requests and how it may respond to changes |
| **Applications in Web Pen Testing** | Testing for SQL injections, command injections, upload bypass, authentication bypass, XSS, XXE, error handling, deserialization, and many other potential web vulnerabilities (covered in other HTB Academy web modules) |
| **Basic example — setup** | Turn request interception back on, set the IP value on the page, click the **Ping** button; once intercepted, get an HTTP request similar to: `POST /ping HTTP/1.1`, `Host: 94.237.62.138:32306`, `Content-Length: 4`, `Content-Type: application/x-www-form-urlencoded`, `User-Agent: Mozilla/5.0 ... Chrome/139.0.0.0 ...`, body `ip=1` |
| **Basic example — manipulation** | Typically only numbers can be specified in the IP field (front-end JavaScript prevents non-numeric characters); with interception and manipulation, try other characters to "break" the application (breaking the request/response flow by manipulating the target parameter, not damaging the target web application); if the back-end does not verify/validate HTTP requests, may be able to exploit it |
| **Basic example — payload** | Change the `ip` parameter's value from `1` to `;ls;` and see how the web application handles the input |
| **Basic example — result** | After clicking continue/forward, the response changes from the default ping output to the `ls` output → successfully manipulated the request to inject a command; output lists `flag.txt`, `index.html`, `node_modules`, `package-lock.json`, `public`, `server.js` |
| **Takeaway** | Demonstrates a basic example of how request interception and manipulation helps test web applications for various vulnerabilities; considered an essential tool to test different web applications effectively |
| **Note** | Specific web attacks are not covered in this module, but rather how Web Proxies facilitate various types of attacks; other HTB Academy web modules cover these attacks in depth |

|---|---|
| **Context** | In some instances, may need to intercept HTTP responses from the server before they reach the browser; useful to change how a specific web page looks (e.g., enabling disabled fields or showing hidden fields), helping in penetration testing |
| **Use case — IP field example** | In the previous exercise, the IP field only allowed numeric values; intercepting the response before it reaches the browser allows editing it to accept any value, enabling direct input of the payload used previously |
| **Burp — enable response interception** | Go to **Proxy > Proxy settings** and enable **Intercept Response** under Response interception rules; settings show rules table with Add, Edit, Remove, Up, Down buttons; options to intercept responses and update Content-Length header |
| **Burp — intercept workflow** | Enable request interception again → refresh the page with **CTRL+SHIFT+R** (force full refresh) → go back to Burp → see intercepted request → click **Forward** → see the intercepted response |
| **Burp — intercepted response (HTML)** | HTML form code for "Ping Your IP" with input field for IP address: `type="number"`, `min="1"`, `max="255"`, `maxlength="3"` |
| **Burp — modify response** | Change `type="number"` on line 27 to `type="text"` (enable writing any value); change `maxlength="3"` to `maxlength="100"` (allow longer input); example: `<input type="text" id="ip" name="ip" min="1" max="255" maxlength="100" oninput="javascript: if (this.value.length > this.maxLength) this.value = this.value.slice(0, this.maxLength);" required>` |
| **Burp — forward and examine** | Click **Forward** again → go back to Firefox to examine the edited response → page can now input any value; same technique can persistently enable any disabled HTML buttons by modifying their HTML code |
| **Exercise** | Try using the payload used previously directly within the browser to test how intercepting responses makes web app pentesting easier |
| **ZAP — response interception** | When requests are intercepted by ZAP, click **Step** → sends the request and automatically intercepts the response; HTTP Message dialog shows response headers and HTML form code with Step, Continue, Drop buttons |
| **ZAP — modify and continue** | Make the same changes as before → click **Continue** → can use any input value |
| **ZAP HUD — Show/Enable button** | Third button on the left (light bulb icon) enables/shows disabled or hidden input fields without intercepting the response or refreshing the page; e.g., for a web application with the IP input field disabled, click **Show/Enable** → field is enabled and can be interacted with; similarly use this feature to show all hidden fields or buttons |
| **Burp — similar feature** | **Proxy > Proxy settings > Response modification rules** → select an option like **Unhide hidden form fields** |
| **ZAP HUD — Comments button** | Indicates positions where there are HTML comments (usually only visible in source code); click the **+** button on the left pane → select **Comments** to add the button → click it to show Comments indicators; hovering over an indicator shows the comment's content |
| **Takeaway** | Being able to modify how the web page looks makes web app pentesting much easier in certain scenarios instead of having to send input through an intercepted request; next: automate the process to modify changes in the response automatically so you don't have to keep intercepting and manually changing responses |

## Automatic Modification

| **Category** | **Details** |
|---|---|
| **Context** | May want to apply certain modifications to all outgoing HTTP requests or all incoming HTTP responses; utilize automatic modifications based on rules set, so the web proxy tools apply them automatically |
| **Automatic Request Modification — overview** | Match any text within requests (request header or request body) and replace it with different text; demonstration: replace User-Agent with `HackTheBox Agent 1.0` — handy when dealing with filters that block certain User-Agents |
| **Burp Match and Replace — location** | Go to **Proxy > Proxy settings > HTTP match and replace rules** → click **Add** |
| **Burp — rule options** | **Type**: Request header (change is in the request header, not body); **Match**: `^User-Agent.*$` (regex matching the entire line with User-Agent); **Replace**: `User-Agent: HackTheBox Agent 1.0`; **Regex match**: True (exact User-Agent string unknown, so regex matches any value matching the pattern) |
| **Burp — result** | New Match and Replace option added, enabled, and automatically replaces the User-Agent header; verify by visiting any website using the pre-configured Burp browser and reviewing the intercepted request → `User-Agent: HackTheBox Agent 1.0` |
| **ZAP Replacer — access** | Similar feature called **Replacer**; press **CTRL+R** or click Replacer in ZAP's options menu → click **Add** |
| **ZAP — rule options** | **Description**: HTB User-Agent; **Match Type**: Request Header (will add if not present); **Match String**: `User-Agent` (select the header from the drop-down; ZAP replaces its value); **Replacement String**: `HackTheBox Agent 1.0`; **Enable**: True |
| **ZAP — Request Header String (Regex)** | ZAP also has the Request Header String option usable with a regex pattern; try using the same values as Burp to see how it works |
| **ZAP — Initiators** | Option to set Initiators (accessible via the other tab); enables selecting where the Replacer option is applied; keep default **Apply to all HTTP(S) messages** |
| **ZAP — verify** | Enable request interception by pressing **CTRL+B** → visit any page in the pre-configured ZAP browser → `User-Agent: HackTheBox Agent 1.0` highlighted in the request |
| **Automatic Response Modification — overview** | Same concept with HTTP responses; previously the modifications made to the IP field were temporary and not applied on refresh unless intercepted and added again; automate response modification to automatically enable any characters in the IP field for easier command injection |
| **Burp — response rule** | Go back to **Proxy > Options > Match and Replace** → add another rule; **Type**: Response body (change exists in the response body, not headers); no regex needed since the exact string is known (though regex is possible) |
| **Burp — response rule options** | **Type**: Response body; **Match**: `type="number"`; **Replace**: `type="text"`; **Regex match**: False |
| **Burp — additional rule** | Add another rule to change `maxlength="3"` to `maxlength="100"` |
| **Burp — verify persistence** | Refresh the page with **CTRL+SHIFT+R** → can add any input to the input field; persists between page refreshes |
| **Burp — result** | Click **Ping** → command injection should work without intercepting and modifying the request |

## Encoding/Decoding

| **Category** | **Details** |
|---|---|
| **Context** | As we modify and send custom HTTP requests, we may need to perform various types of encoding and decoding to interact with the web server properly; both tools have built-in encoders to quickly encode/decode various types of text |
| **URL Encoding — why essential** | Ensure request data is URL-encoded and request headers are correctly set; otherwise may get a server error in the response; key characters to encode: **Spaces** (may indicate end of request data if not encoded), **&** (otherwise interpreted as a parameter delimiter), **#** (otherwise interpreted as a fragment identifier) |
| **Burp — URL-encode** | In Burp Repeater, select the text → right-click → **Convert Selection > URL > URL-encode key characters**, or select text and click **CTRL+U**; Burp also supports URL-encoding as you type if you right-click and enable that option (encodes all text as you type) |
| **ZAP — URL-encode** | ZAP automatically URL-encodes all request data in the background before sending the request, though it may not be visible explicitly |
| **Other URL-encoding types** | Full URL-Encoding or Unicode URL-encoding — may be helpful for requests with many special characters |
| **Decoding — why important** | URL-encoding is key to HTTP requests, but not the only type of encoding encountered; web applications commonly encode their data, so be able to quickly decode it to examine the original text; back-end servers may expect data encoded in a particular format or with a specific encoder, so be able to quickly encode data before sending |
| **Encoders supported by both tools** | HTML, Unicode, Base64, ASCII hex |
| **Burp — full encoder** | Go to the **Decoder** tab; input any text and quickly encode or decode |
| **ZAP — full encoder** | Use the **Encoder/Decoder/Hash** by clicking **CTRL+E**; input any text and quickly encode or decode |
| **Example — Base64 cookie** | Cookie: `eyJ1c2VybmFtZSI6Imd1ZXN0IiwgImlzX2FkbWluIjpmYWxzZX0=`; input in Burp Decoder → select **Decode as > Base64** → get the decoded value |
| **Burp Inspector** | Recent Burp versions can use the **Burp Inspector** tool to perform encoding and decoding (among other things); found in various places like Burp Proxy or Burp Repeater; shows URL and Base64 decoding for encoded IP in request and HTML response |
| **ZAP — Encoder/Decoder/Hash** | Automatically decodes strings using various decoders in the **Decode** tab; shows Base64 encoded string and its decoded JSON output |
| **ZAP — Tip** | Create customized tabs in ZAP's Encoder/Decoder/Hash with the **Add New Tab** button; add any type of encoder/decoder you want the text shown in; try creating your own tab with a few encoders/decoders |
| **Encoding — example** | Decoded text holds `{"username":"guest", "is_admin":false}`; during a pentest, if a cookie holds this value, test modifying it to see whether it changes user privileges |
| **Encoding — modify and re-encode** | Copy the value, change `guest` to `admin` and `false` to `true`, re-encode using the original encoding method (Base64) → new base64 string |
| **Tip — Burp Decoder chaining** | Burp Decoder output can be directly encoded/decoded with a different encoder; select the new encoder method in the output pane at the bottom, and it will be encoded/decoded again |
| **Tip — ZAP chaining** | Copy the output text and paste it into the input field above |
| **Using the encoded string** | Copy the base64 encoded string and use it with the request in Burp Repeater or ZAP Request Editor; same concept for encoding/decoding various types of encoded text to perform effective web pentesting without other tools |

## Proxying Tools

| **Category** | **Details** |
|---|---|
| **Context** | Important aspect of using web proxies is enabling interception of web requests made by command-line tools and thick client applications; gives transparency into web requests made by these applications and allows utilization of all proxy features used with web applications |
| **Routing tool traffic** | To route all web requests made by a specific tool through web proxy tools, set them up as the tool's proxy (e.g., `http://127.0.0.1:8080`), similarly to browsers; each tool may have a different method for setting its proxy — may have to investigate how to do so for each one |
| **Section scope** | Covers examples of how to use web proxies to intercept web requests made by such tools; use either Burp or ZAP, as the setup process is the same |
| **Note — performance** | Proxying tools usually slows them down; only proxy tools when you need to investigate their requests, not for normal usage |
| **Proxychains — overview** | Very useful Linux tool that routes all traffic coming from any command-line tool to any specified proxy; adds a proxy to any command-line tool — simplest and easiest method to route web traffic of command-line tools through web proxies |
| **Proxychains — configure** | Edit `/etc/proxychains.conf`, comment out the final line, and add: `#socks4 127.0.0.1 9050` then `http 127.0.0.1 8080` |
| **Proxychains — quiet mode** | Use the `-q` option to operate in "quiet" mode, suppressing connection information output to the console; useful for reducing terminal clutter and focusing on application output |
| **Proxychains — example** | `proxychains -q curl http://SERVER_IP:PORT` → returns the HTML of the Ping IP page; back in Burp, the request has indeed gone through the proxy (Proxy tab showing HTTP GET request details with Forward, Drop, Intercept is on, Action, Open Browser) |
| **Metasploit — overview** | Proxy web traffic made by Metasploit modules to better investigate and debug them; start Metasploit with `msfconsole`; set a proxy for any exploit within Metasploit using the `set PROXIES` flag |
| **Metasploit — example** | `msfconsole` → `use auxiliary/scanner/http/robots_txt` → `set PROXIES HTTP:127.0.0.1:8080` → `set RHOST SERVER_IP` → `set RPORT PORT` → `run` → `[*] Scanned 1 of 1 hosts (100% complete)`, `[*] Auxiliary module execution completed` |
| **Metasploit — verify** | Go back to the web proxy and examine proxy history to view all sent requests; GET request to `/robots.txt` with 404 status — request has indeed gone through the web proxy |
| **Other tools** | Same method can be used with other scanners, exploits, and other features in Metasploit; similarly use web proxies with other tools and applications, including scripts and thick clients; all we have to do is set the proxy of each tool to use our web proxy |
| **Value** | Allows examining exactly what these tools are sending and receiving, and potentially repeating and modifying their requests while performing web application penetration testing |

# Web Fuzzer
## Burp Intruder

| **Category** | **Details** |
|---|---|
| **Context** | Both Burp and ZAP provide additional features beyond the default web proxy; two of the most important are web fuzzers and web scanners; built-in web fuzzers act as web fuzzing, enumeration, and brute-forcing tools; can be an alternative to CLI-based fuzzers like ffuf, dirbuster, gobuster, wfuzz |
| **Burp Intruder — overview** | Burp's web fuzzer; can fuzz pages, directories, sub-domains, parameters, parameter values, and many other things; much more advanced than most CLI-based web fuzzing tools |
| **Burp Intruder — free vs pro** | Free Burp Community version is throttled at **1 request per second** — extremely slow compared to CLI tools (up to 10k requests per second); use free version for short queries; Pro version has unlimited speed and very useful features — one of the best web fuzzing and brute-forcing tools |
| **Target — send to Intruder** | Start Burp and pre-configured browser → visit web application → go to Proxy History → locate request → right-click → **Send to Intruder**, or use shortcut **CTRL+I** |
| **Target — open Intruder** | Click the Intruder tab or use shortcut **CTRL+SHIFT+I**; Target text box shows details of the target fed from the request |
| **Positions — overview** | Place the payload position pointer — the point where words from the wordlist are placed and iterated over; demonstrate fuzzing web directories (similar to ffuf or gobuster) |
| **Positions — example** | To check whether a web directory exists, fuzz `GET /DIRECTORY/`; existing pages return 200 OK, otherwise 404 NOT FOUND; select DIRECTORY as the payload position by wrapping it with `§` or selecting the word and clicking **Add §** |
| **Positions — note** | Leave the extra two lines at the end of the request, otherwise may get an error response from the server |
