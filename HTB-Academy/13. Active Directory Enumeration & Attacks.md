# Active Directory Enumeration & Attacks
## Introduction to Active Directory Enumeration & Attacks

|**Category**|**Details**|
|---|---|
|**Active Directory Explained**||
|Definition|Directory service for Windows enterprise environments; officially implemented in 2000 with Windows Server 2000; incrementally improved with each subsequent server OS|
|Based on|Protocols x.500 and LDAP; still utilizes these protocols today|
|Structure|Distributed, hierarchical structure; centralized management of organization's resources (users, computers, groups, network devices, file shares, group policies, devices, trusts)|
|Functions|Authentication, accounting, authorization within Windows enterprise environment|
|Reference|Introduction to Active Directory module for in-depth look at structure, function, objects|
|**Why Should We Care About AD**||
|Market share|~43% market share for enterprise organizations utilizing Identity and Access management solutions (at time of writing)|
|Vulnerabilities|Microsoft had over 2,000 reported vulnerabilities tied to a CVE in last two years|
|Risk|Many services and main purpose of making information easy to find/access → behemoth to manage and correctly harden; exposes enterprises to vulnerabilities and exploitation from simple misconfigurations of services and permissions; combined with common user/OS vulnerabilities → perfect storm for attacker|
|Module focus|Identify, enumerate, take advantage of common issues; practice enumerating AD utilizing native tools/languages (Sysinternals, WMI, DNS, etc.); attacks: Password spraying, Kerberoasting, Responder, Kerbrute, BloodHound|
|**Goal of AD Assessment**||
|General goal|Escalate privileges by moving laterally or vertically throughout network until accomplishing intent of assessment|
|Intent varies|Accessing specific host, user's email inbox, database, or complete domain compromise; every possible path to Domain Admin level access within testing period|
|Approach|Understand how to perform enumeration manually; understand "why" behind flaws and misconfigurations; provide sound recommendations and remediation advice|
|Requirement|Comfortable enumerating and attacking AD from both Windows and Linux with limited toolset or built-in Windows tools ("living off the land"); adapt quickly on the fly|
|**Real-World Examples — Scenario 1 (Waiting On An Admin)**||
|Steps|Compromised single host → SYSTEM level access → enumerate domain → found SPNs → Kerberoasting → retrieved TGS tickets → attempted cracking with Hashcat (unsuccessful at first) → left cracking job overnight with large wordlist + d3ad0ne rule → hit on one ticket → cleartext password for user account → write access on certain file shares → dropped SCF files around shares + Responder → got NetNTLMv2 hash of user → BloodHound output showed user was domain admin|
|**Scenario 2 (Spraying The Night Away)**||
|Steps|Found SMB NULL session using enum4linux → retrieved user listing and domain password policy → password policy: minimum eight-character, complexity enforced (3/4 of special character, number, uppercase, lowercase, i.e., Welcome1) → tried common weak passwords (Welcome1, Password1, Password123, Spring2018) no hits → Spring@18 hit → ran BloodHound → found hosts where user had local admin access → domain admin had active session on one host → used Rubeus to extract Kerberos TGT ticket → pass-the-ticket attack → authenticate as domain admin → took over trusting domain (Domain Administrators group for taken-over domain was part of Administrators group in trusting domain via nested group membership)|
|**Scenario 3 (Fighting In The Dark)**||
|Steps|Used Kerbrute to enumerate valid usernames → used linkedin2username tool to mashup potential usernames from LinkedIn page → combined with statistically-likely-usernames GitHub repo → 516 valid users → password spraying with Welcome2021 (single hit) → ran Python version of BloodHound → all domain users had RDP access to single box → logged in → used DomainPasswordSpray to spray again (view password policy, remove accounts close to lockout from target list) → sprayed with Fall2021 (several hits) → one account in Help Desk group with GenericAll rights over Enterprise Key Admins group → Enterprise Key Admins had GenericAll privileges over domain controller → added account to group → authenticated → inherited privileges → performed Shadow Credentials attack → retrieved NT hash for domain controller machine account → DCSync attack → retrieved NTLM password hashes for all users in domain|
|**This Is The Way**||
|Takeaway|Importance of iterative enumeration, understanding target, adapting and thinking outside the box; some concepts outside scope of module; will perform many parts of attack chains in module sections; attack two different AD environments at end of module|
|**Practical Examples**||
|Environment|Target VMs can be spawned within relevant sections; RDP credentials for MS01 (Windows host); SSH access to preconfigured Parrot Linux host (ATTACK01)|
|Connection via FreeRDP|`xfreerdp /v:<MS01 target IP> /u:htb-student /p:Academy_student_AD!`|
|Connection via SSH|`ssh htb-student@<ATTACK01 target IP>` (enter provided password)|
|Xfreerdp to ATTACK01|`xfreerdp /v:<ATTACK01 target IP> /u:htb-student /p:HTB_@cademy_stdnt!` (XRDP server installed for GUI access to Parrot attack host; used for BloodHound GUI)|
|Note|Most sections provide credentials for htb-student on MS01 or ATTACK01; some sections different user/alternate credentials; labs can take 3-5 minutes to spawn|
|**Toolkit**||
|Windows attack host (MS01)|Tools in `C:\Tools` directory; Active Directory PowerShell module loads upon opening PowerShell console|
|Linux attack host (ATTACK01)|Tools installed and added to htb-student user's PATH or present in `/opt` directory|
|Recommendation|Compile/upload own tools and scripts to attack hosts; host on SMB share from Pwnbox; when performing actual penetration test, compile tools yourself to examine code beforehand and ensure nothing malicious hidden in compiled executable|
|**Final Note**||
|Encouragement|Have fun; think outside of the box; AD is immense; will not master overnight; keep working at it|

## Tools of the Trade

|**Tool**|**Description**|
|---|---|
|PowerView/SharpView|PowerShell tool and .NET port used to gain situational awareness in AD; replacements for various Windows net* commands; gather much of data BloodHound does but requires more work to make meaningful relationships; great for checking additional access with new credentials, targeting specific users/computers, finding "quick wins" (Kerberoasting/ASREPRoasting)|
|BloodHound|Visually map out AD relationships and plan attack paths that may otherwise go unnoticed; uses SharpHound PowerShell or C# ingestor; data imported into BloodHound JavaScript (Electron) application with Neo4j database for graphical analysis|

We are Penetration Testers working for CAT-5 Security. After a few successful engagements shadowing with the team, the more senior members want to see how well we can do starting an assessment on our own. The team lead sent us the following email detailing what we need to accomplish.

Tasking Email
Email from Jack Smith to Pentesting Interns about an assessment on Inlanefreight. Tasks include domain enumeration, credential discovery, lateral movement, privilege escalation, and acquiring Domain Admin credentials. The findings will guide further actions. Signed by J. Smith, Red Team Lead at Cat5 Security LLC. Includes a leadership quote.

This module will allow us to practice our skills (both prior and newly minted) with these tasks. The final assessment for this module is the execution of two internal penetration tests against the company Inlanefreight. During these assessments, we will work through an internal penetration test simulating starting from an external breach position and a second one beginning with an attack box inside the internal network as clients often request. Completing the skills assessments signifies the successful completion of the tasks mentioned in the scoping document and tasking email above. In doing so, we will demonstrate a firm grasp of many automated and manual AD attack and enumeration concepts, knowledge of and experience with a wide array of tools, and the ability to interpret data gathered from an AD environment to make critical decisions to advance the assessment. The content in this module is meant to cover core enumeration concepts necessary for anyone to be successful in performing internal penetration tests in Active Directory environments. We will also cover many of the most common attack techniques in great depth while working through some more advanced concepts as a primer for AD-focused material that will be covered in more advanced modules.

Methods Used
The following methods are authorized for assessing Inlanefreight and its systems :

External Information Gathering (Passive Checks)
External information gathering is authorized to demonstrate the risks associated with information that can be gathered about the company from the internet. To simulate a real-world attack, CAT-5 and its assessors will conduct external information gathering from an anonymous perspective on the internet with no information provided in advance regarding Inlanefreight outside of what is provided within this document.

Cat-5 will perform passive enumeration to uncover information that may help with internal testing. Testing will employ various degrees of information gathering from open-source resources to identify publicly accessible data that may pose a risk to Inlanefreight and assist with the internal penetration test. No active enumeration, port scans, or attacks will be performed against internet-facing "real-world" IP addresses or the website located at https://www.inlanefreight.com.

Internal Testing
The internal assessment portion is designed to demonstrate the risks associated with vulnerabilities on internal hosts and services ( Active Directory specifically) by attempting to emulate attack vectors from within Inlanefreight's area of operations. The result will allow Inlanefreight to assess the risks of internal vulnerabilities and the potential impact of a successfully exploited vulnerability.

To simulate a real-world attack, Cat-5 will conduct the assessment from an untrusted insider perspective with no advance information outside of what's provided in this documentation and discovered from external testing. Testing will start from an anonymous position on the internal network with the goal of obtaining domain user credentials, enumerating the internal domain, gaining a foothold, and moving laterally and vertically to achieve compromise of all in-scope internal domains. Computer systems and network operations will not be intentionally interrupted during the test.

Password Testing
Password files captured from Inlanefreight devices, or provided by the organization, may be loaded onto offline workstations for decryption and utilized to gain further access and accomplish the assessment goals. At no time will a captured password file or the decrypted passwords be revealed to persons not officially participating in the assessment. All data will be stored securely on Cat-5 owned and approved systems and retained for a period of time defined in the official contract between Cat-5 and Inlanefreight.

## LLMNR/NBT-NS Poisoning - from Linux

|**Category**|**Details**|
|---|---|
|**Core Concepts**||
|Goal|Acquire valid cleartext credentials for domain user account → foothold in domain for credentialed enumeration|
|Attack type|Man-in-the-Middle on LLMNR and NBT-NS broadcasts; can provide low-privileged or administrative level password hashes (cracked offline or cleartext credentials); hashes sometimes used for SMB Relay attack|
|**LLMNR & NBT-NS Primer**||
|LLMNR|Link-Local Multicast Name Resolution — Microsoft Windows component; alternate host identification when DNS fails; asks all other machines on local network via LLMNR; based on DNS format; allows hosts on same local link to perform name resolution; uses port 5355 over UDP|
|NBT-NS|NetBIOS Name Service — used if LLMNR fails; identifies systems on local network by NetBIOS name; uses port 137 over UDP|
|Vulnerability|ANY host on network can reply; attacker with network access can spoof authoritative name resolution source in broadcast domain by responding to LLMNR and NBT-NS traffic as if they have answer|
|Result|Victims communicate with attacker's system; capture NetNTLM hash → offline brute force → cleartext password; authentication request can be relayed to access another host or different protocol (LDAP) on same host; LLMNR/NBNS spoofing + lack of SMB signing can lead to administrative access|
|**Quick Example — Attack Flow**||
|Step 1|Host attempts to connect to `\\print01.inlanefreight.local` but types `\\printer01.inlanefreight.local`|

|Step 4|Attacker (Responder running) responds stating it is `\\printer01.inlanefreight.local`|

# Sighting In, Hunting For A User
## Password Spraying Overview

|**Category**|**Details**|
|---|---|
|**Core Concepts**||
|Definition|Attempting to log into an exposed service using one common password and longer list of usernames or email addresses|
|Usernames source|Gathered during OSINT phase or initial enumeration attempts|
|Context|Penetration test not static; constantly iterating through techniques and repeating processes; work in team or execute multiple TTPs at once; most assessments time-boxed|
|**Story Time — Scenario 1**||
|Situation|Non-evasive "grey box" assessment; internal network access with Linux VM; list of in-scope IP ranges; no SMB NULL session or LDAP anonymous bind found|
|Approach|Used Kerbrute to build target username list by enumerating valid domain users; combined jsmith.txt username list from statistically-likely-usernames GitHub repo with results from scraping LinkedIn|
|Action|Enumerated valid users with Kerbrute; password spray with common password `Welcome1`|
|Result|Two hits for very low privileged users; enough access to run BloodHound; eventually identified attack paths leading to domain compromise|
|**Story Time — Scenario 2**||
|Situation|Similar setup; enumerating valid domain users with common username lists and LinkedIn results yielded no results|
|Approach|Searched Google for PDFs published by organization; confirmed in document properties of 4 PDFs that internal username structure was format `F9L8` (randomly generated GUIDs using capital letters and numbers A-Z, 0-9)|
|Insight|Information published in Author field; importance of scrubbing document metadata before posting online|
|Username generation|Short Bash script generated 1,679,616 possible username combinations|
|Script|`#!/bin/bash` / `for x in {{A..Z},{0..9}}{{A..Z},{0..9}}{{A..Z},{0..9}}{{A..Z},{0..9}}` / `do echo $x;` / `done`|
|Action|Used generated username list with Kerbrute to enumerate every single user account in domain|
|Result|Predictable GUID combined with PDF metadata allowed enumeration of every account; significantly increased chances of successful password spraying; obtained valid passwords for few accounts; followed complicated attack chain involving Resource-Based Constrained Delegation (RBCD) and Shadow Credentials attack to ultimately gain control over domain|
|Note|Typically can only identify 40-60% of valid accounts using list such as jsmith.txt|
|**Password Spraying Considerations**||
|Risk|Careless use may cause considerable harm (locking out hundreds of production accounts)|
|Contrast with brute-forcing|Brute-forcing attempts to identify password for an account using long list of passwords; password spraying is more measured, utilizing very common passwords across multiple industries|
|Visualization|Attack 1: bob.smith@inlanefreight.local / Welcome1, john.doe@... / Welcome1, jane.doe@... / Welcome1 → DELAY → Attack 2: same users / Passw0rd → DELAY → Attack 3: same users / Winter2022|
|Lockout risk|Sending fewer login requests per username; less likely to lock out accounts than brute force; still risk of lockouts; introduce delay between login attempts|
|Internal use|Move laterally within network; same considerations regarding account lockouts; may be possible to obtain domain password policy with internal access, significantly lowering risk|
|**Password Policy**||
|Common configuration|Five bad attempts before lockout; 30-minute auto-unlock threshold|
|More extended|Longer account lockout thresholds; even requiring administrator to unlock accounts manually|
|Unknown policy|Good rule of thumb: wait a few hours between attempts (long enough for account lockout threshold to reset)|
|Best practice|Obtain password policy before attempting attack during internal assessment (not always possible)|
|Caution|Err on side of caution; choose just one targeted password spraying attempt using weak/common password as "hail mary" if all other options exhausted|
|Clarification|Ask client to clarify password policy depending on type of assessment|
|Enumeration|If already have foothold or provided user account, enumerate password policy in various ways (covered in next section)|

## Kerberoasting - from Linux

|**Category**|**Details**|
|---|---|
|**Core Concepts**||
|Kerberoasting|Lateral movement/privilege escalation technique in AD; targets Service Principal Names (SPN) accounts|
|SPNs|Unique identifiers Kerberos uses to map service instance to service account in whose context service runs; domain accounts often used to run services (overcome network authentication limitations of built-in accounts like `NT AUTHORITY\LOCAL SERVICE`)|
|Requirement|Any domain user can request Kerberos ticket for any service account in same domain; possible across forest trusts if authentication permitted across trust boundary; need account's cleartext password (or NTLM hash), shell in context of domain user account, or SYSTEM level access on domain-joined host|
|Risk|Domain accounts running services often local administrators, if not highly privileged domain accounts; service accounts may be granted administrator privileges on multiple servers across enterprise; often added to privileged groups (Domain Admins) directly or via nested membership; finding SPNs associated with highly privileged accounts very common|
|Mechanism|Retrieving Kerberos ticket for account with SPN does not by itself allow executing commands in context of this account; ticket (TGS-REP) encrypted with service account's NTLM hash → cleartext password can potentially be obtained by offline brute-force attack with Hashcat|
|Weakness|Service accounts often configured with weak/reused passwords to simplify administration; sometimes password same as username; if domain SQL Server service account password cracked → likely local admin on multiple servers, if not Domain Admin; even low-privilege user account → craft service tickets for service specified in SPN (e.g., SPN set to `MSSQL/SRV01` → access MSSQL service as sysadmin, enable `xp_cmdshell`, gain code execution)|
|Origin|Tim Medin's talk at Derbycon 2014|
|**Performing the Attack — Positions**||
|1|From non-domain joined Linux host using valid domain user credentials|
|2|From domain-joined Linux host as root after retrieving keytab file|
|3|From domain-joined Windows host authenticated as domain user|
|4|From domain-joined Windows host with shell in context of domain account|
|5|As SYSTEM on domain-joined Windows host|
|6|From non-domain joined Windows host using `runas /netonly`|
|**Tools**||
|1|Impacket's `GetUserSPNs.py` from non-domain joined Linux host|

|**Efficacy of the Attack**||
|Scenarios|Crack TGS ticket and obtain Domain Admin access straightway, or obtain credentials that help move down path to domain compromise; retrieve many TGS tickets, some crackable but none for privileged users (no additional access); unable to crack single TGS ticket even after days of cracking attempts with Hashcat on powerful GPU rig|

# An ACE in the Hole
## Access Control List (ACL) Abuse Primer

| Item | Details |
|---|---|
| **ACL definition** | Lists that define (a) who has access to which asset/resource and (b) the level of access provisioned; settings inside an ACL are called **Access Control Entries (ACEs)** |
| **ACE definition** | Each ACE maps back to a user, group, or process (security principal) and defines the rights granted to that principal; every AD object has an ACL but can have multiple ACEs; ACLs can also be used for auditing |
| **DACL** | Discretionary Access Control List — defines which security principals are granted or denied access to an object; made up of allow/deny ACEs; if no DACL exists → full rights granted to all; if DACL exists but has no ACEs → access denied to all |
| **SACL** | System Access Control List — allows administrators to log access attempts made to secured objects (via the Auditing tab) |
| **ACE types — Access denied** | Used within a DACL to explicitly deny a user/group access to an object |
| **ACE types — Access allowed** | Used within a DACL to explicitly grant a user/group access to an object |
| **ACE types — System audit** | Used within a SACL to generate audit logs when access is attempted; records whether access was granted and what type occurred |
| **ACE components (4)** | 1) SID of the user/group with access; 2) flag denoting ACE type (denied/allowed/audit); 3) inheritance flags (whether child containers/objects inherit the ACE); 4) access mask (32-bit value defining granted rights) |
| **Permission check order** | ACLs are checked from top to bottom until an **access denied** is found |
| **Why ACEs matter** | Attackers use ACEs for further access or persistence; organizations often unaware of applied ACEs; not detected by vulnerability scanners; often unchecked for years in large/complex environments; great for lateral/vertical movement when low-hanging fruit is fixed |
| **Abusable permissions (examples)** | ForceChangePassword → `Set-DomainUserPassword`; Add Members → `Add-DomainGroupMember`; GenericAll → `Set-DomainUserPassword` or `Add-DomainGroupMember`; GenericWrite → `Set-DomainObject`; WriteOwner → `Set-DomainObjectOwner`; WriteDACL → `Add-DomainObjectACL`; AllExtendedRights → `Set-DomainUserPassword` or `Add-DomainGroupMember`; AddSelf → `Add-DomainGroupMember` |
| **ForceChangePassword** | Right to reset a user's password without knowing their current password; use cautiously, best to consult client before resetting passwords |
| **GenericWrite** | Right to write to any non-protected attribute on an object; over a user → assign SPN and Kerberoast (needs weak password); over a group → add yourself/another principal; over a computer → resource-based constrained delegation (out of scope) |
| **AddSelf** | Shows security groups a user can add themselves to |
| **GenericAll** | Full control over a target object; over a user/group → modify membership, force password change, targeted Kerberoasting; over a computer with LAPS → read LAPS password, gain local admin |
| **Other interesting ACEs** | `ReadGMSAPassword` (use GMSAPasswordReader), `Unexpire-Password`, `Reanimate-Tombstones`; familiarize with all BloodHound edges and AD Extended Rights |
| **Attack use cases** | Lateral movement, privilege escalation, persistence |
| **Scenario — Forgot password** | Help Desk/IT users often have password reset rights; take over such an account → reset a more privileged account's password |
| **Scenario — Group membership mgmt** | Staff with add/remove rights over groups; enumerate to add a controlled account into a privileged built-in AD group |
| **Scenario — Excessive user rights** | Excessive rights on user/computer/group objects (e.g., Exchange install adds many ACL changes; legacy/accidental configs); take over an account given rights out of convenience |
| **Caution** | Some ACL attacks are "destructive" (e.g., password changes, AD modifications); run by client first for written approval; document attacks start to finish; revert changes; highlight changes in the report so client can verify reversion |

## DCSync

| **Category** | **Details** |
|---|---|
| **Recap** | From previous section, we have control over user `adunn` who has DCSync privileges in `INLANEFREIGHT.LOCAL`; this section covers leveraging it for full domain compromise from Linux and Windows attack hosts |
| **Scenario setup** | Move between Windows and Linux attack hosts; RDP into MS01 with `htb-student:Academy_student_AD!`; for Linux portion (secretsdump.py), open PowerShell on MS01 and SSH to `172.16.5.225` with `htb-student:HTB_@cademy_stdnt!`; could also use secretsdump.exe compiled for Windows |
| **What is DCSync** | Technique for stealing the AD password database using the built-in **Directory Replication Service Remote Protocol** (used by DCs to replicate domain data); allows an attacker to mimic a Domain Controller to retrieve user NTLM password hashes |
| **Attack crux** | Request a Domain Controller to replicate passwords via the **DS-Replication-Get-Changes-All** extended right (extended access control right within AD allowing replication of secret data) |
| **Prerequisite** | Must have control over an account with rights to perform domain replication (**Replicating Directory Changes** and **Replicating Directory Changes All** permissions); Domain/Enterprise Admins and default domain administrators have this by default |
| **Common finding** | Other accounts (e.g., standard domain users) are often found with these rights during assessments; once compromised, their access can retrieve current NTLM hash for any domain user plus previous password hashes |
| **View adunn's group membership** | `Get-DomainUser -Identity adunn \|select samaccountname,objectsid,memberof,useraccountcontrol \|fl` → SID `S-1-5-21-3842939050-3880317879-2865463114-1164`; memberof VPN Users, Shared Calendar Read, Printer Access, File Share H Drive...; `useraccountcontrol: NORMAL_ACCOUNT, DONT_EXPIRE_PASSWORD` |
| **Confirm replication rights with PowerView** | `$sid= "S-1-5-21-3842939050-3880317879-2865463114-1164"`<br>`Get-ObjectAcl "DC=inlanefreight,DC=local" -ResolveGUIDs \| ? { ($_.ObjectAceType -match 'Replication-Get')} \| ?{$_.SecurityIdentifier -match $sid} \|select AceQualifier, ObjectDN, ActiveDirectoryRights,SecurityIdentifier,ObjectAceType \| fl` → confirms `adunn` has `DS-Replication-Get-Changes`, `DS-Replication-Get-Changes-All`, `DS-Replication-Get-Changes-In-Filtered-Set` |
| **Track-covering option** | With certain rights over the user (e.g., WriteDacl), add the privilege to a controlled user, execute DCSync, then remove privileges to attempt covering tracks |
| **DCSync tools** | Mimikatz, Invoke-DCSync, Impacket's `secretsdump.py` |
| **secretsdump.py — extract NTLM + Kerberos keys** | `secretsdump.py -outputfile inlanefreight_hashes -just-dc INLANEFREIGHT/adunn@172.16.5.5` — `-just-dc` extracts NTLM hashes and Kerberos keys from NTDS; outputs administrator (RID 500) hash `88ad09182de639ccc6579eb0849751cf`, krbtgt hash `16e26ba33e455a8c338142af8d89ffbc`, etc. |
| **secretsdump.py — useful flags** | `-just-dc-ntlm` (NTLM only); `-just-dc-user <USERNAME>` (specific user); `-pwd-last-set` (when password last changed); `-history` (password history); `-user-status` (check disabled users); filter out disabled users when providing password cracking statistics to client |
| **Output files** | `-just-dc` creates three files: `.ntds` (NTLM hashes), `.ntds.kerberos` (Kerberos keys), `.ntds.cleartext` (cleartext passwords for accounts with reversible encryption) |
| **Reversible encryption** | Rare but seen occasionally; set to support applications using certain protocols requiring user password for authentication; passwords stored using **RC4 encryption** (not true cleartext); key to decrypt (Syskey) stored in registry and extractable by Domain Admin or equivalent; `secretsdump.py` decrypts them while dumping NTDS; if disabled, user must change password for it to be stored with one-way encryption |

| **Enumerate reversible encryption — PowerView** | `Get-DomainUser -Identity * \| ? {$_.useraccountcontrol -like '*ENCRYPTED_TEXT_PWD_ALLOWED*'} \|select samaccountname,useraccountcontrol` → `proxyagent ENCRYPTED_TEXT_PWD_ALLOWED, NORMAL_ACCOUNT` |
| **View decrypted password** | `cat inlanefreight_hashes.ntds.cleartext` → `proxyagent:CLEARTEXT:Pr0xy_ILFREIGHT!` |
| **Real-world note** | Some engagements have all user accounts stored with reversible encryption; clients may do this to dump NTDS and perform periodic password strength audits without offline cracking |
| **Mimikatz — runas context** | Mimikatz must run in context of user with DCSync privileges; use `runas /netonly /user:INLANEFREIGHT\adunn powershell` from cmd, enter password, then spawn PowerShell |
| **Mimikatz — DCSync** | `.\mimikatz.exe` → `privilege::debug` → `lsadump::dcsync /domain:INLANEFREIGHT.LOCAL /user:INLANEFREIGHT\administrator` → retrieves administrator NTLM hash `88ad09182de639ccc6579eb0849751cf`; could also target krbtgt for Golden Ticket persistence (out of scope) |

## Kerberos "Double Hop" Problem

| **Category** | **Details** |
|---|---|
| **What is the Double Hop problem** | Issue that arises when an attacker attempts to use Kerberos authentication across two (or more) hops; concerns how Kerberos tickets are granted for specific resources |
| **Kerberos tickets vs passwords** | Kerberos tickets are not passwords — they are signed pieces of data from the KDC stating what resources an account can access; a ticket permits access to the requested resource (a single machine) |
| **Password authentication contrast** | When using a password to authenticate, the NTLM hash is stored in the session and can be used elsewhere without issue |
| **When it occurs** | Often when using WinRM/PowerShell — default authentication only provides a ticket to access a specific resource; causes issues with lateral movement or accessing file shares from the remote shell; the user has rights to perform an action but is denied access |
| **Common shell acquisition** | Attacking an application on the target host or using credentials + PSExec; initial authentication was likely over SMB or LDAP, so the user's NTLM hash is stored in memory |
| **Crux of the issue** | When using WinRM to authenticate over two or more connections, the user's password is never cached as part of their login; Mimikatz shows all credentials blank |
| **Example — Enter-PSSession + Mimikatz** | `Enter-PSSession -ComputerName DEV01 -Credential INLANEFREIGHT\backupadm` → `.\mimikatz "privilege::debug" "sekurlsa::logonpasswords" exit` → no credentials for `backupadm` in memory; `wsmprovhost.exe` runs in `backupadm` context (spawned by WinRM) |
| **Three-host scenario** | Attack host (Parrot, not domain-joined) → DEV01 → DC01; credentials are part of Remote Management Users on DEV01; PowerView enumeration requires communication with DC01 |
| **Why it fails** | Connecting to DEV01 via evil-winrm uses network authentication → credentials not stored in memory; when loading PowerView, Kerberos has no way to tell the DC the user can access resources; the user's **TGT is not sent to the remote session**, only the **TGS** for the target service |
| **Technical explanation** | TGS ticket is sent to the remote service (allows command execution), but TGT is not sent; when accessing subsequent resources, the TGT is missing → remote service cannot prove authentication is valid → access denied |
| **Unconstrained delegation exception** | If unconstrained delegation is enabled on a server, likely won't face the Double Hop problem; the user's TGT is sent along with the TGS, cached in memory, and can be used to request a TGS for the next host; generally, landing on a box with unconstrained delegation means you already won |
| **Workarounds overview** | Covered in an external post; two methods: (1) PSCredential object for evil-winrm sessions; (2) Register PSSession Configuration for GUI/Windows hosts |
| **Workaround #1 — PSCredential object** | Connect to remote host via host A, set up PSCredential object, pass credentials again with each command |
| **Workaround #1 — error without credentials** | `import-module .\PowerView.ps1` → `get-domainuser -spn` → error: "Exception calling FindAll... An operations error occurred" |
| **Workaround #1 — klist check** | `klist` → shows only 1 cached ticket: `Server: academy-aen-ms0$` (current server only); `Cache Flags: 0x4 -> S4U` |
| **Workaround #1 — set up credential** | `$SecPassword = ConvertTo-SecureString '!qazXSW@' -AsPlainText -Force`<br>`$Cred = New-Object System.Management.Automation.PSCredential('INLANEFREIGHT\backupadm', $SecPassword)` |
| **Workaround #1 — successful query** | `get-domainuser -spn -credential $Cred \| select samaccountname` → returns SPN accounts (azureconnect, backupjob, krbtgt, mssqlsvc, sqltest, sqlqa, sqldev, mssqladm, svc_sql, sqlprod, sapsso, sapvc, vmwarescvc) |
| **Workaround #1 — without -credential** | Fails again with the same error |
| **Workaround #1 — RDP contrast** | RDP to same host → `klist` → 4 cached tickets including `krbtgt/INLANEFREIGHT.LOCAL` (TGT), `ProtectedStorage/DC01`, `cifs/DC01`; password stored in memory → sent with every request → no double hop problem |
| **Workaround #2 — Register PSSession Configuration** | For domain-joined hosts connecting via WinRM (`Enter-PSSession`); alternative to PSCredential objects when tools don't support passing credentials |
| **Workaround #2 — establish session** | `Enter-PSSession -ComputerName ACADEMY-AEN-DEV01.INLANEFREIGHT.LOCAL -Credential inlanefreight\backupadm` |
| **Workaround #2 — klist check** | Shows only 1 TGS: `Server: HTTP/ACADEMY-AEN-DEV01...` (WinRM uses SOAP/XML over HTTP); `Cache Flags: 0x8 -> ASC`; no TGT |
| **Workaround #2 — PowerView fails** | `Import-Module .\PowerView.ps1` → `get-domainuser -spn \| select samaccountname` → same "FindAll" error |
| **Workaround #2 — register session config** | `Register-PSSessionConfiguration -Name backupadmsess -RunAsCredential inlanefreight\backupadm` — warnings about RunAs security model and WinRM restart |
| **Workaround #2 — restart WinRM** | `Restart-Service WinRM` in current PSSession (kicks you out) |
| **Workaround #2 — reconnect** | `Enter-PSSession -ComputerName DEV01 -Credential INLANEFREIGHT\backupadm -ConfigurationName backupadmsess` |
| **Workaround #2 — klist after reconnect** | Shows TGT: `Server: krbtgt/INLANEFREIGHT.LOCAL`, `Ticket Flags 0x40e10000 -> forwardable renewable initial pre_authent name_canonicalize`, `Cache Flags: 0x1 -> PRIMARY`, `Kdc Called: DC01` → double hop eliminated |
| **Workaround #2 — PowerView works** | `get-domainuser -spn \| select samaccountname` → returns SPN accounts without needing PSCredential |
| **Workaround #2 — limitations** | Cannot use `Register-PSSessionConfiguration` from evil-winrm (no credentials popup); `-RunAsCredential $Cred` fails because RunAs requires elevated PowerShell; doesn't work from PowerShell on Parrot/Ubuntu attack host due to Linux PowerShell/Kerberos limitations; highly effective from Windows attack host or RDP jump host |
| **Other methods (not covered)** | CredSSP, port forwarding, injecting into a process running in the context of a target user (sacrificial process) |
| **Wrap up** | Will encounter this often during assessments; must understand the issue and have tactics in the toolbox to avoid losing time |

# Why So Trusting ?
## Domain Trusts Primer

| **Category** | **Details** |
|---|---|
| **Scenario — why trusts exist** | Large organizations acquire companies over time; establishing a trust relationship with the new domain avoids migrating all established objects, making integration quicker; trusts can introduce weaknesses if not careful — a subdomain with an exploitable flaw can provide a quick route into the target domain |
| **Other trust scenarios** | Trusts with other companies (e.g., an MSP), a customer, or other business units of the same company (e.g., a division in another geographic region) |
| **Trust definition** | Used to establish forest-forest or domain-domain (intra-domain) authentication, allowing users to access resources in (or perform administrative tasks in) another domain outside the main domain where their account resides; creates a link between the authentication systems of two domains; may allow one-way or two-way (bidirectional) communication |
| **Trust types — Parent-child** | Two or more domains within the same forest; the child domain has a two-way transitive trust with the parent domain (e.g., `corp.inlanefreight.local` ↔ `inlanefreight.local`) |
| **Trust types — Cross-link** | Trust between child domains to speed up authentication |
| **Trust types — External** | Non-transitive trust between two separate domains in separate forests not already joined by a forest trust; utilizes SID filtering (filters out authentication requests by SID not from the trusted domain) |
| **Trust types — Tree-root** | Two-way transitive trust between a forest root domain and a new tree root domain; created by design when setting up a new tree root domain within a forest |
| **Trust types — Forest** | Transitive trust between two forest root domains |
| **Trust types — ESAE** | A bastion forest used to manage Active Directory |
| **Transitive trust** | Trust is extended to objects that the child domain trusts; e.g., if Domain A trusts Domain B and Domain B transitively trusts Domain C, then Domain A automatically trusts Domain C |
| **Non-transitive trust** | Only the child domain itself is trusted; not extended to next-level child domains |
| **Transitive vs non-transitive table** | **Transitive**: shared, 1-to-many; shared with anyone in the forest; forest, tree-root, parent-child, and cross-link trusts are transitive. **Non-transitive**: direct trust; not extended to next-level child domains; typical for external or custom trust setups |
| **Analogy** | Transitive: extended permission to anyone in your household (forest) to accept a package; non-transitive: strict orders that only the delivery service and you can handle and sign for the package |
| **One-way trust** | Users in a trusted domain can access resources in a trusting domain, not vice-versa |
| **Bidirectional trust** | Users from both trusting domains can access resources in the other domain (e.g., `INLANEFREIGHT.LOCAL` ↔ `FREIGHTLOGISTICS.LOCAL`) |
| **Security risk** | Trusts are often set up incorrectly and can provide critical unintended attack paths; trusts set up for ease of use may not be reviewed later for security implications; M&A can result in bidirectional trusts with acquired companies, unknowingly introducing risk if the acquired company's security posture is unknown/untested |
| **"End-around" attack** | Attackers may target a softer acquired company to get into your organization indirectly; not uncommon to Kerberoast a domain outside the principal domain and obtain a user with administrative access within the principal domain; many pen tests find no foothold in the principal domain but a flaw in a trusted domain gives a foothold or full admin rights |
| **Reporting note** | Often the larger organization is unaware that a trust relationship exists with one or more domains; keep this in mind for reporting |

| **SID History Primer** | `sidHistory` used in migration scenarios; when a user is migrated to another domain, a new account is created and the original user's SID is added to the new user's SID history attribute, ensuring access to resources in the original domain |
| **SID History — abuse** | Intended to work across domains but can work in the same domain; using Mimikatz, an attacker can perform SID history injection and add an administrator account to the SID History attribute of a controlled account; when logging in, all SIDs associated with the account are added to the user's token |
| **SID History — impact** | Token determines resource access; if a Domain Admin SID is added to the SID History attribute, the account can perform DCSync and create a Golden Ticket/TGT → authenticate as any account in the domain of choice for persistence |
| **ExtraSids Attack — overview** | Allows compromise of a parent domain once the child domain is compromised; within the same AD forest, the `sidHistory` property is respected due to lack of **SID Filtering** protection |
| **SID Filtering** | Protection that filters out authentication requests from a domain in another forest across a trust; since it's not applied within the same forest, a child-domain user with `sidHistory` set to the Enterprise Admins group (which only exists in the parent domain) is treated as a member → administrative access to the entire forest |

# Defensive Considerations
## Hardening Active Directory

| **Category** | **Details** |
|---|---|
| **Context** | Goal as penetration testers is to help provide a better operational picture of the customer's network to their defenders and improve security posture; understand common defense tactics and how they affect assessed networks; basic hardening steps do more than purchasing the next big EDR or SIEM tool — extra equipment only helps if baseline security (logging, documentation, tracking) is in place |
| **Step One: Document and Audit** | Proper AD hardening keeps attackers contained and prevents lateral movement, privilege escalation, and access to sensitive data; essential step is understanding everything in the AD environment; audit annually (if not every few months) to keep records up to date |
| **Things to document and track** | Naming conventions of OUs, computers, users, groups; DNS, network, and DHCP configurations; intimate understanding of all GPOs and applied objects; assignment of FSMO roles; full and current application inventory; list of all enterprise hosts and locations; any trust relationships with other domains or outside entities; users with elevated permissions |
| **People, Process, Technology** | AD hardening broken into three categories encompassing hardware, software, and human aspects of any network |
| **People — overview** | Users remain the weakest link even in the most hardened environment; enforce security best practices for standard users and administrators to prevent "easy wins"; keep users educated and aware of threats |
| **People — password policy** | Strong password policy with a password filter disallowing common words (welcome, password, names of months/days/seasons, company name); use an enterprise password manager if possible |
| **People — service accounts** | Rotate passwords periodically for all service accounts |
| **People — local admin** | Disallow local administrator access on user workstations unless a specific business need exists |
| **People — RID-500** | Disable the default RID-500 local admin account and create a new admin account for administration subject to LAPS password rotation |
| **People — split tiers** | Implement split tiers of administration; often during an assessment, Domain Admin credentials are found on a computer an admin uses for all work activities |
| **People — clean up privileged groups** | Does the organization need 50+ Domain/Enterprise Admins? Restrict group membership in highly privileged groups to only those requiring access for day-to-day duties |
| **People — Protected Users** | Where appropriate, place accounts in the **Protected Users** group; disable Kerberos delegation for administrative accounts (Protected Users may not do this) |
| **Protected Users group — overview** | First appeared with Windows Server 2012 R2; restricts what members can do in a domain; prevents user credentials from being abused if left in memory on a host |
| **Protected Users — enumerate** | `Get-ADGroup -Identity "Protected Users" -Properties Name,Description,Members` → Description, DistinguishedName `CN=Protected Users,CN=Users,DC=INLANEFREIGHT,DC=LOCAL`, GroupCategory Security, GroupScope Global, Members `sqlprod`, `sqldev`, Name, ObjectClass, ObjectGUID, SamAccountName, SID `S-1-5-21-2974783224-3764228556-2640795941-525` |
| **Protected Users — DC/device protections** | Members cannot be delegated with constrained or unconstrained delegation; CredSSP will not cache plaintext credentials in memory even if "Allow delegating default credentials" is set; Windows Digest will not cache plaintext password even if enabled; members cannot authenticate using NTLM or use DES or RC4 keys; after acquiring a TGT, long-term keys or plaintext credentials are not cached; members cannot renew a TGT longer than the original 4-hour TTL |
| **Protected Users — caution** | Can cause unforeseen issues with authentication, easily resulting in account lockouts; never place all privileged users in this group without staged testing |
| **Processes — overview** | Maintaining and enforcing policies and procedures significantly impacts overall security posture; without defined policies, impossible to hold employees accountable and difficult to respond to incidents without defined and practiced procedures (e.g., disaster recovery plan) |
| **Processes — items** | Proper policies/procedures for AD asset management; AD host audit, asset tags, periodic asset inventories; access control policies (user account provisioning/de-provisioning), MFA mechanisms; processes for provisioning and decommissioning hosts (baseline security hardening guideline, gold images); AD cleanup policies (are former employee accounts removed or just disabled? process for removing stale records?); processes for decommissioning legacy OS/services (e.g., proper uninstallation of Exchange when migrating to O365); schedule for user, group, and host audits |
| **Technology — overview** | Periodically review AD for legacy misconfigurations and new/emerging threats; as changes are made to AD, ensure common misconfigurations are not introduced; pay attention to vulnerabilities introduced by AD and tools/applications in the environment |
| **Technology — items** | Run tools like BloodHound, PingCastle, Grouper periodically to identify AD misconfigurations; ensure administrators are not storing passwords in the AD account description field; review SYSVOL for scripts containing passwords and other sensitive data; avoid "normal" service accounts — use gMSA/MSA wherever possible to mitigate Kerberoasting risk; disable Unconstrained Delegation wherever possible; prevent direct access to DCs through hardened jump hosts; consider setting `ms-DS-MachineAccountQuota` to 0 (disallows users from adding machine accounts; prevents attacks such as noPac and RBCD); disable the print spooler service wherever possible; disable NTLM authentication for DCs if possible; use Extended Protection for Authentication + Require SSL only to allow HTTPS for CA Web Enrollment and Certificate Enrollment Web Service; enable SMB signing and LDAP signing; take steps to prevent enumeration with tools like BloodHound; perform quarterly penetration tests/AD security assessments (annually at minimum if budget constrained); test backups for validity and review/practice disaster recovery plans; enable restriction of anonymous access and prevent null session enumeration by setting `RestrictNullSessAccess` registry key to 1 |
| **Protections by section — overview** | Significant actions broken out by section and correlated controls based on TTP and a MITRE tag; TA = overarching tactic, T### = technique under tactics in Enterprise ATT&CK Matrix |
| **TTP — External Reconnaissance** | MITRE Tag **T1589**: extremely hard to detect and defend against; attacker does not interact with your environment directly; monitor and control data released publicly (job postings, documents and metadata, open information sources like BGP and DNS records); scrub documents before release; avoid detailed information about tools/equipment in job postings |
| **TTP — Internal Reconnaissance** | MITRE Tag **T1595**: active phase generating network traffic; monitor for suspicious bursts of packets/large volume from one or several sources (indicative of scanning); properly configured Firewall/NIDS spots trends and alerts; may proactively add rules blocking traffic; network monitoring + SIEM crucial; tune Windows Firewall/EDR to not respond to ICMP and other traffic types to deny information |
| **TTP — Poisoning** | MITRE Tag **T1557**: use SMB message signing and strong encryption to stop poisoning & MITM attacks; SMB signing uses hashed authentication codes and verifies sender/recipient identity; breaks relay attacks since attacker is just spoofing traffic |
| **TTP — Password Spraying** | MITRE Tag **T1110/003**: easiest to defend/detect; simple logging and monitoring tips you off; watch Event IDs **4624** and **4648** for strings of invalid attempts; strong password policies, account lockout policy, 2FA/MFA help prevent success; reference recommended policy settings and NIST documentation |
| **TTP — Credentialed Enumeration** | MITRE Tag **TA0006**: no real defense once attacker has valid credentials — can perform any action the user is allowed; vigilant defender can detect and stop; monitor unusual activity (CLI commands when user shouldn't need it, multiple RDP requests host-to-host, movement of files from various hosts); if attacker acquires admin privileges, much more difficult — network heuristics tools analyze network constantly for anomalous activity; network segmentation helps a lot |
| **TTP — LOTL** | MITRE Tag **N/A**: hard to spot attacker using built-in OS resources; baseline of network traffic and user behavior helps; defenders must understand day-to-day regular activity to spot abnormal; watch for command shells; properly configured AppLocker policy prevents use of applications/tools users shouldn't access |
| **TTP — Kerberoasting** | MITRE Tag **T1558/003**: widely documented; plenty of ways to spot and defend; number one protection is stronger encryption than RC4 for Kerberos authentication; strong password policies prevent success; Group Managed service accounts are probably best defense (makes Kerberoasting no longer possible); periodically audit user account permissions for excessive group membership |
| **MITRE ATT&CK breakdown — Kerberoasting example** | Kerberoasting is part of Tactic **TA0006 Credential Access** (green); within scope, scroll to **Steal or Forge Kerberos Tickets** = Technique **T1558** (blue); contains four sub-techniques (.00#): Golden Ticket, Silver Ticket, Kerberoasting, AS-REP Roasting; select sub-technique **T1558.003** (orange) → new page with general explanation, ATT&CK platform classification, real-world use examples, mitigations/detections, references; technique classified under **TA0006/T1558.003** |
| **Closing thoughts** | Not an exhaustive list of defensive measures but a strong start; as attackers, understanding potential defenses helps plan alternate means of exploitation and movement; won't win every battle — some defenders lock down environments and see every move, others may have missed one of these recommendations; explore them all and help provide the defensive team with the best results; understanding attacks and defenses improves us as cybersecurity practitioners |

| **PingCastle — value** | Helpful for thorough domain enumeration combined with other tools; gives clients a quick analysis of domain security posture; can be used by internal teams to self-assess and find areas of concern/opportunities for further hardening |
| **Group3r — overview** | Excellent tool purpose-built to find vulnerabilities in Active Directory associated Group Policy; must be run from a domain-joined host with a domain user (does not need to be administrator), or in the context of a domain user (e.g., using `runas /netonly`) |
| **Group3r — basic usage** | `group3r.exe -f <filepath-name.log>`; must specify `-s` (send results to stdout) or `-f` (send results to file); use `-h` for more options and usage info |
| **Group3r — reading output** | Each indentation is a different level: no indent = the GPO, one indent = policy settings, another = findings in those settings |
| **Group3r — finding example** | Registry updates for `LDAPServerIntegrity`, `RequireSignOrSeal`, `RequireSecuritySignature`, `EnableSecuritySignature`, plus user rights assignment details; presents a linked box to the policy setting, defines the interesting portion, and gives a reason for the finding |

| **ADRecon — overview** | Several other tools gather a large amount of data from AD at once; in an assessment where stealth is not required, worth running ADRecon and analyzing results in case enumeration missed something minor useful or worth pointing out to the client |
